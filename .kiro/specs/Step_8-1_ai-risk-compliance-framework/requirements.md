# Requirements Document

## Introduction

This document specifies the requirements for the AI Risk & Compliance Framework (Phase 8.1) of AlcoaBase. The framework establishes a formal classification system that categorizes all AI-powered features into risk tiers (High, Medium, Low) based on their potential impact on GxP-regulated processes. It defines task-specific control measures, human-in-the-loop (HITL) requirements, validation depth, and audit logging granularity for each tier.

The framework serves as the foundational governance layer for all AI operations within AlcoaBase. It integrates with the existing Multi-Agent Auditing system (5.2), AI Document Generator (5.4), RAG Knowledge Base (4.2), AI Training Ecosystem (5.3), Change Impact Analysis (5.5), Traceability & Gap Discovery (5.6), and the Audit Trail (6.3) to enforce tier-appropriate controls at runtime. Each company/tenant can customize risk classifications and control sets to align with their specific regulatory context (GMP, GLP, GCP, ISO 13485, IVDR).

This framework is a prerequisite for Phase 8.4 (Cross-Sector AI Regulatory Guidelines) and provides the structural foundation for all subsequent governance documents.

## Glossary

- **Risk_Classification_Service**: The backend service responsible for managing AI task risk classifications, evaluating risk tier assignments, and enforcing tier-specific control requirements at runtime.
- **Risk_Tier**: A classification level (High, Medium, Low) assigned to an AI task type that determines the depth of validation, HITL requirements, and audit logging granularity applied to that task.
- **AI_Task_Type**: A categorized AI operation within AlcoaBase (e.g., document_generation, multi_agent_audit, rag_query, training_content_generation, change_impact_analysis, traceability_discovery). Each task type maps to exactly one Risk_Tier per company.
- **Control_Set**: A collection of control measures (HITL checkpoints, validation requirements, audit logging depth, review gates) that are enforced for a specific Risk_Tier.
- **HITL_Checkpoint**: A mandatory human-in-the-loop intervention point where a qualified user must review, approve, or reject AI-generated output before it progresses in the system.
- **Validation_Requirement**: A specific validation action (e.g., automated consistency check, cross-reference verification, format validation) that must pass before AI output is accepted.
- **Audit_Depth**: The granularity of audit logging for an AI operation: "full" (all inputs, outputs, intermediate steps, token counts, model parameters), "standard" (inputs, outputs, model used, duration), or "minimal" (operation type, timestamp, user, success/failure).
- **Risk_Assessment_Record**: An immutable record documenting the rationale for a risk tier assignment, including the assessor, assessment date, risk factors considered, and regulatory references.
- **Control_Enforcement_Log**: An audit record created each time a control measure is enforced (or bypassed) during an AI operation, providing evidence of compliance.
- **Company_Risk_Profile**: A per-tenant configuration that maps AI_Task_Types to Risk_Tiers and defines company-specific control overrides, regulatory framework alignment, and HITL role requirements.
- **Default_Risk_Profile**: The system-provided baseline risk classification that applies when a company has not configured a custom Company_Risk_Profile.
- **Risk_Override**: A documented deviation from the Default_Risk_Profile where a company assigns a different Risk_Tier to an AI_Task_Type, requiring a justification and approval.
- **Control_Gate**: A runtime enforcement point in the AI execution pipeline that checks whether all required controls for the applicable Risk_Tier have been satisfied before allowing the operation to proceed or its output to be consumed.
- **Regulatory_Framework**: A named regulatory standard (e.g., "GMP", "GLP", "GCP", "ISO 13485", "21 CFR Part 11", "EU AI Act") that influences risk tier assignments and control requirements.

## Requirements

### Requirement 1: AI Task Type Registry

**User Story:** As a system administrator, I want a centralized registry of all AI-powered task types in AlcoaBase with their descriptions and default risk classifications, so that the system has a single source of truth for what AI operations exist and how they are governed.

#### Acceptance Criteria

1. THE Risk_Classification_Service SHALL maintain a registry of AI_Task_Types with the following fields per entry: task_type_id (unique string identifier, maximum 100 characters, lowercase alphanumeric and underscores only), display_name (maximum 200 characters), description (maximum 2000 characters), module_reference (the AlcoaBase phase/feature that implements the task, e.g., "5.4"), default_risk_tier (High, Medium, or Low), risk_factors (array of strings describing why this tier was assigned, maximum 20 entries, each entry maximum 500 characters), and is_active (boolean).
2. THE Risk_Classification_Service SHALL include the following AI_Task_Types in the Default_Risk_Profile: "document_generation" (High — generates GxP-regulated content that may enter approval workflows), "multi_agent_audit" (High — produces compliance assessments that influence approval decisions), "training_content_generation" (High — generates training materials and assessments that gate user access to GxP operations), "change_impact_analysis" (Medium — identifies affected documents but does not modify them), "traceability_gap_discovery" (Medium — identifies gaps but does not create or modify traceability records), "rag_knowledge_query" (Low — retrieves and summarizes existing approved content without creating new records), "document_search" (Low — performs hybrid search across existing indexed content), "template_analysis" (Low — analyzes document structure without generating content).
3. THE Risk_Classification_Service SHALL expose a GET /api/risk-framework/task-types endpoint that returns all registered AI_Task_Types with their default risk tier and current company-specific tier (if overridden), supporting pagination via limit (default 20, maximum 100) and offset (default 0) query parameters, ordered by task_type_id ascending.
4. THE Risk_Classification_Service SHALL expose a GET /api/risk-framework/task-types/{task_type_id} endpoint that returns the full detail of a single AI_Task_Type including its risk factors, control set, and any company-specific overrides.
5. IF a request to GET /api/risk-framework/task-types/{task_type_id} specifies a task_type_id that does not exist in the registry, THEN THE Risk_Classification_Service SHALL return an HTTP 404 response with an error message indicating the requested task type was not found.
6. THE Risk_Classification_Service SHALL scope all task type queries to include both system-defined (global) task types and any company-specific custom task types registered for the company identified by the X-Company-Id header.
7. IF a new AI feature is added to AlcoaBase that performs inference operations, THEN THE Risk_Classification_Service SHALL require that feature to register an AI_Task_Type before it can invoke the InferenceClient, enforced via a pre-execution check in the AI execution pipeline that rejects the inference request with an error indicating the task type is not registered.

### Requirement 2: Risk Tier Definitions and Control Sets

**User Story:** As a compliance officer, I want clearly defined control measures for each risk tier (High, Medium, Low), so that I can verify that appropriate safeguards are applied to AI operations based on their potential impact on regulated processes.

#### Acceptance Criteria

1. THE Risk_Classification_Service SHALL define the High Risk_Tier Control_Set with the following mandatory controls: (a) HITL_Checkpoint required before AI output enters any approval workflow or becomes visible to end users, (b) full Audit_Depth logging of all inputs, outputs, intermediate reasoning steps, token counts, model parameters, and inference duration, (c) automated Validation_Requirements including format validation against the expected output schema, cross-reference consistency check verifying that all referenced document identifiers and version numbers exist in the system, and content completeness check confirming all required output sections are present and non-empty, (d) mandatory Generation_Provenance record creation (linking to existing 5.4 provenance), (e) maximum 72-hour validity window after which unreviewed output expires, is marked as "Expired", and must be regenerated before it can be used in any downstream process.
2. THE Risk_Classification_Service SHALL define the Medium Risk_Tier Control_Set with the following mandatory controls: (a) HITL_Checkpoint required before AI output is used to trigger automated actions (e.g., creating tasks, sending notifications), (b) standard Audit_Depth logging of inputs, outputs, model used, and duration, (c) automated Validation_Requirements including format validation against the expected output schema, (d) output flagged with "AI-assisted" label visible in the UI.
3. THE Risk_Classification_Service SHALL define the Low Risk_Tier Control_Set with the following mandatory controls: (a) no mandatory HITL_Checkpoint (output may be presented directly to users), (b) minimal Audit_Depth logging of operation type, timestamp, user, and success/failure status, (c) output flagged with "AI-generated" indicator in the UI, (d) rate limiting of 100 requests per user per hour to prevent automated misuse.
4. THE Risk_Classification_Service SHALL expose a GET /api/risk-framework/tiers endpoint that returns the three tier definitions with their complete Control_Sets, including all control measures, their enforcement type (mandatory or recommended), and applicable regulatory references, within 2 seconds of receiving the request.
5. THE Risk_Classification_Service SHALL expose a GET /api/risk-framework/tiers/{tier_level} endpoint that returns the full Control_Set for a specific tier (high, medium, or low), including descriptions of each control measure and whether the control is enforced automatically by the system or requires manual verification by the operator.
6. IF a request to GET /api/risk-framework/tiers/{tier_level} specifies a tier_level value other than "high", "medium", or "low", THEN THE Risk_Classification_Service SHALL return an error response indicating the provided tier level is not recognized and listing the valid tier level values.
7. WHEN the 72-hour validity window for a High Risk_Tier AI output elapses without a completed HITL review, THEN THE Risk_Classification_Service SHALL mark the output status as "Expired" and prevent the output from being referenced or consumed by any downstream workflow or approval process.

### Requirement 3: Company-Specific Risk Profile Configuration

**User Story:** As a company administrator, I want to customize risk tier assignments for AI task types within my company, so that our risk classifications align with our specific regulatory context and risk appetite.

#### Acceptance Criteria

1. THE Risk_Classification_Service SHALL allow each company to create a Company_Risk_Profile that overrides the Default_Risk_Profile for specific AI_Task_Types.
2. THE Risk_Classification_Service SHALL expose a POST /api/risk-framework/profiles endpoint that creates a Company_Risk_Profile containing: profile_name (minimum 3 characters, maximum 200 characters), description (maximum 2000 characters, optional), regulatory_frameworks (array of 1 to 20 applicable framework identifiers), and overrides (array of 1 to 50 entries, each containing {task_type_id, assigned_tier, justification (minimum 50 characters, maximum 2000 characters)}). This endpoint SHALL require the X-Change-Reason header and SHALL return the created profile with its generated profile_id.
3. THE Risk_Classification_Service SHALL expose a GET /api/risk-framework/profiles endpoint that returns the active Company_Risk_Profile for the company identified by the X-Company-Id header, including all overrides and their justifications. IF no active Company_Risk_Profile exists for the company, THEN THE endpoint SHALL return HTTP 404 with an indication that no custom profile is configured.
4. THE Risk_Classification_Service SHALL expose a PUT /api/risk-framework/profiles/{profile_id} endpoint that updates an existing Company_Risk_Profile. Updatable fields SHALL be: profile_name, description, regulatory_frameworks, and overrides (subject to the same escalation/de-escalation rules as profile creation). This endpoint SHALL require the X-Change-Reason header. IF the profile_id does not exist or does not belong to the requesting company, THEN THE endpoint SHALL return HTTP 404.
5. WHEN a company overrides a risk tier, THE Risk_Classification_Service SHALL only permit escalation (Low→Medium, Low→High, Medium→High) without additional approval. De-escalation (High→Medium, High→Low, Medium→Low) SHALL require a Risk_Override record with: justification (minimum 50 characters), regulatory_reference (the specific regulation or guidance that supports the de-escalation), approved_by (user_id of a user with system_admin or doc_admin role), and approval_date.
6. THE Risk_Classification_Service SHALL create a Risk_Assessment_Record for every tier assignment change (both escalation and de-escalation), capturing: task_type_id, previous_tier, new_tier, assessor_user_id, assessment_date, justification, and regulatory_references.
7. THE Risk_Classification_Service SHALL enforce that a company can have at most one active Company_Risk_Profile at any time. Creating a new profile SHALL deactivate the previous one (soft-delete with is_active=false) while preserving it for audit purposes.
8. IF no Company_Risk_Profile exists for a company, THEN THE Risk_Classification_Service SHALL apply the Default_Risk_Profile for all risk tier lookups.
9. THE Risk_Classification_Service SHALL scope all profile operations to the company identified by the X-Company-Id header, and all mutating endpoints SHALL require the X-Change-Reason header.
10. IF a profile creation or update request references a task_type_id that does not exist in the AI_Task_Type registry, THEN THE Risk_Classification_Service SHALL reject the request with HTTP 422 and an error indicating which task_type_id values are invalid.
11. IF a profile creation or update request contains duplicate task_type_id values within the overrides array, THEN THE Risk_Classification_Service SHALL reject the request with HTTP 422 and an error indicating the duplicated entries.

### Requirement 4: Runtime Control Gate Enforcement

**User Story:** As a system, I want to enforce risk-tier-appropriate controls at runtime before and after AI operations execute, so that no AI output bypasses the required validation, HITL checkpoints, or audit logging for its assigned tier.

#### Acceptance Criteria

1. THE Risk_Classification_Service SHALL provide a Control_Gate dependency that AI service functions invoke before executing an inference operation. The Control_Gate SHALL resolve the applicable Risk_Tier for the given AI_Task_Type and company_id, then verify that all pre-execution controls required by that tier (HITL reviewer availability for High/Medium tiers, audit trail writability, metadata tagging capability) are confirmable before allowing the inference call to proceed.
2. WHEN a High-tier AI operation completes, THE Control_Gate SHALL prevent the output from being persisted to any user-visible location (document records, search index entries, dashboard displays) until a HITL_Checkpoint is satisfied by a human reviewer submitting an explicit approve or reject action through the existing review workflow (5.4 Requirement 6 or 5.2 review pipeline).
3. WHEN a Medium-tier AI operation completes, THE Control_Gate SHALL flag the output with an "ai_assisted" metadata tag and prevent it from triggering automated downstream actions (task creation, notification dispatch, workflow transitions) until a HITL_Checkpoint is satisfied by a human reviewer submitting an explicit approve or reject action through the existing review workflow.
4. WHEN a Low-tier AI operation completes, THE Control_Gate SHALL allow the output to be presented directly to the requesting user without blocking, while applying the "ai_generated" metadata tag.
5. THE Control_Gate SHALL create a Control_Enforcement_Log record for every AI operation, containing: task_type_id, risk_tier_applied, company_id, user_id, operation_timestamp, controls_enforced (array of control names), controls_satisfied (boolean per control), overall_gate_result (passed or blocked), and blocking_reason (if blocked).
6. IF the Control_Gate determines that a required control cannot be enforced (HITL reviewer pool is empty for the company, audit trail service is unreachable, or validation service is unavailable), THEN THE Control_Gate SHALL block the operation and return an error indicating which specific control could not be satisfied, without executing the inference call.
7. IF no Risk_Tier is configured for the given AI_Task_Type and company_id combination, THEN THE Control_Gate SHALL block the operation and return an error indicating that the task type has no assigned risk tier, without executing the inference call.
8. THE Control_Gate SHALL enforce audit logging at the depth specified by the applicable tier's Audit_Depth setting, delegating to the existing audit trail infrastructure (6.3).
9. THE Control_Gate SHALL complete its pre-execution checks within 500 milliseconds. IF the check exceeds this threshold, THEN THE Control_Gate SHALL log a performance warning but still complete the check rather than bypassing controls.
10. IF a HITL_Checkpoint for a High-tier or Medium-tier operation is neither approved nor rejected within 72 hours of the operation completing, THEN THE Control_Gate SHALL flag the pending output for escalation and record an escalation entry in the Control_Enforcement_Log.

### Requirement 5: HITL Checkpoint Management

**User Story:** As a quality manager, I want to manage human-in-the-loop checkpoints for high-risk AI operations, so that qualified personnel review and approve AI outputs before they affect regulated processes.

#### Acceptance Criteria

1. THE Risk_Classification_Service SHALL expose a GET /api/risk-framework/checkpoints endpoint that returns all pending HITL_Checkpoints for the current company, filterable by: task_type_id, status (pending, approved, rejected, expired), assigned_reviewer (user_id), and date range (ISO 8601 date strings for start_date and end_date query parameters). Pagination SHALL be supported via limit (default 20, maximum 100) and offset (default 0) query parameters.
2. THE Risk_Classification_Service SHALL expose a POST /api/risk-framework/checkpoints/{checkpoint_id}/review endpoint that accepts {action ("approve" or "reject"), reviewer_comments (maximum 2000 characters), reviewed_sections (optional array of section identifiers that were reviewed, maximum 50 items)} and transitions the checkpoint status from "pending" to the corresponding terminal state. This endpoint SHALL require the X-Change-Reason header.
3. WHEN a HITL_Checkpoint is created for a High-tier operation, THE Risk_Classification_Service SHALL record: checkpoint_id, operation_id (reference to the AI operation), task_type_id, ai_output_reference (storage location of the output awaiting review), created_at, expires_at (72 hours from creation), assigned_reviewer_role (the minimum role required to review: system_admin or doc_admin), and status (pending).
4. WHEN a HITL_Checkpoint is approved, THE Risk_Classification_Service SHALL update the checkpoint status to "approved", persist the associated AI output to user-visible locations, enable any blocked workflow transitions dependent on that output, and record the approval (including reviewer user_id, timestamp, and reviewer_comments) in the Control_Enforcement_Log.
5. WHEN a HITL_Checkpoint is rejected, THE Risk_Classification_Service SHALL update the checkpoint status to "rejected", mark the associated AI output as rejected to prevent it from being persisted to user-visible locations or triggering workflow transitions, and record the rejection (including reviewer user_id, timestamp, and reviewer_comments) in the Control_Enforcement_Log.
6. WHEN a HITL_Checkpoint expires (72 hours without review for High-tier), THE Risk_Classification_Service SHALL mark the checkpoint status as "expired", mark the associated AI output as invalid, and create an alert visible in the compliance dashboard indicating an unreviewed high-risk AI output has expired.
7. THE Risk_Classification_Service SHALL enforce that only users with the assigned_reviewer_role (system_admin or doc_admin) can approve or reject HITL_Checkpoints. IF a user without the required role attempts to review, THEN THE Risk_Classification_Service SHALL return HTTP 403.
8. THE Risk_Classification_Service SHALL scope all checkpoint operations (list, review, and status queries) to the company identified by the X-Company-Id header.
9. IF a user attempts to review a HITL_Checkpoint whose status is not "pending" (already approved, rejected, or expired), THEN THE Risk_Classification_Service SHALL reject the request with HTTP 409 and return an error message indicating the current checkpoint status.
10. IF two users submit a review for the same HITL_Checkpoint concurrently, THEN THE Risk_Classification_Service SHALL accept only the first review that transitions the status from "pending" and reject the subsequent attempt with HTTP 409.
11. IF the reviewer_comments field is empty when action is "reject", THEN THE Risk_Classification_Service SHALL reject the request with HTTP 422 and return an error message indicating that reviewer comments are required for rejections.

### Requirement 6: Audit Depth Enforcement and Logging

**User Story:** As a regulatory auditor, I want AI operations to be logged at a depth proportional to their risk tier, so that high-risk operations have complete traceability while low-risk operations do not generate excessive log volume.

#### Acceptance Criteria

1. WHEN a High-tier AI operation executes, THE Risk_Classification_Service SHALL log at "full" Audit_Depth: complete input prompt/context (truncated to 50,000 characters if exceeding), complete output response (truncated to 50,000 characters if exceeding), model_name, model_version, temperature, max_tokens, top_p, token_count_input, token_count_output, inference_duration_ms, all intermediate chain-of-thought steps (for multi-step pipelines), source documents referenced (document_ids and chunk excerpts limited to 200 characters each), and the Control_Enforcement_Log entry.
2. WHEN a Medium-tier AI operation executes, THE Risk_Classification_Service SHALL log at "standard" Audit_Depth: input summary (first 1000 characters of the prompt), complete output response (truncated to 50,000 characters if exceeding), model_name, token_count_input, token_count_output, inference_duration_ms, source document_ids referenced (without chunk excerpts), and the Control_Enforcement_Log entry.
3. WHEN a Low-tier AI operation executes, THE Risk_Classification_Service SHALL log at "minimal" Audit_Depth: task_type_id, user_id, company_id, timestamp, success_or_failure status, inference_duration_ms, and token_count_output.
4. THE Risk_Classification_Service SHALL persist all audit depth logs to a dedicated ai_operation_log table that follows the same immutability rules as the main audit trail (no UPDATE or DELETE operations permitted), and SHALL reject any attempt to UPDATE or DELETE a log entry by returning an error indicating the operation is forbidden.
5. THE Risk_Classification_Service SHALL expose a GET /api/risk-framework/operation-logs endpoint that returns AI operation logs for the current company, filterable by: task_type_id, risk_tier, user_id, date range, and success/failure status. Pagination SHALL be supported via limit (default 20, maximum 100) and offset (default 0) query parameters. Results SHALL be ordered by timestamp descending (most recent first) by default.
6. THE Risk_Classification_Service SHALL enforce a retention policy of minimum 7 years for High-tier logs, 3 years for Medium-tier logs, and 1 year for Low-tier logs, aligned with GxP record retention requirements.
7. THE Risk_Classification_Service SHALL scope all operation log queries to the company identified by the X-Company-Id header.
8. IF a High-tier or Medium-tier AI operation completes (whether successfully or with failure), THEN THE Risk_Classification_Service SHALL write the audit log entry synchronously before returning the operation response to the caller; IF the log write itself fails, THEN THE Risk_Classification_Service SHALL return an error indicating the operation result could not be persisted for audit purposes and SHALL NOT return the AI operation output to the caller.
9. WHEN an AI operation fails during execution, THE Risk_Classification_Service SHALL log the operation at the same Audit_Depth as a successful operation of the same tier, recording a status of "failure" and including available fields up to the point of failure (fields unavailable due to the failure SHALL be recorded as null).

### Requirement 7: Risk Framework Administration UI

**User Story:** As a company administrator, I want a dedicated UI page to view risk tier assignments, manage my company's risk profile, review pending HITL checkpoints, and monitor AI operation compliance, so that I can govern AI usage from a single location.

#### Acceptance Criteria

1. THE Risk_Framework_Page SHALL be accessible at route /admin/ai-risk-framework and restricted to users with system_admin or doc_admin roles. IF a user without system_admin or doc_admin role navigates to /admin/ai-risk-framework, THEN THE Risk_Framework_Page SHALL redirect the user to the main dashboard and display an access denied notification.
2. THE Risk_Framework_Page SHALL display a summary dashboard showing: count of AI operations by tier in the last 30 days, count of pending HITL checkpoints, count of expired checkpoints, count of blocked operations, and the company's active risk profile name. The summary dashboard SHALL retrieve data from the GET /api/risk-framework/dashboard-stats endpoint.
3. THE Risk_Framework_Page SHALL include a "Task Types" tab displaying all AI_Task_Types in a paginated table (20 rows per page, matching the backend limit default) with columns: display_name, module_reference, default_tier, company_tier (if overridden), and status (active/inactive). Each row SHALL be expandable to show risk_factors and the applicable Control_Set.
4. THE Risk_Framework_Page SHALL include a "Risk Profile" tab allowing administrators to: view the current Company_Risk_Profile, create a new profile, add/remove tier overrides with justification (minimum 50 characters for de-escalation overrides), and view the history of profile changes. WHEN an administrator adds a de-escalation override (High→Medium, High→Low, or Medium→Low), THE Risk_Framework_Page SHALL require a regulatory_reference field and display a notice that the override requires approval by a system_admin or doc_admin user.
5. THE Risk_Framework_Page SHALL include a "HITL Queue" tab displaying pending checkpoints in a paginated table (20 rows per page) sorted by expires_at ascending (nearest expiry first) with columns: operation type, created date, expires date, status, and a "Review" action button. WHEN the administrator clicks the "Review" button, THE Risk_Framework_Page SHALL open a detail panel displaying the AI output content, operation metadata, and approve/reject action controls with a reviewer_comments field (maximum 2000 characters).
6. THE Risk_Framework_Page SHALL include an "Operation Logs" tab displaying the most recent 20 AI operation logs (paginated, 20 per page) with filtering by task type, tier, date range, and outcome (passed/blocked). The tab SHALL retrieve data from the GET /api/risk-framework/operation-logs endpoint.
7. THE Risk_Framework_Page SHALL use shadcn/ui components consistent with the existing AlcoaBase admin interface design.
8. THE Risk_Framework_Page SHALL display a visual risk matrix (3x3 grid) on the summary dashboard tab showing AI_Task_Types positioned by their impact severity (vertical axis: Low, Medium, High) and likelihood (horizontal axis: Low, Medium, High), color-coded by their assigned Risk_Tier (High, Medium, Low). The position of each AI_Task_Type SHALL be derived from its risk_factors as defined in the AI_Task_Type registry.

### Requirement 8: Database Models for Risk Framework

**User Story:** As a backend developer, I want well-defined database models for risk classifications, control sets, company profiles, HITL checkpoints, and operation logs, so that all risk framework data is persisted with full audit trail support.

#### Acceptance Criteria

1. THE AITaskType model SHALL include: id (UUID), task_type_id (unique string, maximum 100 characters), display_name (String 200), description (Text), module_reference (String 100), default_risk_tier (enum: High, Medium, Low), risk_factors (JSON array of strings), is_active (boolean default true), is_system_defined (boolean default true), company_id (nullable FK to companies — null for system-defined, set for company-custom), created_at (timestamp with timezone, server-generated), updated_at (timestamp with timezone, server-generated on update).
2. THE CompanyRiskProfile model SHALL include: id (UUID), company_id (FK to companies), profile_name (String 200), description (Text nullable), regulatory_frameworks (JSON array of strings), is_active (boolean default true), created_by (FK to users), created_at (timestamp with timezone, server-generated), updated_at (timestamp with timezone, server-generated on update). THE model SHALL enforce a unique constraint on (company_id, is_active) filtered to is_active=true, ensuring at most one active profile per company.
3. THE RiskTierOverride model SHALL include: id (UUID), profile_id (FK to CompanyRiskProfile), task_type_id (String 100), assigned_tier (enum: High, Medium, Low), justification (Text, minimum 50 characters when assigned_tier is lower than the task type's default_risk_tier), regulatory_reference (Text nullable), approved_by (nullable FK to users — required when assigned_tier is lower than the task type's default_risk_tier), approval_date (nullable timestamp with timezone — required when approved_by is set), created_at (timestamp with timezone, server-generated).
4. THE RiskAssessmentRecord model SHALL include: id (UUID), company_id (FK to companies), task_type_id (String 100), previous_tier (enum: High, Medium, Low, nullable for initial assignment), new_tier (enum: High, Medium, Low), assessor_user_id (FK to users), assessment_date (timestamp with timezone), justification (Text), regulatory_references (JSON array of strings), created_at (timestamp with timezone, server-generated).
5. THE HITLCheckpoint model SHALL include: id (UUID), company_id (FK to companies), operation_id (String 200 — reference to the AI operation), task_type_id (String 100), ai_output_reference (Text — URI or object storage key identifying the stored AI output), status (enum: pending, approved, rejected, expired), assigned_reviewer_role (String 50), reviewer_user_id (nullable FK to users), reviewer_comments (Text nullable), reviewed_sections (JSON array nullable), created_at (timestamp with timezone, server-generated), expires_at (timestamp with timezone), reviewed_at (nullable timestamp with timezone).
6. THE AIOperationLog model SHALL include: id (UUID), company_id (FK to companies), task_type_id (String 100), risk_tier (enum: High, Medium, Low), user_id (FK to users), audit_depth (enum: full, standard, minimal), input_data (JSONB nullable — stored when audit_depth is full or standard; null when minimal), output_data (JSONB nullable — stored when audit_depth is full or standard; null when minimal), model_name (String 200 nullable), inference_duration_ms (Integer nullable), token_count_input (Integer nullable), token_count_output (Integer nullable), gate_result (enum: passed, blocked), blocking_reason (Text nullable), source_document_ids (JSON array nullable), created_at (timestamp with timezone, server-generated).
7. THE ControlEnforcementLog model SHALL include: id (UUID), company_id (FK to companies), operation_log_id (FK to AIOperationLog), task_type_id (String 100), risk_tier (enum: High, Medium, Low), controls_enforced (JSON array of strings), controls_satisfied (JSON object mapping control name to boolean), overall_result (enum: passed, blocked), blocking_reason (Text nullable), enforcement_duration_ms (Integer), created_at (timestamp with timezone, server-generated).
8. THE AITaskType, CompanyRiskProfile, and HITLCheckpoint models SHALL use SQLAlchemy-Continuum versioning (via AuditMixin) for audit trail support. THE RiskAssessmentRecord, AIOperationLog, and ControlEnforcementLog models SHALL be immutable at the application layer by exposing no UPDATE or DELETE endpoints or service methods; attempted updates or deletes SHALL be rejected before reaching the database.
9. IF a HITLCheckpoint record has status "pending" and the current server time exceeds expires_at, THEN THE system SHALL treat the checkpoint as expired and prevent approval or rejection actions on that record.
10. WHEN a RiskTierOverride is created with an assigned_tier lower than the task type's default_risk_tier, THE system SHALL require that approved_by and justification (minimum 50 characters) are provided before persisting the record.

### Requirement 9: Integration with Existing AI Services

**User Story:** As a system architect, I want the risk framework to integrate seamlessly with existing AI services (Document Generator, Multi-Agent Auditing, RAG, Training Ecosystem, Change Impact Analysis, Traceability Discovery), so that controls are enforced without requiring complete rewrites of existing features.

#### Acceptance Criteria

1. THE Risk_Classification_Service SHALL provide a Python decorator `@risk_controlled(task_type_id="...")` that can be applied to any async service function performing AI inference. The decorator SHALL invoke the Control_Gate before execution and log the operation at the appropriate Audit_Depth after execution. IF the decorated function raises an exception during execution, THEN the decorator SHALL still log the operation to the AIOperationLog with gate_result "passed" (since pre-execution checks succeeded), record the exception type and message in the output_data field, mark success_or_failure as "failure", and re-raise the original exception to the caller.
2. WHEN the `@risk_controlled` decorator is applied to the Document_Generator's generation pipeline (5.4), THE Control_Gate SHALL enforce High-tier controls: blocking output persistence until HITL review is completed (integrating with the existing ContentStatus "pending_review" workflow from 5.4 Requirement 6).
3. WHEN the `@risk_controlled` decorator is applied to the Multi-Agent Auditing review pipeline (5.2), THE Control_Gate SHALL enforce High-tier controls: preventing the Master Auditor summary and compliance scores from being displayed in the document approval UI or used as input to approval workflow transitions until a HITL_Checkpoint is approved by a user with doc_admin or system_admin role.
4. WHEN the `@risk_controlled` decorator is applied to RAG knowledge queries (4.2), THE Control_Gate SHALL enforce Low-tier controls: allowing direct response to users with minimal logging and an "AI-generated" indicator on the response.
5. WHEN the `@risk_controlled` decorator is applied to Change Impact Analysis (5.5), THE Control_Gate SHALL enforce Medium-tier controls: flagging output as "AI-assisted" and requiring HITL review before the system creates automated tasks or notifications based on the analysis results.
6. WHEN the `@risk_controlled` decorator is applied to Training Content Generation (5.3), THE Control_Gate SHALL enforce High-tier controls: blocking generated training materials, quizzes, and assessments from being assigned to users until a doc_admin reviews and approves the content.
7. THE Risk_Classification_Service SHALL provide a utility function `get_effective_tier(task_type_id: str, company_id: UUID) -> RiskTier` that resolves the applicable tier by checking the Company_Risk_Profile first, falling back to the Default_Risk_Profile. IF the provided task_type_id does not exist in either the Company_Risk_Profile or the Default_Risk_Profile, THEN the function SHALL raise a ValueError indicating the unregistered task type.
8. THE Risk_Classification_Service SHALL not require modifications to the InferenceClient (4.3) interface. Control enforcement SHALL occur at the service layer above the inference client, wrapping existing service functions.
9. WHEN the `@risk_controlled` decorator is applied to Traceability Gap Discovery (5.6), THE Control_Gate SHALL enforce Medium-tier controls: flagging discovered gaps as "AI-assisted" and requiring HITL review before the system creates traceability link suggestions or gap resolution tasks visible to end users.

### Requirement 10: Risk Framework API Endpoints Summary

**User Story:** As a frontend developer, I want comprehensive REST endpoints for the risk framework, so that the administration UI can be fully functional.

#### Acceptance Criteria

1. THE system SHALL expose GET /api/risk-framework/task-types accepting query parameters limit (integer, default 20, maximum 100) and offset (integer, default 0), returning a JSON object containing items (array of AI task types with effective tier), total, limit, and offset.
2. THE system SHALL expose GET /api/risk-framework/task-types/{task_type_id} returning the full detail of a single task type including its name, description, effective tier assignment, and associated control set.
3. THE system SHALL expose GET /api/risk-framework/tiers returning all three tier definitions (High, Medium, Low) each including tier level, name, description, and the complete control set for that tier.
4. THE system SHALL expose GET /api/risk-framework/tiers/{tier_level} where tier_level is one of "high", "medium", or "low", returning a single tier definition with its control set.
5. THE system SHALL expose POST /api/risk-framework/profiles accepting a JSON body with the company risk profile configuration, requiring the X-Change-Reason header, and returning the created profile with its assigned profile_id and HTTP 201 status.
6. THE system SHALL expose GET /api/risk-framework/profiles returning the single currently active company risk profile for the tenant identified by X-Company-Id.
7. THE system SHALL expose PUT /api/risk-framework/profiles/{profile_id} accepting a JSON body with updated profile configuration, requiring the X-Change-Reason header, and returning the updated profile.
8. THE system SHALL expose GET /api/risk-framework/profiles/history accepting query parameters limit (integer, default 20, maximum 100) and offset (integer, default 0), returning a paginated list of all profile versions for audit purposes ordered by created_at descending.
9. THE system SHALL expose GET /api/risk-framework/checkpoints accepting query parameters limit (integer, default 20, maximum 100), offset (integer, default 0), and optional filters status and task_type_id, returning a paginated list of HITL checkpoints.
10. THE system SHALL expose POST /api/risk-framework/checkpoints/{checkpoint_id}/review accepting a JSON body containing an action field (value "approve" or "reject") and requiring the X-Change-Reason header, returning the updated checkpoint with its new status.
11. THE system SHALL expose GET /api/risk-framework/operation-logs accepting query parameters limit (integer, default 20, maximum 100), offset (integer, default 0), and optional filters task_type_id, risk_tier, and date_from/date_to, returning a paginated list of AI operation log entries ordered by timestamp descending.
12. THE system SHALL expose GET /api/risk-framework/dashboard-stats returning a JSON object containing summary counts for total operations (last 30 days), pending checkpoints, expired checkpoints, blocked operations, and operations per tier.
13. ALL risk-framework endpoints SHALL scope returned data exclusively to the company identified by the X-Company-Id request header; requests missing the X-Company-Id header SHALL receive HTTP 400.
14. IF a request is made to any risk-framework endpoint by a user whose role is not system_admin or doc_admin, THEN THE system SHALL return HTTP 403 with an error message indicating insufficient permissions.
15. IF a mutating request (POST or PUT) to any risk-framework endpoint is missing the X-Change-Reason header or provides an empty value, THEN THE system SHALL return HTTP 400 with an error message indicating that the X-Change-Reason header is required for mutating requests to GxP-relevant endpoints.
16. IF a GET request references a resource that does not exist (invalid task_type_id, unrecognized tier_level, unknown profile_id, or unknown checkpoint_id), THEN THE system SHALL return HTTP 404 with an error message indicating the resource was not found.
