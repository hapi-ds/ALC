# Requirements Document

## Introduction

This feature implements an AI Document Generator (Template-Based) (Phase 5.4) that uses existing .docx files stored in the system as "Master Templates" to guide the structural layout of newly generated regulatory documents. Unlike the JSON-driven Form Builder (Phase 2.4) which produces fillable forms for structured data entry, this engine focuses on high-volume text generation within standard word-processing formats (DOCX), producing complete regulatory documents such as URS (User Requirement Specifications), MVP (Master Validation Plans), SOPs, and similar GxP documentation.

The system synthesizes content from the company's RAG knowledge base (4.2) into the structural layout of a selected DOCX template, using the Technical Writer agent archetype (5.1) via the vLLM inference layer (4.3). It enforces cross-document consistency by ensuring generated documents correctly reference requirements, test cases, and other artifacts from related documents within the same company scope.

The existing `DocumentGenerator` service (placeholder DSPy pipeline) and `POST /api/documents/generate` endpoint provide the foundation. This feature replaces the placeholder generation with a template-aware, knowledge-driven generation pipeline that produces actual .docx output files stored in MinIO.

## Glossary

- **Template_Document**: An existing .docx file stored in the system (via DocumentVersion in MinIO) that has been designated as a "Master Template" for guiding the structure of generated documents. A Template_Document retains its section headings, numbering scheme, formatting conventions, and placeholder markers that the generation engine fills with synthesized content.
- **Document_Generator**: The AI service that orchestrates template-based document generation by analyzing a Template_Document's structure, retrieving relevant content from the knowledge base, and producing a new .docx file that follows the template's layout while containing AI-generated regulatory content.
- **Template_Analysis**: The structured representation of a Template_Document's layout, including section hierarchy (headings, sub-headings), numbering scheme, paragraph styles, table structures, header/footer patterns, and placeholder markers identified within the template.
- **Generation_Job**: An async Celery task that executes the full document generation pipeline (template analysis → knowledge retrieval → content generation → DOCX assembly → storage). Tracked via the JobTracker service with status reporting.
- **Cross_Reference_Map**: A data structure that maps identifiers (requirement IDs, test case IDs, section references) between related documents within the same company, enabling the Document_Generator to produce consistent inter-document references in generated output.
- **Content_Section**: A discrete unit of generated content corresponding to one section of the Template_Document. Contains the section heading, generated body text, any tables or lists, and metadata about which knowledge base sources contributed to the content.
- **Generation_Provenance**: An immutable audit record capturing: which Template_Document was used, which knowledge base sources were retrieved, which agent archetype was used, generation parameters, the requesting user, and timestamp. Extends the existing `GenerationProvenance` dataclass.
- **Technical_Writer**: The existing agent archetype (from 5.1) with agent_type "generation", temperature 0.4, max_tokens 8192, used for document content generation. Configured with evaluation rubric focused on clarity, completeness, structure, and accuracy.
- **InferenceClient**: The existing async HTTP client for vLLM communication (from 4.3).
- **KnowledgeService**: The existing RAG service for document retrieval, text extraction, and semantic search (from 4.2).
- **StorageService**: The existing MinIO S3-compatible storage service for document file persistence.
- **ContentStatus**: The review lifecycle status (pending_review, approved, rejected, draft) governing generated document progression through the approval workflow.
- **Placeholder_Marker**: A recognizable token within a Template_Document (e.g., `{{SECTION_CONTENT}}`, `{{REQUIREMENT_LIST}}`, `{{CROSS_REF:document_type}}`) that signals the Document_Generator where to insert generated content and what type of content is expected.

## Requirements

### Requirement 1: Template Document Registration and Analysis

**User Story:** As a document administrator, I want to designate existing .docx files as Master Templates and have the system analyze their structure, so that the AI generator can use them as blueprints for producing new documents.

#### Acceptance Criteria

1. THE Document_Generator SHALL expose a POST /api/documents/templates/register endpoint that accepts {document_id, document_version_id, template_name (maximum 500 characters), document_type_target (maximum 100 characters, e.g., "URS", "MVP", "SOP")} and returns HTTP 202 with a job_id for the async template analysis task. This endpoint SHALL require the X-Change-Reason header.
2. WHEN a template registration is requested, THE Document_Generator SHALL retrieve the .docx file from MinIO via StorageService, extract its structural layout using python-docx, and produce a Template_Analysis containing: section_hierarchy (ordered list of headings with levels), numbering_scheme (detected numbering format), paragraph_styles (list of named styles used), table_structures (count and column layouts of tables), header_footer_patterns (content of headers and footers), and placeholder_markers (list of detected Placeholder_Markers with their positions).
3. THE Document_Generator SHALL detect Placeholder_Markers in the template by scanning paragraph text for tokens matching the pattern `{{IDENTIFIER}}` or `{{IDENTIFIER:parameter}}`, where IDENTIFIER consists of 1 to 50 uppercase letters and underscores, and parameter is an optional qualifier of 1 to 100 characters.
4. THE Document_Generator SHALL persist the Template_Analysis as a JSON structure associated with the source DocumentVersion record, enabling reuse across multiple generation requests without re-analyzing the template.
5. THE Document_Generator SHALL expose a GET /api/documents/templates endpoint that returns all registered Template_Documents for the current company, filterable by document_type_target, with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters.
6. THE Document_Generator SHALL expose a GET /api/documents/templates/{template_id} endpoint that returns the full Template_Analysis for a specific registered template, including section hierarchy, detected placeholders, and metadata.
7. IF the specified document_version_id does not reference a .docx file (determined by storage_key extension or content type), THEN THE Document_Generator SHALL reject the registration with HTTP 422 and an error message indicating only .docx files can be registered as templates.
8. IF the .docx file cannot be retrieved from MinIO (file not found, access denied, or storage unavailable), THEN THE Document_Generator SHALL mark the registration job as failed with a reason indicating the file was inaccessible.
9. THE Document_Generator SHALL scope all template operations to the company identified by the X-Company-Id header.
10. IF a Template_Document registration already exists for the same document_version_id, THEN THE Document_Generator SHALL return the existing template registration without creating a duplicate, responding with HTTP 200 and the existing template_id.
11. IF the specified document_id or document_version_id does not exist or does not belong to the company identified by the X-Company-Id header, THEN THE Document_Generator SHALL reject the registration with HTTP 404 and an error message indicating the document or version was not found.
12. THE Document_Generator SHALL complete the template analysis Celery task within a maximum of 120 seconds. IF the analysis exceeds this timeout, THEN THE Document_Generator SHALL mark the registration job as failed with a reason indicating the analysis timed out.
13. IF the template_name is empty or exceeds 500 characters, or the document_type_target is empty or exceeds 100 characters, THEN THE Document_Generator SHALL reject the registration with HTTP 422 and an error message indicating the validation failure.

### Requirement 2: Template-Based Document Generation

**User Story:** As a regulatory affairs specialist, I want to generate new regulatory documents (URS, MVP, SOP) by selecting a Master Template and providing generation instructions, so that the AI produces a complete document following the template's structure while synthesizing relevant content from our knowledge base.

#### Acceptance Criteria

1. THE Document_Generator SHALL expose a POST /api/documents/generate-from-template endpoint that accepts {template_id, title (maximum 500 characters), generation_instructions (maximum 10000 characters), reference_document_ids (optional array of document_ids to use as primary sources, maximum 20 entries), output_folder_path (maximum 1000 characters)} and returns HTTP 202 with a job_id for the async generation task. This endpoint SHALL require the X-Change-Reason header.
2. WHEN a generation job is initiated, THE Document_Generator SHALL execute the following pipeline as a Celery task on the ai_operations queue: (a) load the Template_Analysis for the specified template_id, (b) retrieve relevant content from the knowledge base using generation_instructions and reference_document_ids as search context, (c) generate content for each section defined in the Template_Analysis using the Technical_Writer agent archetype via InferenceClient, (d) assemble the generated content into a .docx file preserving the template's formatting and structure, (e) store the output .docx in MinIO via StorageService, (f) create a Document record with status "Draft" and a DocumentVersion record pointing to the stored file.
3. THE Document_Generator SHALL generate content section-by-section, providing the InferenceClient with: the section heading, the section's position in the document hierarchy, content from preceding sections (for continuity), relevant knowledge base excerpts scoped to the section topic, and any Placeholder_Marker instructions specific to that section.
4. THE Document_Generator SHALL preserve the Template_Document's formatting in the output: heading styles and levels, numbering schemes, paragraph styles, table structures (populating cells with generated content where applicable), and header/footer content (substituting dynamic values such as document title, date, and version number).
5. WHEN reference_document_ids are provided, THE Document_Generator SHALL prioritize content from those documents over general knowledge base results, using them as primary source material for content synthesis.
6. THE Document_Generator SHALL produce output documents with a maximum size of 50 MB. IF the generated content would exceed this limit, THEN THE Document_Generator SHALL truncate generation at the last complete section that fits within the limit and record a warning in the job result.
7. THE Document_Generator SHALL record generation metadata including: inference_duration_ms (total time spent on LLM calls), total_token_count (sum of input and output tokens across all section generations), sections_generated (count of successfully generated sections), sections_total (total sections in template), and model_used.
8. THE Document_Generator SHALL scope all generation operations to the company identified by the X-Company-Id header.
9. IF the InferenceClient is unavailable or returns an error during content generation for a section, THEN THE Document_Generator SHALL retry that section once after a 5-second delay. IF the retry also fails, THEN THE Document_Generator SHALL insert a placeholder text "[GENERATION FAILED: Section requires manual completion]" for that section and continue with remaining sections, recording the failure in the job metadata.
10. IF the template_id does not exist or does not belong to the requesting company, THEN THE Document_Generator SHALL reject the request with HTTP 404 and an error message indicating the template was not found.
11. IF the knowledge base returns no relevant content for the generation instructions (zero search results), THEN THE Document_Generator SHALL mark the generation job as failed with a reason indicating insufficient source material was available.
12. IF any reference_document_ids do not exist or do not belong to the requesting company, THEN THE Document_Generator SHALL reject the request with HTTP 422 and an error message indicating which document IDs were not found, without initiating the generation job.
13. IF the generation_instructions field is empty or contains only whitespace, THEN THE Document_Generator SHALL reject the request with HTTP 422 and an error message indicating that generation instructions are required.

### Requirement 3: Cross-Document Consistency and Reference Resolution

**User Story:** As a quality manager, I want generated documents to correctly reference requirements, test cases, and sections from related documents, so that the generated MVP accurately cites the specific URS requirements it validates and maintains traceability.

#### Acceptance Criteria

1. WHEN generating a document with reference_document_ids specified, THE Document_Generator SHALL build a Cross_Reference_Map by extracting identifiable items from each reference document using the following patterns: requirement IDs matching `REQ-\d{1,5}` or `URS-\d{1,3}\.\d{1,3}`, test case IDs matching `TC-\d{1,5}` or `TEST-\d{1,5}`, section numbers matching heading-level numbering (e.g., "1", "1.1", "1.1.1" up to 4 levels), and document titles with their document_uuids. The Cross_Reference_Map SHALL contain a maximum of 500 entries per reference document.
2. THE Document_Generator SHALL instruct the Technical_Writer agent (via system prompt) to use Cross_Reference_Map entries when generating content that references other documents, ensuring generated text uses the exact identifiers and titles from the reference documents rather than fabricating references.
3. WHEN a Placeholder_Marker of the form `{{CROSS_REF:document_type}}` is encountered in the template, THE Document_Generator SHALL generate a cross-reference section that lists all items from reference documents matching the specified document_type, formatted as a table if the reference documents contain 5 or more extractable items, or as a numbered list if fewer than 5 items are found. Each entry SHALL include the reference_identifier, reference_text (first 150 characters), and source_document_title.
4. THE Document_Generator SHALL validate cross-references in the generated output by checking that every document_uuid, requirement ID, or section reference mentioned in the generated text exists in the Cross_Reference_Map. References that cannot be validated SHALL be flagged in the generation metadata as "unverified_references" with their location specified as section_number and paragraph_index within the output document.
5. THE Document_Generator SHALL expose a GET /api/documents/{document_id}/cross-references endpoint that returns the Cross_Reference_Map for a generated document, showing: source_document_id, source_document_title, reference_type (requirement, section, test_case), reference_identifier, and location_in_generated_document (section number and paragraph index).
6. IF no reference_document_ids are provided and the template contains `{{CROSS_REF:*}}` placeholders, THEN THE Document_Generator SHALL search the knowledge base for documents of the specified type within the same company and use the top 5 most relevant results to build the Cross_Reference_Map, recording which documents were auto-selected in the generation provenance.
7. THE Document_Generator SHALL scope all cross-reference operations to the company identified by the X-Company-Id header, ensuring references never span across company boundaries.
8. IF a reference document specified in reference_document_ids cannot be retrieved from storage or fails text extraction, THEN THE Document_Generator SHALL skip that document from the Cross_Reference_Map, record a warning in the generation metadata identifying the inaccessible document_id, and continue building the map from remaining reference documents.

### Requirement 4: DOCX Output Assembly and Formatting

**User Story:** As a document administrator, I want generated documents to be properly formatted .docx files that preserve the template's professional appearance, so that they can be used directly in our document management workflow without manual reformatting.

#### Acceptance Criteria

1. THE Document_Generator SHALL produce output .docx files using python-docx that replicate the Template_Document's: heading hierarchy (Heading 1 through Heading 4 styles), body paragraph style (Normal, with the same font family name and point size as the template), numbered and bulleted list formatting, table styles (borders, shading, column widths), and page layout (margins, orientation, page size).
2. THE Document_Generator SHALL populate the .docx document properties (core properties) with: title (from generation request), author (name of the requesting user), company (company name from tenant), created date (generation timestamp), and a custom property "generated_by" set to "AlcoaBase AI Document Generator v1.0".
3. THE Document_Generator SHALL preserve header and footer content from the Template_Document, substituting the following dynamic tokens if present in header/footer text: `{title}` with the document title, `{date}` with the generation date in ISO 8601 date format (YYYY-MM-DD), `{version}` with "1.0" for initial generation, and `{company}` with the company name. IF a token matching the `{identifier}` pattern is present in header/footer text but is not one of the four supported tokens, THEN THE Document_Generator SHALL leave that token text unchanged in the output and record a warning in the generation metadata identifying the unrecognized token.
4. WHEN the Template_Document contains tables with header rows, THE Document_Generator SHALL generate table content that matches the column structure, populating cells with content derived from the knowledge base and generation context for that section. The number of generated data rows SHALL be between 1 and 50 per table. Empty tables in the template SHALL be preserved as-is if no content is applicable.
5. THE Document_Generator SHALL generate a Table of Contents placeholder at the position where one exists in the Template_Document, using the standard Word TOC field code that updates when the document is opened in Microsoft Word or LibreOffice.
6. THE Document_Generator SHALL ensure all generated text uses UTF-8 encoding and that special characters (em-dashes, bullet symbols, non-ASCII regulatory symbols) render without corruption or character substitution when the output .docx is opened in Microsoft Word or LibreOffice.
7. IF the Template_Document uses custom styles not available in the default python-docx style set, THEN THE Document_Generator SHALL copy those style definitions from the template into the output document so that paragraphs using those styles render with the same font family, size, color, and spacing as in the Template_Document.
8. THE Document_Generator SHALL preserve images, logos, and embedded graphic objects from the Template_Document in their original positions and dimensions in the output .docx. Generated content SHALL be inserted around preserved images without displacing them from their anchored locations.
9. WHEN DOCX assembly is complete, THE Document_Generator SHALL validate the output file by verifying it conforms to the Open Packaging Conventions (valid ZIP archive with correct content types). IF validation fails, THEN THE Document_Generator SHALL mark the generation job as failed with a reason indicating the output file was malformed and SHALL NOT store the invalid file in MinIO.
10. THE Document_Generator SHALL preserve section breaks and page breaks from the Template_Document in the output .docx, maintaining the template's page structure between sections.

### Requirement 5: Generation Provenance and Audit Trail

**User Story:** As a quality auditor, I want a complete audit trail for every AI-generated document showing which template was used, what sources were consulted, and what parameters were applied, so that I can verify the generation process meets GxP compliance requirements.

#### Acceptance Criteria

1. THE Document_Generator SHALL create an immutable Generation_Provenance record for each generation job containing: generation_id (UUID), template_id, template_document_uuid, source_document_uuids (all documents retrieved from knowledge base), reference_document_ids (explicitly provided by user), agent_archetype_used ("Technical Writer"), generation_parameters (temperature, max_tokens, model_name), requesting_user_id, company_id, generation_timestamp, total_inference_duration_ms, and total_token_count.
2. THE Document_Generator SHALL record per-section provenance: for each Content_Section generated, the provenance SHALL include section_heading, knowledge_base_query_used, source_chunks_retrieved (document_uuid + chunk excerpt truncated to the first 200 characters for each), token_count_for_section, and inference_duration_ms_for_section.
3. THE Document_Generator SHALL expose a GET /api/documents/{document_id}/provenance endpoint that returns the full Generation_Provenance for a generated document, including per-section source attribution. This endpoint SHALL return HTTP 404 if the document was not AI-generated or if the document does not belong to the company identified by the X-Company-Id header.
4. THE Document_Generator SHALL persist Generation_Provenance records in the database as immutable rows (no UPDATE or DELETE operations permitted on provenance records). Provenance records SHALL be retained indefinitely regardless of whether the generated document is later deleted or superseded.
5. THE Document_Generator SHALL include a "Sources" appendix section at the end of every generated .docx document listing: each source document's title, document_uuid, version, and the section headings from which content was synthesized. This appendix SHALL be clearly labeled as "AI Generation Sources — For Audit Purposes".
6. THE Document_Generator SHALL scope all provenance queries to the company identified by the X-Company-Id header.
7. IF a generated document is regenerated (new generation from the same template with updated instructions), THEN THE Document_Generator SHALL create a new Generation_Provenance record linked to the new DocumentVersion, preserving the original provenance record for the previous version unchanged. The new provenance record SHALL include a previous_generation_id field referencing the generation_id of the immediately preceding provenance record for the same document, enabling version-to-version traceability.
8. IF the Generation_Provenance record cannot be persisted during a generation job (database write failure), THEN THE Document_Generator SHALL fail the entire generation job and NOT store the generated document, ensuring no AI-generated content exists without a corresponding audit trail.

### Requirement 6: Generated Document Review Workflow

**User Story:** As a document coordinator, I want generated documents to enter a review workflow before they become active in the system, so that no AI-generated content is used without human verification and approval.

#### Acceptance Criteria

1. THE Document_Generator SHALL create all generated documents with current_status "Draft" and an associated ContentStatus of "pending_review", requiring explicit human approval before the document can transition to "Review" or "Approved" status.
2. THE Document_Generator SHALL expose a POST /api/documents/{document_id}/review endpoint that accepts {action ("approve" or "reject"), reviewer_comments (optional string, maximum 2000 characters)} and transitions the document's ContentStatus accordingly. This endpoint SHALL require the X-Change-Reason header. On success, the endpoint SHALL return HTTP 200 with the updated document_id, current_status, and content_status.
3. WHEN a generated document is approved, THE Document_Generator SHALL transition the document's current_status from "Draft" to "Review" (entering the standard BPMN workflow), making it available for the normal document lifecycle process (3.2).
4. WHEN a generated document is rejected, THE Document_Generator SHALL mark the ContentStatus as "rejected" and retain the document in "Draft" status. The rejection reason SHALL be recorded in the audit trail. The document SHALL remain editable via the standard document update endpoint and eligible for a new generation job against the same template.
5. THE Document_Generator SHALL expose a GET /api/documents/generated endpoint that returns all AI-generated documents for the current company, filterable by content_status (pending_review, approved, rejected), document_type, and generation_date_range (ISO 8601 date strings for start_date and end_date query parameters), with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters.
6. THE Document_Generator SHALL prevent generated documents with ContentStatus "pending_review" or "rejected" from appearing in standard document search results (4.1) or being referenced by other generation jobs, ensuring only approved generated content enters the active document ecosystem.
7. THE Document_Generator SHALL scope all review operations to the company identified by the X-Company-Id header.
8. IF the review endpoint is called on a document that is not AI-generated (has no associated Generation_Provenance record), THEN THE Document_Generator SHALL reject the request with HTTP 422 and an error message indicating only AI-generated documents can be reviewed through this endpoint.
9. IF the review endpoint is called on a document whose ContentStatus is not "pending_review" (already approved or rejected), THEN THE Document_Generator SHALL reject the request with HTTP 409 and an error message indicating the document has already been reviewed, including the current content_status in the response.
10. IF the reviewer_comments field exceeds 2000 characters, THEN THE Document_Generator SHALL reject the request with HTTP 422 and an error message indicating the maximum comment length has been exceeded.

### Requirement 7: Generation Job Management and Status Tracking

**User Story:** As a user who initiated a document generation, I want to track the progress of my generation job and retrieve the result when complete, so that I know when my document is ready and can handle any failures.

#### Acceptance Criteria

1. THE Document_Generator SHALL track all generation jobs via the existing JobTracker service, creating a job with operation "template_document_generation" and estimated_duration_seconds based on template section count (30 seconds per section as baseline estimate).
2. THE Document_Generator SHALL update job progress as generation proceeds: 10% after template analysis loading, 20% after knowledge base retrieval, 20-90% proportionally as each section is generated (evenly distributed across sections), 95% after DOCX assembly, and 100% after MinIO storage and database record creation.
3. THE Document_Generator SHALL expose a GET /api/documents/generate-from-template/{job_id}/status endpoint that returns: job_id, status (processing, completed, failed), progress_percent, current_section (name of section currently being generated, null if not actively generating a section), sections_completed, sections_total, estimated_time_remaining_seconds (calculated as (100 - progress_percent) / 100 × estimated_duration_seconds), and error_message (null unless status is failed).
4. WHEN a generation job completes successfully, THE Document_Generator SHALL include in the job result: generated_document_id, generated_document_uuid, storage_key, file_size_bytes, sections_generated, unverified_references_count, and generation_duration_ms.
5. IF a generation job fails, THEN THE Document_Generator SHALL record the failure reason, the last successfully generated section name, and the progress_percent at the time of failure. Partial results (sections generated before failure) SHALL NOT be stored as a document — generation is all-or-nothing except for individual section placeholder fallbacks (Requirement 2, criterion 9).
6. THE Document_Generator SHALL prevent concurrent generation jobs for the same template_id + title combination within the same company, returning HTTP 409 with the existing job_id if a duplicate generation request is detected while a job with status "processing" already exists for that combination.
7. THE Document_Generator SHALL enforce a maximum generation timeout of 600 seconds (10 minutes) per job. IF the timeout is exceeded, THEN THE Document_Generator SHALL mark the job as failed with reason "Generation timeout exceeded" and clean up partial state by deleting any in-progress MinIO objects created during the job and removing the GenerationJobMetadata record's result references.
8. THE Document_Generator SHALL scope all job status queries to the company identified by the X-Company-Id header.
9. IF the job_id provided to the status endpoint does not exist or does not belong to the requesting company, THEN THE Document_Generator SHALL return HTTP 404 with an error message indicating the job was not found.

### Requirement 8: Database Models for Template-Based Generation

**User Story:** As a backend developer, I want well-defined database models for template registrations, generation provenance, cross-reference maps, and generation job metadata, so that all template-based generation data is persisted with full audit trail support.

#### Acceptance Criteria

1. THE DocumentTemplate model SHALL use table name "document_templates" and include: id (Integer, primary key), document_id (Integer, FK to documents, NOT NULL), document_version_id (Integer, FK to document_versions, NOT NULL), company_id (Integer, FK to companies, NOT NULL, indexed), template_name (String, max 500, NOT NULL), document_type_target (String, max 100, NOT NULL, e.g., "URS", "MVP", "SOP"), template_analysis (JSONB containing the full Template_Analysis structure, NOT NULL), status (String, max 20, NOT NULL, default "active", constrained to values: "active", "archived"), registered_by (Integer, FK to users, NOT NULL), registered_at (DateTime with timezone, server default now()), created_at (DateTime with timezone, server default now()), updated_at (DateTime with timezone, server default now(), onupdate now()). THE model SHALL enforce a unique constraint on (document_version_id, company_id) to prevent duplicate registrations.
2. THE GenerationProvenance model SHALL use table name "generation_provenance" and include: id (Integer, primary key), generation_id (UUID, unique, indexed, NOT NULL), document_id (Integer, FK to documents, nullable — set after document creation), document_version_id (Integer, FK to document_versions, nullable), template_id (Integer, FK to document_templates, NOT NULL), company_id (Integer, FK to companies, NOT NULL, indexed), requesting_user_id (Integer, FK to users, NOT NULL), agent_archetype (String, max 100, NOT NULL), generation_parameters (JSONB containing temperature, max_tokens, model_name, NOT NULL), source_document_uuids (JSON array, NOT NULL, default empty array), reference_document_ids (JSON array, NOT NULL, default empty array), section_provenance (JSONB array of per-section provenance records, NOT NULL), total_inference_duration_ms (Integer, NOT NULL, minimum 0), total_token_count (Integer, NOT NULL, minimum 0), unverified_references (JSON array, NOT NULL, default empty array), generation_timestamp (DateTime with timezone, NOT NULL), created_at (DateTime with timezone, server default now()). THE model SHALL NOT include AuditMixin and SHALL enforce immutability by omitting updated_at and by enforcing append-only semantics at the application layer (no UPDATE or DELETE operations permitted).
3. THE CrossReferenceEntry model SHALL use table name "cross_reference_entries" and include: id (Integer, primary key), generation_provenance_id (Integer, FK to generation_provenance, NOT NULL), source_document_id (Integer, FK to documents, NOT NULL), reference_type (String, max 50, NOT NULL, constrained to values: "requirement", "section", "test_case"), reference_identifier (String, max 200, NOT NULL), reference_text (Text, max 5000 characters, the referenced content excerpt), location_in_output (JSONB containing section_number and paragraph_index, NOT NULL), company_id (Integer, FK to companies, NOT NULL, indexed), created_at (DateTime with timezone, server default now()). THE model SHALL enforce a composite index on (generation_provenance_id, reference_type) for efficient querying. THE model SHALL NOT include AuditMixin (records are append-only, following the same immutability pattern as GenerationProvenance).
4. THE GenerationJobMetadata model SHALL use table name "generation_job_metadata" and include: id (Integer, primary key), job_id (String, UUID format, unique, indexed, NOT NULL), template_id (Integer, FK to document_templates, NOT NULL), company_id (Integer, FK to companies, NOT NULL, indexed), requesting_user_id (Integer, FK to users, NOT NULL), title (String, max 500, NOT NULL), generation_instructions (Text, NOT NULL), reference_document_ids (JSON array, NOT NULL, default empty array), output_folder_path (String, max 1000, NOT NULL), status (String, max 20, NOT NULL, default "processing", constrained to values: "processing", "completed", "failed"), progress_percent (Integer, NOT NULL, default 0, check constraint 0 <= progress_percent <= 100), current_section (String, nullable, max 500), sections_completed (Integer, NOT NULL, default 0), sections_total (Integer, NOT NULL, minimum 1), error_message (Text, nullable), result_document_id (Integer, FK to documents, nullable), result_storage_key (String, max 500, nullable), file_size_bytes (Integer, nullable, minimum 0), generation_duration_ms (Integer, nullable, minimum 0), started_at (DateTime with timezone, NOT NULL, server default now()), completed_at (DateTime with timezone, nullable), created_at (DateTime with timezone, server default now()), updated_at (DateTime with timezone, server default now(), onupdate now()). THE model SHALL enforce a check constraint that sections_completed <= sections_total.
5. THE DocumentTemplate and GenerationJobMetadata models SHALL include AuditMixin for automatic versioning via SQLAlchemy-Continuum. THE GenerationProvenance and CrossReferenceEntry models SHALL NOT include AuditMixin because they are append-only immutable records. ALL four models SHALL include company_id (Integer, FK to companies, NOT NULL, indexed) for multi-tenancy scoping.
6. THE GenerationProvenance model SHALL define a one-to-many relationship to CrossReferenceEntry via the generation_provenance_id foreign key, with cascade "all, delete-orphan" disabled (cross-reference entries are never cascade-deleted). THE relationship SHALL support eager or lazy loading for efficient retrieval of all cross-references for a given generation event.
7. WHEN a DocumentTemplate record's status is changed to "archived", THE system SHALL retain all associated GenerationProvenance and GenerationJobMetadata records unchanged, ensuring historical audit trail integrity is preserved.

### Requirement 9: Knowledge Base Integration for Content Synthesis

**User Story:** As the document generation system, I want to retrieve and synthesize relevant content from the company's knowledge base for each section of the template, so that generated documents contain accurate, company-specific regulatory content rather than generic text.

#### Acceptance Criteria

1. WHEN generating content for a template section, THE Document_Generator SHALL query the KnowledgeService with a search query constructed from: the section heading, the generation_instructions, and the document_type_target, retrieving the top 10 most relevant chunks (with relevance_score >= 0.3) scoped to the requesting company. IF fewer than 10 chunks meet the relevance threshold, THE Document_Generator SHALL use only those chunks that qualify.
2. THE Document_Generator SHALL provide retrieved knowledge base chunks as context to the Technical_Writer agent alongside the section-specific generation prompt, ordering chunks by descending relevance_score, instructing the agent to synthesize the information into prose that addresses the section heading's topic within the document structure.
3. WHEN reference_document_ids are provided, THE Document_Generator SHALL retrieve full text content of those documents (via KnowledgeService text extraction from MinIO-stored files), extract excerpts of up to 2000 characters per document relevant to the current section heading, and include those excerpts before general knowledge base chunks in the generation context so that the Technical_Writer agent treats them as primary source material.
4. IF the combined generation context (template structure + knowledge base excerpts + preceding sections) exceeds 6000 tokens, THEN THE Document_Generator SHALL summarize preceding sections into a condensed context of no more than 1000 tokens and select only the top 5 most relevant knowledge base chunks for that section.
5. THE Document_Generator SHALL record which knowledge base chunks were used for each section in the per-section provenance, including: chunk_document_uuid, chunk_text (first 200 characters), and relevance_score.
6. IF the KnowledgeService returns no results for a section query (zero chunks meeting the relevance_score >= 0.3 threshold), THEN THE Document_Generator SHALL generate content based solely on the section heading, generation_instructions, and preceding section context, recording in the section provenance that no knowledge base sources were available for that section.
7. THE Document_Generator SHALL scope all knowledge base queries to the company identified by the X-Company-Id header, ensuring no cross-tenant content leakage.
8. IF the KnowledgeService is unavailable or returns an error during a section query, THEN THE Document_Generator SHALL retry the query once after a 3-second delay. IF the retry also fails, THEN THE Document_Generator SHALL proceed with generation using only the section heading, generation_instructions, and preceding section context, and SHALL record the failure reason in the section provenance.

### Requirement 10: Template Placeholder Processing

**User Story:** As a document administrator, I want to define placeholder markers in my template documents that instruct the AI what type of content to generate in each location, so that I can control the generation output with precision beyond just section headings.

#### Acceptance Criteria

1. THE Document_Generator SHALL recognize and process the following standard Placeholder_Markers in Template_Documents: `{{SECTION_CONTENT}}` (generate section body text), `{{REQUIREMENT_LIST}}` (generate a numbered list of requirements), `{{CROSS_REF:document_type}}` (generate cross-references to documents of the specified type), `{{TABLE:description}}` (generate a table with content matching the description), `{{PROCEDURE_STEPS}}` (generate numbered procedural steps), and `{{RISK_ASSESSMENT}}` (generate a risk assessment table with severity, likelihood, and mitigation columns). A single Template_Document SHALL contain a maximum of 50 Placeholder_Markers.
2. WHEN a `{{REQUIREMENT_LIST}}` placeholder is encountered, THE Document_Generator SHALL extract requirements from reference documents and format them as a numbered list with: requirement ID, requirement text (truncated to 500 characters per item if longer), and source document reference, containing a maximum of 200 items.
3. WHEN a `{{TABLE:description}}` placeholder is encountered, THE Document_Generator SHALL generate a table where the description parameter (maximum 200 characters) guides the column structure and content. The generated table SHALL have a header row and between 2 and 50 data rows, with column count determined by the description context (maximum 8 columns).
4. WHEN a `{{PROCEDURE_STEPS}}` placeholder is encountered, THE Document_Generator SHALL generate numbered procedural steps derived from relevant SOPs and Work Instructions in the knowledge base (queried via KnowledgeService scoped to the requesting company), with each step containing: step number, action description, responsible role (if determinable from source), and acceptance criteria (if applicable). The generated output SHALL contain a maximum of 50 steps.
5. WHEN a `{{RISK_ASSESSMENT}}` placeholder is encountered, THE Document_Generator SHALL generate a risk assessment table with columns: Risk ID, Risk Description, Severity (1-5), Likelihood (1-5), Risk Priority Number (Severity × Likelihood), and Mitigation Strategy. Content SHALL be derived from the generation_instructions, reference documents, and knowledge base results for the current section. The generated table SHALL contain between 2 and 25 risk rows.
6. IF an unrecognized Placeholder_Marker pattern is encountered (matches `{{...}}` syntax but is not a standard marker), THEN THE Document_Generator SHALL treat it as a `{{SECTION_CONTENT}}` placeholder and generate general section content, recording a warning in the generation metadata that an unknown placeholder was encountered.
7. THE Document_Generator SHALL remove all Placeholder_Marker tokens from the final output .docx, replacing them entirely with the generated content. No raw placeholder text SHALL appear in the output document.
8. IF a `{{REQUIREMENT_LIST}}` placeholder is encountered and no requirements can be extracted from the reference documents or knowledge base (zero extractable requirement IDs), THEN THE Document_Generator SHALL insert a notice stating that no requirements were found for the specified context and record a warning in the generation metadata.
9. IF a `{{PROCEDURE_STEPS}}` placeholder is encountered and no relevant SOPs or Work Instructions are found in the knowledge base, THEN THE Document_Generator SHALL generate generic procedural steps based solely on the section heading and generation_instructions, and record in the section provenance that no SOP sources were available.
10. WHEN a `{{SECTION_CONTENT}}` placeholder is encountered, THE Document_Generator SHALL generate prose body text for the enclosing section using the section heading, generation_instructions, and relevant knowledge base content as context, producing between 1 and 10 paragraphs of content appropriate to the section topic.
