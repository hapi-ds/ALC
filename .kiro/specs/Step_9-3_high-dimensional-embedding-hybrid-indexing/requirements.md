# Requirements Document

## Introduction

This document specifies the requirements for Phase 9.3 — High-Dimensional Embedding Generation & Hybrid Indexing — of AlcoaBase. This feature builds on the Automated Ingestion Pipeline (Phase 9.2) by routing ingested abstracts and full-text `Structured_Content` through the vLLM Service Layer (Phase 4.3) to generate high-dimensional semantic embeddings. These embeddings are indexed alongside classic BM25 keyword indices in OpenSearch, enabling unified hybrid search across both public literature and private company documents. Literature embeddings are strictly partitioned within the multi-tenancy framework (Phase 1.1) using isolated corporate vector spaces. Metadata tags are appended automatically to distinguish public literature from private proprietary knowledge while allowing unified hybrid querying within a single company's scope. The system reuses the existing `InferenceClient`, `ModelManager`, `KnowledgeService` chunking infrastructure, and the `Ingestion_Pipeline_Service` state machine from prior phases.

## Glossary

- **Embedding_Service**: The backend service responsible for generating high-dimensional semantic embedding vectors from text content by routing requests through the vLLM Service Layer (Phase 4.3).
- **Literature_Index_Manager**: The component responsible for creating, maintaining, and querying OpenSearch indices that store literature embeddings and BM25 keyword fields, partitioned per company.
- **Corporate_Vector_Space**: An isolated OpenSearch index (or index partition via routing) scoped to a single company, ensuring that one company's literature embeddings are never accessible to another company during search operations.
- **Hybrid_Query_Engine**: The component that executes combined BM25 keyword + kNN semantic similarity searches against a company's vector space, merging scores and returning ranked results.
- **Embedding_Vector**: A high-dimensional floating-point array (default 1024 dimensions) representing the semantic meaning of a text chunk, generated by the vLLM embedding model.
- **Content_Chunk**: A segment of text (approximately 512 tokens with 50-token overlap) extracted from an abstract or Structured_Content body, suitable for embedding generation.
- **Partition_Tag**: A metadata label attached to each indexed document chunk distinguishing its origin as either `public_literature` (from external sources via Phase 9.1/9.2) or `private_knowledge` (from internal company document uploads).
- **Index_Template**: An OpenSearch index template defining the mapping for literature indices, including kNN vector fields, BM25 text fields, metadata fields, and partition tags.
- **Chunking_Pipeline**: The text segmentation component that splits abstracts and full-text Structured_Content into Content_Chunks suitable for embedding, reusing the existing KnowledgeService chunking logic.
- **Embedding_Task**: A Celery task responsible for generating embeddings for one or more Content_Chunks and indexing them into the appropriate Corporate_Vector_Space.
- **Ingestion_Record**: The per-company, per-paper lifecycle record from Phase 9.2, extended here with an `indexed` terminal state reached after successful embedding and indexing.
- **Structured_Content**: The normalized internal format from Phase 9.2's Sanitization_Pipeline containing extracted sections (title, abstract, body, references).
- **Company**: The multi-tenant entity (from Phase 1.1) to which all indices, embeddings, and search operations are scoped.
- **InferenceClient**: The existing httpx-based client (Phase 4.3) for communicating with vLLM instances, supporting the `/v1/embeddings` endpoint.
- **ModelManager**: The existing service (Phase 4.3) managing model lifecycle and routing embedding requests to the dedicated vLLM embedding instance.

## Requirements

### Requirement 1: Embedding Generation from Ingested Content

**User Story:** As a quality manager, I want ingested literature automatically converted into semantic embeddings, so that the content becomes searchable via semantic similarity alongside keyword matching.

#### Acceptance Criteria

1. WHEN an Ingestion_Record transitions to the `sanitized` state with a non-empty Structured_Content, THE Embedding_Service SHALL dispatch an Embedding_Task to generate embeddings for all Content_Chunks derived from the Structured_Content, scoped to the Ingestion_Record's company_id for tenant isolation.
2. WHEN an Ingestion_Record has a non-empty abstract and is in the `abstract_indexed` state, THE Embedding_Service SHALL generate embeddings for the abstract text and index them into the company-scoped OpenSearch embedding index without waiting for full-text retrieval to complete.
3. THE Embedding_Service SHALL split input text into Content_Chunks using the existing KnowledgeService `chunk_text` method with a chunk_size of 512 tokens and a 50-token overlap between consecutive chunks, where tokens are approximated by whitespace splitting.
4. WHEN generating embeddings, THE Embedding_Service SHALL route requests to the dedicated vLLM embedding instance via the existing InferenceClient `create_embeddings` method, using the model configured in `MODEL_EMBEDDING_NAME`, in batches of up to 32 chunks per request.
5. THE Embedding_Service SHALL generate embedding vectors with the dimension configured in `MODEL_EMBEDDING_DIMENSION` (default: 1024).
6. WHEN embedding generation completes for all Content_Chunks of an Ingestion_Record, THE Embedding_Service SHALL transition the Ingestion_Record state from `sanitized` to `indexed` and record the transition in both the state_history JSONB array and an IngestionAuditLog entry with event_type `state_transition`.
7. IF the vLLM embedding instance is unavailable or returns an error, THEN THE Embedding_Service SHALL retry embedding generation up to 3 times with exponential backoff (30 seconds, 2 minutes, 10 minutes) before transitioning the Ingestion_Record to the `failed` state with error_type `embedding_generation_error`.
8. THE Embedding_Service SHALL process embedding generation as a Celery task on the `literature_ingestion` queue with priority 5, triggered automatically upon state transition to `sanitized`.

### Requirement 2: Content Chunking Strategy

**User Story:** As a developer building downstream search features, I want literature content chunked consistently with internal documents, so that search relevance is comparable across both content sources.

#### Acceptance Criteria

1. THE Chunking_Pipeline SHALL segment abstract text into Content_Chunks using a maximum chunk size of 512 tokens and an overlap of 50 tokens between consecutive chunks, where tokens are approximated by whitespace-delimited words consistent with the existing `KnowledgeService.chunk_text()` method.
2. THE Chunking_Pipeline SHALL segment Structured_Content body sections respecting section boundaries, preferring to split at paragraph breaks or section heading boundaries rather than mid-sentence, where a section boundary is defined as a heading element or a double-newline-separated block.
3. IF a single section or paragraph exceeds 512 tokens, THEN THE Chunking_Pipeline SHALL split it at the nearest sentence boundary (period, question mark, or exclamation mark followed by whitespace) that keeps the chunk within the 512-token limit.
4. IF no sentence boundary exists within the 512-token limit for a given text segment, THEN THE Chunking_Pipeline SHALL split at the 512-token word boundary.
5. THE Chunking_Pipeline SHALL prepend the document title and section heading (if applicable) to each Content_Chunk as context, consuming no more than 64 tokens for the prepended context; if the combined title and heading exceeds 64 tokens, the prepended text SHALL be truncated to 64 tokens at the nearest word boundary.
6. THE Chunking_Pipeline SHALL produce at least one Content_Chunk for any input text that contains at least one non-whitespace character; input consisting solely of whitespace characters SHALL produce zero chunks.
7. THE Chunking_Pipeline SHALL produce chunks where the concatenation of unique (non-overlapping) text portions reconstructs the entire original input text without omission or reordering (completeness property).
8. THE Chunking_Pipeline SHALL reuse the existing `KnowledgeService.chunk_text()` implementation (whitespace-split token approximation, 512 chunk size, 50 overlap) to maintain consistency with internal document indexing.

### Requirement 3: OpenSearch Index Structure for Literature

**User Story:** As a system administrator, I want literature embeddings stored in well-structured OpenSearch indices, so that hybrid search performs efficiently and indices can be managed per company.

#### Acceptance Criteria

1. THE Literature_Index_Manager SHALL create one OpenSearch index per company using the naming convention `literature-embeddings-{company_id}`, ensuring complete data isolation between tenants.
2. THE Literature_Index_Manager SHALL define the index mapping with the following fields: `embedding_vector` (knn_vector, dimension from `MODEL_EMBEDDING_DIMENSION`), `chunk_text` (text, analyzed for BM25), `title` (text, analyzed for BM25), `abstract_snippet` (text), `authors` (keyword array), `doi` (keyword), `publication_date` (date), `source_id` (keyword), `external_id` (keyword), `ingestion_record_id` (integer), `company_id` (integer), `partition_tag` (keyword, values: `public_literature` or `private_knowledge`), `section_heading` (keyword), `chunk_index` (integer), `created_at` (date).
3. THE Literature_Index_Manager SHALL configure the kNN vector field to use the HNSW algorithm with `ef_construction` of 256, `m` of 16, and `space_type` of `cosinesimil` for cosine similarity scoring.
4. WHEN the Literature_Index_Manager receives a request to index literature documents for a company whose index `literature-embeddings-{company_id}` does not yet exist, THE Literature_Index_Manager SHALL create the company's index using the Index_Template before proceeding with the indexing operation.
5. THE Literature_Index_Manager SHALL apply an OpenSearch index template named `literature-embeddings-template` that automatically configures new indices matching the `literature-embeddings-*` pattern.
6. IF the OpenSearch cluster is unavailable during index creation, THEN THE Literature_Index_Manager SHALL retry creation up to 3 times with 10-second intervals, and if all retries are exhausted, SHALL raise an error indicating the cluster is unreachable and log the failure details including the company_id and attempted index name.
7. THE Literature_Index_Manager SHALL configure index settings with `number_of_shards: 1` and `number_of_replicas: 1` as defaults, configurable via environment variables `ALC_LITERATURE_INDEX_SHARDS` and `ALC_LITERATURE_INDEX_REPLICAS`.
8. IF the index `literature-embeddings-{company_id}` already exists when index creation is triggered, THEN THE Literature_Index_Manager SHALL skip creation and proceed without error.

### Requirement 4: Isolated Corporate Vector Spaces

**User Story:** As a system administrator, I want each company's literature embeddings stored in completely isolated vector spaces, so that multi-tenant data separation is enforced at the infrastructure level and no cross-tenant data leakage is possible.

#### Acceptance Criteria

1. THE Literature_Index_Manager SHALL enforce that all indexing operations include the `company_id` field matching the authenticated company context from the `X-Company-Id` header; before writing any document to OpenSearch, the system SHALL validate that the document's `company_id` equals the `company_id` resolved from the request's `X-Company-Id` header.
2. THE Literature_Index_Manager SHALL enforce that all search operations query only the index belonging to the requesting company (`literature-embeddings-{company_id}`) by constructing the target index name exclusively from the authenticated `X-Company-Id` header value.
3. IF a search or indexing request contains a `company_id` in the payload that does not match the authenticated company context from the `X-Company-Id` header, THEN THE Literature_Index_Manager SHALL reject the request with HTTP 403, return an error response indicating a tenant isolation violation, and log a security violation entry to the audit trail including the authenticated company_id, the mismatched target company_id, the requesting user_id, the operation type, and a timestamp.
4. WHEN an Ingestion_Record is indexed, THE Literature_Index_Manager SHALL store the embedding in the index corresponding to the Ingestion_Record's `company_id` and SHALL NOT write to any other company's index.
5. THE Literature_Index_Manager SHALL validate company isolation by including a `company_id` filter in every OpenSearch query as a mandatory boolean filter clause, providing defense-in-depth beyond index-level separation; queries constructed without this filter SHALL NOT be executed.
6. WHEN a company is deleted or deactivated, THE Literature_Index_Manager SHALL delete the entire company's OpenSearch index (`literature-embeddings-{company_id}`), removing all associated embeddings and keyword data within 60 seconds of the deletion trigger.
7. IF the `X-Company-Id` header is missing or empty on any indexing or search request, THEN THE Literature_Index_Manager SHALL reject the request with HTTP 400 and return an error response indicating that tenant context is required.
8. IF index deletion fails during company removal (due to OpenSearch unavailability or partial failure), THEN THE Literature_Index_Manager SHALL retry deletion up to 3 times with 30-second intervals before logging a critical error to the audit trail and alerting administrators that manual cleanup is required for the orphaned index.

### Requirement 5: Partition Tagging (Public Literature vs Private Knowledge)

**User Story:** As a quality manager, I want to distinguish between public literature and private company documents in search results, so that I can filter results by origin and understand the provenance of each result.

#### Acceptance Criteria

1. WHEN indexing content from the literature ingestion pipeline (Phase 9.2), THE Literature_Index_Manager SHALL assign `partition_tag: public_literature` to all Content_Chunks derived from that Ingestion_Record.
2. WHEN indexing content from internal company document uploads (existing KnowledgeService pipeline), THE Literature_Index_Manager SHALL assign `partition_tag: private_knowledge` to all Content_Chunks derived from that document.
3. THE Hybrid_Query_Engine SHALL accept a `partition_filter` parameter with allowed values `public_literature`, `private_knowledge`, or `all` (default: `all`), and SHALL return only Content_Chunks matching the specified partition value.
4. IF no `partition_filter` parameter is specified in a search query, THEN THE Hybrid_Query_Engine SHALL search across both `public_literature` and `private_knowledge` partitions within the requesting company's vector space.
5. THE Hybrid_Query_Engine SHALL include the `partition_tag` value in every result item within search responses, enabling the UI to display origin badges (e.g., "Literature" vs "Internal").
6. WHEN a re-tagging request is submitted for an Ingestion_Record specifying target tag `private_knowledge`, THE Literature_Index_Manager SHALL atomically update the `partition_tag` from `public_literature` to `private_knowledge` for all Content_Chunks belonging to that Ingestion_Record, such that either all chunks are updated or none are.
7. IF a re-tagging operation fails after partial execution, THEN THE Literature_Index_Manager SHALL roll back all affected Content_Chunks to their original `partition_tag` value and return an error indicating the failure reason.
8. WHEN a re-tagging operation completes successfully, THE Literature_Index_Manager SHALL record an audit log entry containing the Ingestion_Record identifier, the previous partition_tag value, the new partition_tag value, the requesting user identifier, and the timestamp.

### Requirement 6: Hybrid Search Execution (BM25 + Semantic)

**User Story:** As a quality manager, I want to search across ingested literature using both keyword matching and semantic similarity, so that I can find relevant papers whether I know the exact terminology or only the general concept.

#### Acceptance Criteria

1. WHEN a user submits a search query of 1 to 1000 characters, THE Hybrid_Query_Engine SHALL execute both a BM25 keyword search against the `chunk_text` and `title` fields and a kNN semantic search against the `embedding_vector` field, combining results using reciprocal rank fusion (RRF), and return results scoped to the user's tenant (company_id).
2. THE Hybrid_Query_Engine SHALL generate an embedding vector for the user's query text using the same vLLM embedding model and InferenceClient used for indexing, ensuring vector space consistency.
3. THE Hybrid_Query_Engine SHALL apply reciprocal rank fusion with a configurable `k` parameter (integer, minimum 1, maximum 200, default: 60) to merge BM25 and kNN result lists into a single ranked output.
4. THE Hybrid_Query_Engine SHALL support configurable weighting between BM25 and semantic scores via a `semantic_weight` parameter (float 0.0–1.0, default: 0.5), where 0.0 is pure keyword and 1.0 is pure semantic.
5. THE Hybrid_Query_Engine SHALL return results paginated with configurable page size (minimum 1, default 20, maximum 100) and a page offset (minimum 0, default 0), and include an estimated total result count in the response.
6. THE Hybrid_Query_Engine SHALL return each result with: chunk_text, title, authors, doi, publication_date, source_id, relevance_score (float 0.0–1.0), partition_tag, section_heading, and ingestion_record_id.
7. THE Hybrid_Query_Engine SHALL complete search requests within 5 seconds (measured from request receipt to response dispatch) for indices containing up to 1 million chunks.
8. IF the vLLM embedding instance is unavailable for query embedding generation, THEN THE Hybrid_Query_Engine SHALL fall back to BM25-only search, return results ranked by BM25 score alone, and include a `degraded_mode: true` flag in the response metadata.
9. IF the user submits an empty or whitespace-only search query, THEN THE Hybrid_Query_Engine SHALL reject the request and return an error response indicating that a non-empty query is required.
10. IF the OpenSearch cluster is unreachable or returns an error during query execution, THEN THE Hybrid_Query_Engine SHALL return an error response indicating search service unavailability without exposing internal infrastructure details.

### Requirement 7: Unified Search Across Literature and Internal Documents

**User Story:** As a quality manager, I want a single search interface that queries both ingested literature and internal company documents, so that I can discover all relevant content without switching between separate search systems.

#### Acceptance Criteria

1. THE Hybrid_Query_Engine SHALL support a unified search mode that queries both the literature index (`literature-embeddings-{company_id}`) and the existing internal document index within a single request, returning up to 100 results per page (default 20, minimum 1).
2. WHEN unified search mode is active, THE Hybrid_Query_Engine SHALL merge results from both indices using the same reciprocal rank fusion scoring (with the configured `k` parameter, default 60), presenting a single ranked list to the user.
3. THE Hybrid_Query_Engine SHALL include the `partition_tag` field (value `public_literature` or `private_knowledge`) in every unified search result so the UI can distinguish literature results from internal document results.
4. THE Hybrid_Query_Engine SHALL respect existing ABAC permissions for internal documents (filtering results to those the requesting user is permitted to access) while applying company-level isolation for literature results (querying only `literature-embeddings-{company_id}`).
5. WHEN a user has the `member` role or higher within the requesting company, THE Hybrid_Query_Engine SHALL grant access to all `public_literature` results for that company without additional per-document permission checks.
6. THE Hybrid_Query_Engine SHALL support query-time boosting: users can specify a `literature_boost` or `internal_boost` factor (float, range 0.1–10.0, default 1.0) to multiply the RRF score of results from the corresponding partition before final ranking.
7. IF one of the two indices is unreachable during a unified search request, THEN THE Hybrid_Query_Engine SHALL return results from the available index only and include a `partial_results: true` flag along with a `unavailable_index` field indicating which index could not be queried.
8. IF the requesting user does not have the `member` role or higher within the requesting company, THEN THE Hybrid_Query_Engine SHALL reject the unified search request and return an error indicating insufficient permissions.

### Requirement 8: Embedding Update and Re-indexing

**User Story:** As a system administrator, I want to re-generate embeddings when the embedding model changes, so that all literature content uses consistent vectors for accurate semantic search.

#### Acceptance Criteria

1. THE Embedding_Service SHALL provide a batch re-indexing operation that re-generates embeddings for all Ingestion_Records belonging to a specified company.
2. WHEN a batch re-indexing operation is initiated, THE Embedding_Service SHALL process records in configurable batch sizes (integer, default: 50, range: 10–200, read from `ALC_REINDEX_BATCH_SIZE` environment variable), dispatching each batch as a separate Celery task to avoid overwhelming the vLLM instance.
3. THE Embedding_Service SHALL persist re-indexing progress in the database (not solely in memory), tracking per company: job status (queued, in_progress, completed, failed, cancelled), current batch number, total batches, records processed, records failed, started_at timestamp, and updated_at timestamp, and SHALL expose this data via the re-indexing progress API endpoint.
4. WHEN re-indexing a record, THE Embedding_Service SHALL delete the existing indexed chunks from OpenSearch and insert newly generated chunks atomically per record, ensuring no stale vectors remain; IF deletion succeeds but insertion fails, THEN THE Embedding_Service SHALL NOT leave the record with zero indexed chunks and SHALL retry the full delete-and-insert sequence for that record up to 2 times before marking it as failed.
5. THE Embedding_Service SHALL support selective re-indexing by state: administrators can choose to re-index only records currently in the `indexed` state, or include `abstract_indexed` records.
6. IF re-indexing fails for a specific record, THEN THE Embedding_Service SHALL log the failure with ingestion_record_id and error details, skip the record, and continue processing remaining records in the batch without halting the entire re-indexing job.
7. THE Embedding_Service SHALL require the `system_admin` role to initiate, cancel, or query batch re-indexing operations.
8. IF a batch re-indexing operation is already in progress for a company, THEN THE Embedding_Service SHALL reject any new re-indexing request for the same company and return an error indicating that a re-indexing job is already active, including the existing job's task_id and progress.
9. IF a single Embedding_Task batch does not complete within 10 minutes, THEN THE Embedding_Service SHALL mark the timed-out batch as failed, record the timeout in progress tracking, and proceed to dispatch the next batch.
10. WHEN a system administrator submits a cancellation request for an active re-indexing job, THE Embedding_Service SHALL set the job status to `cancelled`, cease dispatching new batches, allow the currently executing batch to complete, and record the cancellation in the audit trail with the requesting user_id and timestamp.

### Requirement 9: Embedding Configuration

**User Story:** As a system administrator, I want to configure embedding generation parameters per company, so that different teams can tune chunk size, model selection, and indexing behavior for their use case.

#### Acceptance Criteria

1. THE Embedding_Service SHALL provide per-company embedding configuration with the following settings: `chunk_size_tokens` (integer, default: 512, range: 128–2048), `chunk_overlap_tokens` (integer, default: 50, range: 0–256), `auto_embed_on_ingest` (boolean, default: true), `embed_abstract_only` (boolean, default: false), `max_chunks_per_document` (integer, default: 500, range: 1–5000).
2. WHILE `auto_embed_on_ingest` is true for a company, WHEN an Ingestion_Record transitions to `sanitized` or when an abstract becomes available, THE Embedding_Service SHALL automatically generate and index embeddings using that company's configured `chunk_size_tokens` and `chunk_overlap_tokens` values within 60 seconds of the triggering state transition.
3. WHILE `auto_embed_on_ingest` is false for a company, THE Embedding_Service SHALL NOT automatically generate embeddings on ingestion state transitions, and SHALL generate embeddings only when explicitly triggered via the embedding generation API endpoint.
4. WHILE `embed_abstract_only` is true for a company, THE Embedding_Service SHALL generate embeddings only from the abstract text field and SHALL skip full-text body sections.
5. IF `embed_abstract_only` is true and the Ingestion_Record has a null or empty abstract, THEN THE Embedding_Service SHALL skip embedding generation for that record and SHALL log the skip event in the audit trail with the reason "abstract_unavailable".
6. IF the number of Content_Chunks produced from a single Ingestion_Record exceeds the company's configured `max_chunks_per_document` value, THEN THE Embedding_Service SHALL index only the first N chunks up to the configured maximum (prioritizing title, abstract, and leading body sections in document order) and SHALL record the truncation event in the audit trail including the total chunk count produced and the maximum applied.
7. WHEN an embedding configuration is created or updated, THE Embedding_Service SHALL record the change in the audit trail including the previous setting values, the new setting values, the acting user ID, a server timestamp, and the X-Change-Reason header value.
8. IF a user without the `document_admin` or `system_admin` role attempts to create or update an embedding configuration, THEN THE Embedding_Service SHALL reject the request with HTTP 403 and an error message indicating insufficient permissions.
9. IF a configuration create or update request contains values outside the defined ranges (chunk_size_tokens outside 128–2048, chunk_overlap_tokens outside 0–256, or max_chunks_per_document outside 1–5000), THEN THE Embedding_Service SHALL reject the request with HTTP 422 and an error message indicating which parameter violated its allowed range.

### Requirement 10: Search API Endpoints

**User Story:** As a developer building the literature search UI (Phase 9.6), I want RESTful API endpoints for executing hybrid searches against literature embeddings, so that the frontend can provide rich search experiences.

#### Acceptance Criteria

1. THE Hybrid_Query_Engine SHALL expose a search endpoint at `POST /api/literature/search/hybrid` accepting a JSON body with: `query` (string, 1–1000 characters, required), optional filters (`partition_tag`, `date_range` as start/end ISO-8601 dates, `source_id`, `authors` as string array, `publication_type`), pagination parameters (`page` integer minimum 1 default 1, `page_size` integer 1–100 default 20), and scoring parameters (`semantic_weight` float 0.0–1.0 default 0.5, `literature_boost` float 0.1–10.0 default 1.0, `internal_boost` float 0.1–10.0 default 1.0), returning HTTP 200 with results on success.
2. THE Hybrid_Query_Engine SHALL expose a unified search endpoint at `POST /api/literature/search/unified` that queries both literature and internal document indices, accepting the same parameters as the hybrid endpoint plus an `include_internal` boolean (default: true), returning HTTP 200 with results on success.
3. THE Hybrid_Query_Engine SHALL expose an index status endpoint at `GET /api/literature/index/status` returning the index health as a status value (one of `green`, `yellow`, `red` corresponding to OpenSearch cluster health for the company's index), document count, total chunks indexed, index size in bytes, and last indexing timestamp (ISO-8601) for the requesting company.
4. THE Embedding_Service SHALL expose a re-indexing endpoint at `POST /api/literature/index/reindex` accessible only to `system_admin` role, accepting optional filters (`state` to select records in `indexed` or `abstract_indexed` state, `ingestion_record_ids` as an array of specific record IDs), returning HTTP 202 with a `task_id` for tracking progress.
5. THE Embedding_Service SHALL expose a re-indexing progress endpoint at `GET /api/literature/index/reindex/{task_id}` returning: percentage progress (0–100), records processed count, records failed count, and estimated time remaining in seconds.
6. THE Embedding_Service SHALL expose an embedding configuration endpoint at `GET /api/literature/index/config` (returning the current configuration) and `PUT /api/literature/index/config` (updating the configuration), both requiring at least the `document_admin` role.
7. WHEN any mutation endpoint (POST, PUT, DELETE) is called, THE Hybrid_Query_Engine SHALL require the X-Change-Reason header and return HTTP 400 if it is missing or empty.
8. THE Hybrid_Query_Engine SHALL require at least the `member` role for search endpoints (`/search/hybrid`, `/search/unified`) and the index status endpoint (`/index/status`), `document_admin` role for the configuration endpoint (`/index/config`), and `system_admin` role for the re-indexing endpoints (`/index/reindex`, `/index/reindex/{task_id}`), returning HTTP 403 when the caller lacks the required role.
9. IF the `query` field is missing, empty, or exceeds 1000 characters in a search request, THEN THE Hybrid_Query_Engine SHALL return HTTP 422 with an error message indicating the query validation failure.
10. IF the OpenSearch index for the requesting company does not exist when a search endpoint is called, THEN THE Hybrid_Query_Engine SHALL return HTTP 200 with an empty results array and zero total count rather than an error.

### Requirement 11: Audit Trail for Embedding and Indexing Operations

**User Story:** As a quality manager, I want all embedding generation and indexing operations logged in the audit trail, so that I can demonstrate the provenance and integrity of search capabilities during regulatory audits.

#### Acceptance Criteria

1. WHEN embeddings are generated for an Ingestion_Record, THE Audit_Logger SHALL record: ingestion_record_id, company_id, user_id (or system identifier if automated), chunk_count, embedding_dimension, model_name, generation_duration_ms, triggering_event (auto or manual), and a UTC timestamp.
2. WHEN Content_Chunks are indexed into OpenSearch, THE Audit_Logger SHALL record: ingestion_record_id, company_id, user_id (or system identifier if automated), index_name, chunks_indexed, indexing_duration_ms, partition_tag, and a UTC timestamp.
3. WHEN a batch re-indexing operation is initiated, THE Audit_Logger SHALL record: company_id, initiating_user_id, total_records_targeted, reason (from X-Change-Reason), task_id, and a UTC timestamp.
4. IF embedding generation or indexing fails, THEN THE Audit_Logger SHALL record the failure with: ingestion_record_id, company_id, failed_operation, error_type, error_message (truncated to a maximum of 2000 characters), retry_attempt_number, and a UTC timestamp.
5. WHEN a search query is executed, THE Audit_Logger SHALL record: company_id, user_id, query_text_length (not the query text itself), search_mode (hybrid, keyword-only, semantic-only, unified), result_count, response_time_ms, partition_filter_applied, and a UTC timestamp.
6. THE Audit_Logger SHALL never log embedding vectors, full query text, or document content in audit records to minimize storage overhead and avoid sensitive data exposure.
7. THE Audit_Logger SHALL store all embedding and indexing audit records as append-only entries that cannot be modified or deleted through application-level operations, preserving ALCOA+ Original and Enduring principles.

### Requirement 12: Error Handling and Resilience

**User Story:** As a system administrator, I want the embedding and indexing pipeline to gracefully handle failures without losing data, so that temporary infrastructure issues do not corrupt the search index or lose ingested content.

#### Acceptance Criteria

1. IF the vLLM embedding instance is unavailable, THEN THE Embedding_Service SHALL retain Ingestion_Records in their current state (`sanitized` or `abstract_indexed`) and requeue Embedding_Tasks with exponential backoff (30 seconds, 2 minutes, 10 minutes) up to a maximum of 3 retry attempts before transitioning the Ingestion_Record to the `failed` state with error_type `embedding_generation_error`.
2. IF OpenSearch is unreachable during indexing, THEN THE Literature_Index_Manager SHALL retry the indexing operation 3 times with 10-second intervals before transitioning the Ingestion_Record to `failed` with error_type `indexing_unavailable`.
3. IF OpenSearch is unreachable during a search query, THEN THE Hybrid_Query_Engine SHALL return HTTP 503 with a message indicating that the search service is temporarily unavailable.
4. THE Embedding_Service SHALL implement idempotent indexing: re-indexing the same Ingestion_Record SHALL delete all existing chunks for that record (filtered by `ingestion_record_id`) before inserting newly generated chunks, ensuring no duplicate chunks exist in OpenSearch and the final chunk count and vector content match a fresh indexing of the same source text.
5. WHEN deleting indexed chunks (during re-indexing or record deletion), THE Literature_Index_Manager SHALL use the `ingestion_record_id` as the delete filter to ensure only the target record's chunks are removed.
6. IF an Embedding_Task encounters a partial failure (some chunks embedded successfully, others fail), THEN THE Embedding_Service SHALL roll back all indexed chunks for that record by deleting them from OpenSearch and retry the entire record as a new Embedding_Task, subject to the same maximum of 3 retry attempts defined in criterion 1.
7. THE Embedding_Service SHALL validate that embedding vectors have the expected dimension (as configured in `MODEL_EMBEDDING_DIMENSION`) before indexing; IF a vector has a dimension that does not equal the configured value, THEN THE Embedding_Service SHALL reject the entire batch of chunks for that record, transition the Ingestion_Record to `failed` with error_type `embedding_dimension_mismatch`, and log an error indicating the expected versus actual dimension.
8. IF the Embedding_Service exhausts all retry attempts for an Embedding_Task (due to vLLM unavailability, partial failure, or OpenSearch unavailability), THEN THE Embedding_Service SHALL transition the Ingestion_Record to `failed` with the corresponding error_type and preserve all source content (Structured_Content and original files) so that the record can be manually retried without data loss.

### Requirement 13: Environment and Deployment Configuration

**User Story:** As a system administrator, I want all embedding and indexing settings configurable via environment variables, so that deployment in different environments requires no code changes.

#### Acceptance Criteria

1. THE Embedding_Service SHALL read the OpenSearch connection URL from the `ALC_OPENSEARCH_URL` environment variable (default: `http://localhost:9200`).
2. THE Embedding_Service SHALL read the default embedding dimension from the `MODEL_EMBEDDING_DIMENSION` environment variable (default: 1024) and accept only integer values between 1 and 8192.
3. THE Embedding_Service SHALL read the embedding model name from the `MODEL_EMBEDDING_NAME` environment variable with no default value, treating it as a required configuration.
4. THE Embedding_Service SHALL read the index shard count from `ALC_LITERATURE_INDEX_SHARDS` (default: 1) and replica count from `ALC_LITERATURE_INDEX_REPLICAS` (default: 1), accepting only integer values of 1 or greater.
5. THE Embedding_Service SHALL read the HNSW `ef_construction` parameter from `ALC_LITERATURE_HNSW_EF_CONSTRUCTION` (default: 256) and `m` parameter from `ALC_LITERATURE_HNSW_M` (default: 16), accepting only integer values of 1 or greater.
6. THE Embedding_Service SHALL read the default reciprocal rank fusion `k` parameter from `ALC_LITERATURE_RRF_K` (default: 60), accepting only integer values of 1 or greater.
7. THE Embedding_Service SHALL read the Celery queue name from `ALC_LITERATURE_EMBEDDING_QUEUE` (default: `literature_ingestion`), accepting only non-empty string values.
8. IF required environment variables (`ALC_OPENSEARCH_URL`, `MODEL_EMBEDDING_NAME`) are not set, THEN THE Embedding_Service SHALL refuse to start and log an error message at ERROR level to standard error indicating the name of each missing variable.
9. IF any numeric environment variable (`MODEL_EMBEDDING_DIMENSION`, `ALC_LITERATURE_INDEX_SHARDS`, `ALC_LITERATURE_INDEX_REPLICAS`, `ALC_LITERATURE_HNSW_EF_CONSTRUCTION`, `ALC_LITERATURE_HNSW_M`, `ALC_LITERATURE_RRF_K`) contains a non-integer value or a value outside its accepted range, THEN THE Embedding_Service SHALL refuse to start and log an error message at ERROR level to standard error indicating the invalid variable name and its accepted range.
10. WHEN the Embedding_Service starts successfully, THE Embedding_Service SHALL log the resolved values of all configuration variables at INFO level, redacting connection credentials from the OpenSearch URL if present.

### Requirement 14: Embedding Vector Round-Trip Integrity

**User Story:** As a developer, I want to verify that embeddings stored in OpenSearch are identical to those generated by the model, so that search quality is not degraded by storage precision loss.

#### Acceptance Criteria

1. FOR ALL embedding vectors generated by the Embedding_Service and stored in OpenSearch, retrieving the stored vector via the OpenSearch `_source` field and comparing it element-by-element to the original generated vector SHALL yield values equal within floating-point precision tolerance (absolute difference less than 1e-6 per element) across all dimensions configured in `MODEL_EMBEDDING_DIMENSION`.
2. THE Literature_Index_Manager SHALL store embedding vectors in OpenSearch using `float32` precision (knn_vector with `data_type: float`) to match the vLLM output precision.
3. FOR ALL text inputs between 1 and 8192 characters containing at least one alphabetic character, generating an embedding, indexing it, refreshing the index, and then performing a kNN search with the same text as query against the same index SHALL return the indexed chunk as the top-1 result with a similarity score of 1.0 (self-retrieval property).
4. WHEN verifying round-trip integrity via property-based tests, THE Embedding_Service SHALL execute a minimum of 100 Hypothesis-generated examples per property, covering inputs with varying lengths (short phrases under 50 characters, medium paragraphs of 200–1000 characters, and long texts up to 8192 characters).
5. IF a stored embedding vector cannot be retrieved from OpenSearch (document missing, index unavailable, or vector field null), THEN THE Embedding_Service SHALL report a test failure indicating the specific Ingestion_Record ID and the nature of the retrieval error.
