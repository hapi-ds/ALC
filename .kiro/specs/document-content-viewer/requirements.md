# Requirements Document

## Introduction

This feature adds document content viewing and downloading capabilities across the AlcoaBase application. Currently, the system stores documents (PDF, DOCX, MD) in MinIO object storage and tracks metadata in PostgreSQL, but provides no way for users to view or download the actual file content from the UI. This feature introduces a backend download/preview API endpoint and integrates content viewing into the document detail page, search results, knowledge chat citations, and the signatures page.

## Glossary

- **Content_Viewer**: The frontend component responsible for rendering document content inline (PDF preview, Markdown rendering, or fallback display for unsupported formats).
- **Download_API**: The backend FastAPI endpoint that streams file bytes from MinIO storage for a given document version.
- **Document_Detail_Page**: The existing frontend page (`/documents/:uuid`) that shows document metadata, tags, and version history.
- **Storage_Service**: The existing backend service (`StorageService`) wrapping MinIO via aioboto3 for upload, download, and delete operations.
- **Document_Version**: A specific revision of a document identified by major and minor version numbers, with an associated `storage_key` pointing to the file in MinIO.
- **Content_Type**: The MIME type of the stored file (e.g., `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `text/markdown`).
- **Knowledge_Chat**: The AI-powered chat interface that cites source documents in its responses.
- **Presigned_URL**: A time-limited, signed URL generated by the backend that allows the browser to fetch file content directly or via proxy without additional authentication for that specific request.

## Requirements

### Requirement 1: Backend Download Endpoint

**User Story:** As a user, I want to download a specific version of a document, so that I can access the original file stored in the system.

#### Acceptance Criteria

1. WHEN a GET request is received at `/api/documents/{document_uuid}/versions/{major_version}/{minor_version}/download`, THE Download_API SHALL return the file bytes with the correct `Content-Type` header and a `Content-Disposition` header set to `attachment` with the document title as the filename.
2. WHEN the requested document version does not exist in the database, THE Download_API SHALL return HTTP 404 with a descriptive error message.
3. WHEN the requested file does not exist in MinIO storage, THE Download_API SHALL return HTTP 404 with a descriptive error message.
4. THE Download_API SHALL enforce RBAC access checks before serving the file, using the same permission model as the existing document retrieval endpoint.
5. WHEN an unauthenticated request is received, THE Download_API SHALL return HTTP 401.

### Requirement 2: Backend Content Preview Endpoint

**User Story:** As a user, I want to preview document content inline without downloading the full file, so that I can quickly review documents without leaving the application.

#### Acceptance Criteria

1. WHEN a GET request is received at `/api/documents/{document_uuid}/versions/{major_version}/{minor_version}/content`, THE Download_API SHALL return the file bytes with the correct `Content-Type` header and a `Content-Disposition` header set to `inline`.
2. WHEN the document version has a `Content_Type` of `application/pdf`, THE Download_API SHALL stream the full PDF content for browser-native rendering.
3. WHEN the document version has a `Content_Type` of `text/markdown`, THE Download_API SHALL return the raw markdown text with `Content-Type: text/markdown; charset=utf-8`.
4. WHEN the document version has a `Content_Type` that is not natively previewable (e.g., DOCX), THE Download_API SHALL return the file bytes with `Content-Disposition: attachment` as a fallback to trigger a download.
5. IF the Storage_Service raises an error during file retrieval, THEN THE Download_API SHALL return HTTP 502 with a message indicating a storage retrieval failure.

### Requirement 3: Document Detail Page Viewer Integration

**User Story:** As a user, I want to view the content of a document directly on the document detail page, so that I can read documents without downloading them separately.

#### Acceptance Criteria

1. WHEN a user navigates to the Document_Detail_Page, THE Content_Viewer SHALL display a preview of the latest document version content below the metadata section.
2. WHEN the document is a PDF, THE Content_Viewer SHALL render the PDF inline using the browser's native PDF rendering (via an `<iframe>` or `<object>` element pointing to the content endpoint).
3. WHEN the document is a Markdown file, THE Content_Viewer SHALL render the markdown as formatted HTML.
4. WHEN the document is a format not supported for inline preview, THE Content_Viewer SHALL display a message indicating the format is not previewable and offer a download button.
5. THE Document_Detail_Page SHALL display a download button that triggers a file download of the currently viewed version.
6. WHEN the user selects a different version from the version history list, THE Content_Viewer SHALL update to show the content of the selected version.

### Requirement 4: Download Button Across Application Surfaces

**User Story:** As a user, I want a download button wherever documents are referenced in the application, so that I can quickly access file content from any context.

#### Acceptance Criteria

1. WHEN a document is displayed in search results, THE Document_Detail_Page SHALL provide a download icon button that triggers a download of the latest version.
2. WHEN a source document is cited in the Knowledge_Chat response, THE Knowledge_Chat SHALL display a clickable link that opens the document content in a new tab or triggers a download.
3. THE download action SHALL always target the latest version of the document unless a specific version is explicitly selected by the user.
4. WHILE a download is in progress, THE Content_Viewer SHALL display a loading indicator to communicate progress to the user.

### Requirement 5: Content Type Detection and Storage

**User Story:** As a developer, I want document content types to be reliably stored and retrievable, so that the viewer can determine the correct rendering strategy.

#### Acceptance Criteria

1. THE Download_API SHALL determine the content type by reading the `content_type` stored at upload time or by inferring it from the file extension in the storage key.
2. WHEN a document version has no stored content type, THE Download_API SHALL infer the content type from the file extension (`.pdf` → `application/pdf`, `.docx` → `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `.md` → `text/markdown`).
3. THE Download_API SHALL include a `Content-Length` header in the response to enable progress tracking on the client side.

### Requirement 6: Security and Access Control

**User Story:** As an administrator, I want document downloads to respect the same access control rules as document metadata, so that unauthorized users cannot access file content.

#### Acceptance Criteria

1. THE Download_API SHALL require a valid `Authorization: Bearer {token}` header on all download and content requests.
2. THE Download_API SHALL validate that the requesting user has read access to the document via the existing RBAC mechanism before streaming file content.
3. WHEN a user without read permission requests a download, THE Download_API SHALL return HTTP 403 with a descriptive error message.
4. THE Download_API SHALL log all download and content access events to the audit trail, including the user ID, document UUID, version, and timestamp.

### Requirement 7: Frontend API Client Extension

**User Story:** As a frontend developer, I want the API client to support binary file downloads with proper authentication, so that I can integrate download functionality into UI components.

#### Acceptance Criteria

1. THE API Client SHALL provide a `download` method that performs an authenticated GET request and returns the response as a `Blob` object.
2. THE API Client SHALL support triggering a browser-native file save dialog using the downloaded Blob and a provided filename.
3. THE API Client SHALL propagate HTTP error responses (401, 403, 404) as typed errors consistent with the existing `ApiError` class.
