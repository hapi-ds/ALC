# Requirements Document

## Introduction

This feature extends the existing RAG knowledge base (4.2) and vLLM service layer (4.3) with multimodal capabilities. It adds two core functions: (1) Diagram and flowchart understanding during document indexing, enabling the vision model to generate structured textual descriptions of visual content (process flows, decision trees, organizational charts) that are indexed alongside regular text chunks for semantic retrieval; and (2) Video-to-SOP alignment, which supports video file uploads, extracts key frames and optional audio transcription, uses the vision model to describe observed steps, and compares extracted steps against linked SOP documents to produce discrepancy reports. Both capabilities leverage the existing vLLM multimodal inference path (gemma-4-E4B-it vision model via `/v1/chat/completions`) and integrate with the Knowledge_Service indexing and RAG_Pipeline retrieval flows. The system operates on a single GPU (24 GB VRAM) in an air-gapped network with pre-downloaded model weights.

## Glossary

- **Knowledge_Service**: The backend service (`knowledge_service.py`) responsible for document text extraction, chunking, embedding generation, indexing, and hybrid search.
- **RAG_Pipeline**: The retrieval-augmented generation service (`rag_pipeline.py`) that retrieves relevant document chunks and generates grounded responses with source citations.
- **Vision_Model**: The multimodal vision-language model (gemma-4-E4B-it) used for OCR, diagram interpretation, and video frame analysis via the `/v1/chat/completions` endpoint with base64-encoded images.
- **Model_Manager**: The async service managing GPU model loading/unloading on the vLLM server, ensuring only one large model occupies GPU memory at a time.
- **Inference_Client**: The async httpx client used to make HTTP requests to the vLLM OpenAI-compatible API endpoints.
- **Visual_Chunk**: A knowledge index chunk derived from a diagram, flowchart, or other visual element within a document, containing a structured textual description generated by the Vision_Model and metadata identifying the source page and visual type.
- **Video_Document**: A document record representing an uploaded training video file (MP4, AVI, MOV, WebM) stored in MinIO with metadata in PostgreSQL, treated as a specialized document type.
- **Frame_Extraction**: The process of extracting key frames from a video file at configurable intervals using ffmpeg, producing PNG images for vision model analysis.
- **Step_Sequence**: An ordered list of procedural steps extracted from a training video, each containing a timestamp range, a textual description of the observed action, and an optional audio transcript segment.
- **SOP_Alignment**: The process of comparing a Video_Document's extracted Step_Sequence against a linked SOP document's procedural steps to identify discrepancies.
- **Discrepancy_Report**: A structured output from SOP_Alignment containing matched steps, missing steps (in video but not SOP), extra steps (in SOP but not video), and order mismatches with severity ratings.
- **Visual_Content_Detector**: A component that analyzes PDF/DOCX pages to identify pages containing diagrams, flowcharts, or other non-textual visual elements that warrant vision model interpretation.
- **Audio_Transcriber**: An optional component that extracts and transcribes audio from video files using a speech-to-text model (e.g., Whisper) to supplement visual frame descriptions.
- **Alignment_Service**: The backend service orchestrating video-to-SOP comparison, managing frame extraction, step sequence generation, and discrepancy detection.

## Requirements

### Requirement 1: Visual Content Detection During Document Indexing

**User Story:** As a knowledge base administrator, I want the system to automatically detect pages containing diagrams and flowcharts during document indexing, so that visual content is not lost during text-only extraction.

#### Acceptance Criteria

1. WHEN a PDF or DOCX document is indexed by the Knowledge_Service, THE Visual_Content_Detector SHALL analyze each page to determine whether it contains visual elements (diagrams, flowcharts, charts, tables with graphical content, or process maps) by rendering the page to a PNG image at 150 DPI and comparing the ratio of extractable text area to total page area.
2. WHEN a page has an extractable text area ratio below 0.3 (less than 30% of the page area contains selectable text) and the page contains at least one image or drawing object, THE Visual_Content_Detector SHALL classify that page as containing visual content requiring vision model interpretation.
3. WHEN a page is classified as containing visual content, THE Visual_Content_Detector SHALL record the page number, the classification type, and the page dimensions in the indexing metadata. The classification type SHALL be determined as: "flowchart" if the page contains arrow connectors between shapes, "chart" if the page contains axis lines or data plot elements, "diagram" if the page contains shapes or images without arrow connectors, or "mixed" if the page matches more than one of the preceding categories.
4. THE Visual_Content_Detector SHALL process pages sequentially during document indexing after text extraction for the document has completed, ensuring that text chunks are indexed regardless of visual detection outcomes. Each page SHALL be processed within a timeout of 30 seconds, after which the page is skipped and a warning is logged.
5. IF a document contains more than 100 pages classified as visual content, THEN THE Visual_Content_Detector SHALL process only the first 100 visual pages and log a warning indicating the remaining visual pages were skipped due to the processing limit.
6. WHILE the Model_Manager mode is set to "mock", THE Visual_Content_Detector SHALL classify pages using only the text-area ratio heuristic without rendering images or calling the Vision_Model, and SHALL mark detected visual pages with a placeholder flag for future processing.
7. IF a page has an extractable text area ratio below 0.3 but contains no image or drawing objects, THEN THE Visual_Content_Detector SHALL not classify the page as visual content and SHALL log a debug entry indicating the page was skipped due to absence of graphical objects despite low text coverage.

### Requirement 2: Vision Model Interpretation of Diagrams and Flowcharts

**User Story:** As a user querying the knowledge base about processes, I want diagrams and flowcharts to be interpreted and indexed as searchable text, so that I can find information contained only in visual elements.

#### Acceptance Criteria

1. WHEN a page is classified as containing visual content during indexing, THE Knowledge_Service SHALL render the page to a PNG image at 300 DPI (capped at a maximum resolution of 4096x4096 pixels), encode the image as base64, call `ensure_model(OCR)` on the Model_Manager, and send the image to the Vision_Model via the Inference_Client with a structured prompt requesting a textual description of the visual content.
2. THE Knowledge_Service SHALL use a diagram-specific system prompt instructing the Vision_Model to: (a) identify the type of visual (flowchart, process diagram, organizational chart, decision tree, data flow diagram, or other), (b) describe all nodes/steps and their labels, (c) describe all connections/arrows and their direction, (d) describe any decision points and their conditions, and (e) output the description in a structured format with sections for "Type", "Elements", "Connections", and "Summary".
3. WHEN the Vision_Model returns a successful description for a visual page, THE Knowledge_Service SHALL create one or more Visual_Chunk objects containing the structured description text, metadata including `content_type: "visual"`, `visual_type` (flowchart, diagram, etc.), `source_page` (page number), and the document_uuid and version.
4. THE Knowledge_Service SHALL chunk the visual description using the same chunking parameters as regular text (default 512 tokens, 50 token overlap) and generate embeddings for each Visual_Chunk using the Embedding_Model.
5. THE Knowledge_Service SHALL index Visual_Chunks alongside regular text chunks in the same document index, with additional metadata fields (`is_visual: true`, `visual_type`, `source_page`) to enable filtering and attribution.
6. IF the Vision_Model fails to generate a description for a visual page (timeout after 90 seconds, HTTP error, or empty response), THEN THE Knowledge_Service SHALL retry the request once after a 5-second delay, and if the retry also fails, SHALL log a warning with the page number and error details, skip the visual chunk creation for that page, and continue processing remaining pages.
7. IF the Vision_Model returns a description shorter than 20 characters for a visual page, THEN THE Knowledge_Service SHALL discard the description as insufficient and log a warning indicating the visual content could not be meaningfully interpreted.
8. WHILE the Model_Manager mode is set to "mock", THE Knowledge_Service SHALL create Visual_Chunks with placeholder description text "[VISUAL_PENDING: Diagram interpretation requires Vision_Model]" and the correct metadata fields, without making any HTTP requests.
9. THE Knowledge_Service SHALL process visual pages sequentially (one page at a time) to avoid concurrent requests to the Vision_Model on the single GPU, proceeding to the next visual page only after the current page's processing completes or fails.

### Requirement 3: Visual Content Retrieval in RAG Queries

**User Story:** As a user asking questions about processes or workflows, I want the RAG pipeline to retrieve and reference visual content (diagrams, flowcharts) alongside text, so that I receive comprehensive answers that include information from visual elements.

#### Acceptance Criteria

1. WHEN the RAG_Pipeline performs hybrid search for a user query, THE RAG_Pipeline SHALL include Visual_Chunks in the search results alongside regular text chunks, ranked by the same relevance scoring mechanism, with Visual_Chunks counted within the existing top_k retrieval limit (default 5 total chunks including both text and visual).
2. WHEN a Visual_Chunk is included in the RAG context passed to the Chat_Model, THE RAG_Pipeline SHALL format it with the source reference pattern `[Source N: {title} v{version} - {visual_type} on page {source_page}]` followed by the visual description text, distinguishing it from regular text sources.
3. WHEN the RAG_Pipeline returns a response that references Visual_Chunks, THE RAG_Pipeline SHALL include Source_Citations with an additional `content_type` field set to "visual" and a `visual_type` field indicating the type of visual element (flowchart, diagram, etc.).
4. WHEN the Knowledge Chat frontend receives a citation with `content_type` set to "visual", THE Knowledge_Page SHALL render the citation with a visual indicator icon (distinct from text citations) and display the visual_type as a badge alongside the document title and page reference.
5. IF a user query contains keywords related to processes, flows, steps, or diagrams (detected via keyword matching against a configurable list with defaults: "process", "flow", "flowchart", "diagram", "workflow", "steps", "procedure", "decision tree", "sequence"), THEN THE RAG_Pipeline SHALL boost the relevance score of Visual_Chunks by a configurable factor (default 1.5x, minimum 1.0x, maximum 3.0x) prior to ranking and selection, to prioritize visual content for process-related queries.
6. THE RAG_Pipeline SHALL limit the number of Visual_Chunks included in the context to a maximum of 3 per query, selecting the 3 highest-relevance Visual_Chunks (after any boost is applied) when more are available, with remaining retrieval slots filled by text chunks.
7. IF no Visual_Chunks meet the minimum relevance score threshold used for text chunks, THEN THE RAG_Pipeline SHALL return results containing only text chunks without visual content, and SHALL not include any visual-specific citations in the response.

### Requirement 4: Video File Upload and Storage

**User Story:** As a training manager, I want to upload training videos to the document management system, so that they can be analyzed and compared against written SOPs.

#### Acceptance Criteria

1. THE Document_Service SHALL accept video file uploads with content types `video/mp4`, `video/x-msvideo` (AVI), `video/quicktime` (MOV), and `video/webm` via the existing document upload endpoint, storing the video file in MinIO with the document_type set to "Training Video".
2. WHEN a video file is uploaded, THE Document_Service SHALL validate that the file size is greater than 0 bytes and does not exceed 2 GB, and that the content type matches one of the supported video formats, returning HTTP 422 with an error message indicating which validation constraint was violated if validation fails.
3. WHEN a video file is uploaded successfully, THE Document_Service SHALL create a document record in PostgreSQL with the standard document metadata (document_uuid, title, folder_path, tags, version) and additional video-specific metadata including `duration_seconds` (extracted via ffprobe), `resolution` (width x height), `frame_count`, and `codec`, storing the results in the document metadata JSON field.
4. WHEN a video file is uploaded successfully, THE Document_Service SHALL execute ffprobe (from the ffmpeg package) with a timeout of 30 seconds to extract video metadata (duration, resolution, frame count, codec) before returning the upload response to the caller.
5. IF ffprobe fails to extract metadata from the uploaded video (corrupt file, unsupported codec, or timeout exceeded), THEN THE Document_Service SHALL still store the video file but set the video metadata fields (`duration_seconds`, `resolution`, `frame_count`, `codec`) to null and log a warning indicating metadata extraction failed with the failure reason.
6. THE video upload endpoint SHALL require the same authentication headers (`Authorization`, `X-User-Id`, `X-Company-Id`) and audit header (`X-Change-Reason`) as all other mutating document endpoints.
7. WHEN a video file is uploaded, THE Document_Service SHALL not automatically trigger frame extraction or alignment processing; these operations SHALL be initiated separately via dedicated API endpoints.

### Requirement 5: Video Frame Extraction

**User Story:** As a system processing training videos, I want to extract key frames at configurable intervals, so that the vision model can analyze what is happening at each point in the video.

#### Acceptance Criteria

1. WHEN frame extraction is triggered for a Video_Document via `POST /api/knowledge/videos/{document_uuid}/extract-frames`, THE Alignment_Service SHALL use ffmpeg to extract key frames from the video file at a configurable interval (default 5 seconds, minimum 1 second, maximum 60 seconds) specified as a query parameter `interval_seconds`.
2. IF the `interval_seconds` query parameter is provided with a value less than 1, greater than 60, or non-numeric, THEN THE Alignment_Service SHALL return HTTP 422 with an error message indicating the valid range is 1 to 60 seconds.
3. WHEN frame extraction is triggered, THE Alignment_Service SHALL extract frames as PNG images at the video's native resolution (capped at 1920x1080 if the source resolution exceeds this) and store each frame in a processing directory with filenames encoding the timestamp (e.g., `frame_00005.png` for the frame at 5 seconds).
4. WHEN frame extraction is triggered, THE Alignment_Service SHALL return HTTP 202 (Accepted) with a job status object containing a `job_id`, `status` set to "processing", and `estimated_duration_seconds`, and SHALL make the extraction results (total number of frames extracted, the interval used, and the video duration) available via the job status endpoint upon completion.
5. IF the video duration divided by the interval would produce more than 500 frames, THEN THE Alignment_Service SHALL automatically increase the interval to ensure no more than 500 frames are extracted and SHALL include the adjusted interval in the completion results.
6. IF ffmpeg fails during frame extraction (corrupt video, unsupported codec, disk space exhaustion), THEN THE Alignment_Service SHALL mark the job as "failed" with a descriptive error message indicating the failure reason and SHALL clean up any partially extracted frames from the processing directory.
7. THE frame extraction endpoint SHALL require the authentication headers (`Authorization`, `X-User-Id`, `X-Company-Id`) and the `X-Change-Reason` audit header, and SHALL validate that the referenced document_uuid exists and has document_type "Training Video", returning HTTP 404 if the document is not found.
8. WHILE frame extraction is in progress for a given Video_Document, THE Alignment_Service SHALL reject additional extraction requests for the same document with HTTP 409 (Conflict) and a message indicating extraction is already in progress.
9. WHEN frame analysis (Requirement 6) completes or fails for a Video_Document, THE Alignment_Service SHALL delete the extracted frame files from the processing directory within 60 minutes, ensuring temporary frames do not persist beyond their processing lifecycle.

### Requirement 6: Video Frame Analysis via Vision Model

**User Story:** As a system analyzing training videos, I want each extracted frame to be described by the vision model, so that the visual content of the video is converted into structured textual steps.

#### Acceptance Criteria

1. WHEN frame analysis is triggered for a Video_Document via `POST /api/knowledge/videos/{document_uuid}/analyze-frames`, THE Alignment_Service SHALL validate that frame extraction has been completed for the specified Video_Document, load each extracted frame PNG, call `ensure_model(OCR)` on the Model_Manager, and send each frame to the Vision_Model via the Inference_Client with a training-video-specific prompt.
2. IF frame extraction has not been completed for the specified Video_Document when analysis is triggered, THEN THE Alignment_Service SHALL return HTTP 422 with a message indicating that frame extraction must be completed before frame analysis can be performed.
3. THE Alignment_Service SHALL use a frame analysis system prompt instructing the Vision_Model to: (a) describe the primary action or procedure being performed in the frame, (b) identify any equipment, tools, or materials visible, (c) note any safety equipment or PPE visible, (d) identify any text or labels visible in the frame, and (e) output a concise description (maximum 200 words) of the observed step.
4. THE Alignment_Service SHALL process frames sequentially (one at a time) to avoid overwhelming the Vision_Model, with a timeout of 60 seconds per frame.
5. WHEN all frames have been analyzed, THE Alignment_Service SHALL consolidate consecutive frames with similar descriptions (cosine similarity above 0.85 on their embeddings) into single steps, producing a Step_Sequence where each step has a start_timestamp, end_timestamp, description, and frame_indices.
6. THE Alignment_Service SHALL store the generated Step_Sequence in the database associated with the Video_Document, including each step's timestamp range, description text, and confidence score derived from the ratio of successfully analyzed frames to total frames within that step's frame range (1.0 when all frames were analyzed, proportionally lower when frames within the step were marked as unanalyzed).
7. IF the Vision_Model fails to analyze a specific frame (timeout or HTTP error), THEN THE Alignment_Service SHALL log a warning for that frame, mark it as "unanalyzed" in the Step_Sequence, and continue processing remaining frames.
8. IF more than 50% of frames fail analysis, THEN THE Alignment_Service SHALL abort the analysis, return HTTP 500 with a message indicating insufficient frames could be analyzed, and remove any partially generated Step_Sequence data and frame analysis results for the current processing run from the database.
9. WHILE frame analysis is in progress for a given Video_Document, THE Alignment_Service SHALL reject additional analysis requests for the same document with HTTP 409 (Conflict) and a message indicating frame analysis is already in progress.
10. WHILE the Model_Manager mode is set to "mock", THE Alignment_Service SHALL generate placeholder step descriptions ("[FRAME_PENDING: Frame analysis requires Vision_Model]") with correct timestamp metadata, without making any HTTP requests.

### Requirement 7: Audio Transcription from Video

**User Story:** As a system analyzing training videos, I want to extract and transcribe audio narration from videos, so that spoken instructions supplement the visual frame descriptions for more accurate step extraction.

#### Acceptance Criteria

1. WHEN audio transcription is requested for a Video_Document via `POST /api/knowledge/videos/{document_uuid}/transcribe-audio`, THE Alignment_Service SHALL extract the audio track from the video file using ffmpeg, converting it to WAV format (16kHz mono) for transcription processing.
2. WHEN the audio track has been extracted successfully, THE Alignment_Service SHALL segment the extracted audio into chunks of no more than 30 seconds each, process each chunk through the configured speech-to-text model with a timeout of 60 seconds per chunk, and concatenate the results with timestamp alignment preserving the original audio timeline offsets.
3. WHEN audio transcription completes, THE Alignment_Service SHALL store the transcript as a list of segments (maximum 1000 segments), each containing `start_time`, `end_time`, and `text` fields, associated with the Video_Document record.
4. IF the video file contains no audio track, THEN THE Alignment_Service SHALL return HTTP 200 with an empty transcript array and a message indicating no audio track was found.
5. IF the speech-to-text model is not available (model not configured or not downloadable in air-gapped environment), THEN THE Alignment_Service SHALL return HTTP 503 with a message indicating audio transcription is not available and the feature is optional.
6. IF ffmpeg fails to extract the audio track from the video file (corrupt audio stream, unsupported audio codec, or I/O error), THEN THE Alignment_Service SHALL return HTTP 422 with a message indicating audio extraction failed and the reason, and SHALL clean up any partial temporary files.
7. WHEN both frame analysis (Requirement 6) and audio transcription are complete for a Video_Document, THE Alignment_Service SHALL merge the audio transcript segments with the visual Step_Sequence by assigning each transcript segment to the step whose timestamp range overlaps with the segment's time range by the greatest duration, enriching each step with the concatenated text of all assigned transcript segments in chronological order.
8. WHILE audio transcription is in progress for a given Video_Document, THE Alignment_Service SHALL reject additional transcription requests for the same document with HTTP 409 (Conflict) and a message indicating transcription is already in progress.
9. WHILE the Model_Manager mode is set to "mock", THE Alignment_Service SHALL return a placeholder transcript with a single segment containing "[AUDIO_PENDING: Audio transcription requires speech-to-text model]" without making any external calls.

### Requirement 8: SOP Linking and Step Comparison

**User Story:** As a quality manager, I want to link a training video to one or more SOP documents and compare the video's extracted steps against the SOP procedures, so that I can identify discrepancies between what is documented and what is practiced.

#### Acceptance Criteria

1. WHEN a user links a Video_Document to an SOP document via `POST /api/knowledge/videos/{document_uuid}/link-sop`, THE Alignment_Service SHALL create an association record storing the video document_uuid, the SOP document_uuid, and the SOP version at the time of linking, allowing a maximum of 10 SOP documents to be linked to a single Video_Document.
2. WHEN a user submits a link-sop request, THE Alignment_Service SHALL validate that the linked SOP document exists, belongs to the same company (tenant), and has document_type "SOP" or contains "SOP" in its tags, returning HTTP 422 with an error message indicating which validation check failed.
3. IF a user attempts to link an SOP document that is already linked to the same Video_Document, THEN THE Alignment_Service SHALL return HTTP 409 with a message indicating the SOP is already linked.
4. WHEN alignment is triggered via `POST /api/knowledge/videos/{document_uuid}/align`, THE Alignment_Service SHALL retrieve the Video_Document's Step_Sequence and each linked SOP document's text content, extract procedural steps from each SOP text using the Chat_Model with a step-extraction prompt, and perform step-by-step comparison independently for each linked SOP, producing one Discrepancy_Report per linked SOP.
5. THE Alignment_Service SHALL use the Chat_Model to extract SOP steps by sending the SOP text with a system prompt instructing it to: (a) identify all numbered or sequential procedural steps, (b) output each step with its step number and description, and (c) preserve the original ordering from the document.
6. IF the Chat_Model returns zero extracted steps from an SOP document (empty step list), THEN THE Alignment_Service SHALL skip alignment for that SOP and include it in the response with a status indicating no procedural steps could be identified in the document.
7. THE Alignment_Service SHALL compare the video Step_Sequence against the SOP steps using semantic similarity (embedding cosine similarity with a match threshold of 0.7) to identify: matched steps (video step aligns with SOP step above the threshold), missing steps (present in video but no SOP step exceeds the threshold), extra steps (present in SOP but no video step exceeds the threshold), and order mismatches (steps matched above the threshold but appearing at a sequence position difference of 2 or more between video and SOP ordering).
8. IF the Video_Document does not have a completed Step_Sequence (frame analysis not yet run), THEN THE Alignment_Service SHALL return HTTP 422 with a message indicating frame analysis must be completed before alignment can be performed.
9. IF no SOP documents are linked to the Video_Document, THEN THE Alignment_Service SHALL return HTTP 422 with a message indicating at least one SOP must be linked before alignment can be performed.
10. IF the maximum of 10 linked SOPs is already reached when a user attempts to link an additional SOP, THEN THE Alignment_Service SHALL return HTTP 422 with a message indicating the maximum number of linked SOPs has been reached.

### Requirement 9: Discrepancy Report Generation

**User Story:** As a quality manager, I want a structured discrepancy report showing mismatches between training video content and written SOPs, so that I can take corrective action on documentation or training gaps.

#### Acceptance Criteria

1. WHEN SOP alignment completes for a Video_Document, THE Alignment_Service SHALL generate a Discrepancy_Report containing: a summary section with overall alignment score (calculated as the number of matched video steps divided by the total number of video steps, expressed as a value between 0.0 and 1.0), a matched_steps array, a missing_steps array (in video but not SOP), an extra_steps array (in SOP but not video), and an order_mismatches array.
2. THE Discrepancy_Report SHALL assign a severity rating to each discrepancy: "critical" for safety-related steps missing from the SOP (steps involving PPE, hazardous materials, patient contact, or sterile technique as classified by the Chat_Model), "major" for procedural steps missing or in wrong order, and "minor" for steps with similarity score between 0.5 and 0.7 against a corresponding step (partial match below the 0.7 match threshold but same procedural intent).
3. THE Alignment_Service SHALL use the Chat_Model to assess severity by sending each discrepancy with context and a prompt instructing it to classify the severity based on GxP impact (patient safety, data integrity, product quality), with a timeout of 60 seconds per discrepancy assessment.
4. IF the Chat_Model fails to assess severity for a discrepancy (timeout, HTTP error, or unparseable response), THEN THE Alignment_Service SHALL assign a default severity of "major" to that discrepancy and log a warning indicating the severity was assigned by fallback rather than model classification.
5. THE Discrepancy_Report SHALL be stored in the database associated with the Video_Document and linked SOP, including a generated_at timestamp, the alignment_score, total_video_steps, total_sop_steps, and the user_id who triggered the alignment.
6. WHEN a Discrepancy_Report is generated, THE Alignment_Service SHALL return the report via the alignment endpoint response with HTTP 200, including all discrepancy details and the overall alignment score.
7. THE Discrepancy_Report SHALL include for each matched step: the video step description, the SOP step text, the similarity score (value between 0.0 and 1.0), and the video timestamp range where the step was observed.
8. THE Discrepancy_Report SHALL include for each missing or extra step: the step description, the source (video or SOP), the severity rating, and a recommendation text (maximum 500 characters) generated by the Chat_Model suggesting corrective action.
9. IF the Chat_Model fails to generate a recommendation for a discrepancy (timeout or HTTP error), THEN THE Alignment_Service SHALL set the recommendation text to a generic statement indicating that manual review is required for this discrepancy, and SHALL continue processing remaining discrepancies.
10. IF the alignment score is below 0.5 (less than 50% of video steps matched), THEN THE Alignment_Service SHALL flag the report with `requires_review: true` and include a summary recommendation that the SOP or training video may need significant revision.

### Requirement 10: Video Alignment API Endpoints

**User Story:** As a frontend developer, I want well-defined API endpoints for all video alignment operations, so that I can build the UI for video upload, analysis, and discrepancy viewing.

#### Acceptance Criteria

1. THE Alignment_Service SHALL expose the following endpoints under the `/api/knowledge/videos` prefix: `POST /api/knowledge/videos/{document_uuid}/extract-frames` (trigger frame extraction), `POST /api/knowledge/videos/{document_uuid}/analyze-frames` (trigger vision analysis), `POST /api/knowledge/videos/{document_uuid}/transcribe-audio` (trigger audio transcription), `POST /api/knowledge/videos/{document_uuid}/link-sop` (link an SOP document), `POST /api/knowledge/videos/{document_uuid}/align` (trigger alignment and generate report), and `GET /api/knowledge/videos/{document_uuid}/report` (retrieve the latest discrepancy report).
2. ALL video alignment endpoints SHALL require the authentication headers (`Authorization`, `X-User-Id`, `X-Company-Id`) and all POST endpoints SHALL require the `X-Change-Reason` header for ALCOA+ audit compliance; IF any required header is missing, THEN the endpoint SHALL return HTTP 400 with an error message indicating which header is missing.
3. THE `GET /api/knowledge/videos/{document_uuid}/report` endpoint SHALL return the most recent Discrepancy_Report for the specified Video_Document as a JSON object containing: `alignment_score` (float 0.0-1.0), `matched_steps` array, `missing_steps` array, `extra_steps` array, `order_mismatches` array, `total_video_steps` (integer), `total_sop_steps` (integer), `generated_at` (ISO 8601 timestamp), and `requires_review` (boolean); IF no report exists for the specified document, THEN the endpoint SHALL return HTTP 404 with a message indicating no alignment report has been generated.
4. ALL video alignment endpoints SHALL validate that the referenced `document_uuid` is a valid UUID format, exists in the database, belongs to the requesting company (tenant scoping via `X-Company-Id`), and has document_type "Training Video"; IF the `document_uuid` is not a valid UUID format, THEN the endpoint SHALL return HTTP 422; IF the document is not found, THEN the endpoint SHALL return HTTP 404; IF the document belongs to a different company, THEN the endpoint SHALL return HTTP 403.
5. THE `POST /api/knowledge/videos/{document_uuid}/link-sop` endpoint SHALL accept a JSON body with `sop_document_uuid` (required string, must be valid UUID format) and `sop_version` (optional string, defaults to latest version), and SHALL return HTTP 201 on successful linking with the created association record containing `video_document_uuid`, `sop_document_uuid`, `sop_version`, and `linked_at` timestamp.
6. ALL POST endpoints that trigger long-running processing (extract-frames, analyze-frames, transcribe-audio, align) SHALL return HTTP 202 (Accepted) with a JSON job status object containing `job_id` (UUID string), `status` ("processing"), and `estimated_duration_seconds` (integer, calculated based on video duration and operation type), and SHALL provide a `GET /api/knowledge/videos/jobs/{job_id}` endpoint to poll job completion status.
7. THE `GET /api/knowledge/videos/jobs/{job_id}` endpoint SHALL return the current job state as a JSON object containing: `job_id`, `status` (one of "processing", "completed", or "failed"), `started_at` (ISO 8601 timestamp), `completed_at` (ISO 8601 timestamp, null if not finished), `progress_percent` (integer 0-100), and conditionally `result_reference` (resource URL when completed) or `error_message` (string when failed); IF the `job_id` does not exist, THEN the endpoint SHALL return HTTP 404.
8. IF a POST endpoint that triggers long-running processing is called for a Video_Document that already has a job in "processing" state for the same operation type, THEN THE Alignment_Service SHALL return HTTP 409 (Conflict) with a message indicating the operation is already in progress and the existing `job_id`.

### Requirement 11: Discrepancy Report Frontend Display

**User Story:** As a quality manager, I want to view video-to-SOP alignment results in a clear visual interface, so that I can quickly identify and act on discrepancies between training videos and written procedures.

#### Acceptance Criteria

1. THE Knowledge_Page SHALL provide a "Video Alignment" section accessible from the Video_Document detail view, displaying the latest Discrepancy_Report with an overall alignment score shown as a percentage badge with color coding (green for 80%+, yellow for 50-79%, red for below 50%).
2. THE Knowledge_Page SHALL render the Discrepancy_Report as a side-by-side comparison view with video steps on the left column and SOP steps on the right column, with visual connectors (lines or highlights) showing matched pairs.
3. THE Knowledge_Page SHALL highlight discrepancies using color-coded indicators: red background for critical severity, orange for major severity, and yellow for minor severity, with a severity legend displayed at the top of the report view.
4. WHEN a user clicks on a specific video step in the report, THE Knowledge_Page SHALL display the frame thumbnail(s) associated with that step's timestamp range and the full step description including any audio transcript text, or a placeholder message indicating frames are unavailable if the step is marked as "unanalyzed".
5. THE Knowledge_Page SHALL display a summary panel at the top of the report containing: the alignment score, total video steps, total SOP steps, count of matched/missing/extra/reordered steps, the date the report was generated, and the linked SOP document title with a clickable link.
6. IF no Discrepancy_Report exists for a Video_Document, THEN THE Knowledge_Page SHALL display a prompt indicating that the user should run frame extraction and alignment, with action buttons to trigger frame extraction, frame analysis, and SOP alignment in that sequence.
7. WHILE a processing operation (frame extraction, frame analysis, or alignment) is in progress for the Video_Document, THE Knowledge_Page SHALL display a job progress indicator showing the progress percentage and estimated time remaining sourced from the job status endpoint, polling the `GET /api/knowledge/videos/jobs/{job_id}` endpoint every 5 seconds and automatically rendering the completed results when the job status transitions to "completed" or displaying an error message indicating the failure reason when the job status transitions to "failed".
8. IF the Knowledge_Page fails to retrieve the Discrepancy_Report from the API (network error, HTTP 5xx, or timeout after 15 seconds), THEN THE Knowledge_Page SHALL display an error message indicating the report could not be loaded and provide a retry button to re-attempt the request.

### Requirement 12: Visual Content Indexing Pipeline Integration

**User Story:** As a system administrator, I want visual content detection and interpretation to integrate seamlessly with the existing document indexing pipeline, so that enabling multimodal indexing does not disrupt the current text-based indexing flow.

#### Acceptance Criteria

1. WHEN a document is submitted for indexing, THE Knowledge_Service SHALL first perform standard text extraction and chunking, then run the Visual_Content_Detector on the same document, and finally process any detected visual pages through the Vision_Model, ensuring text chunks are always indexed regardless of visual processing outcomes, and completing all visual processing within a maximum of 300 seconds per document (after which remaining unprocessed visual pages are skipped and logged as warnings).
2. IF visual content processing fails for any or all pages of a document, THEN THE Knowledge_Service SHALL still complete the text-based indexing successfully, log a warning per failed visual page including the page number and failure reason, and return the indexing response to the caller with the visual indexing status set to "partial" or "pending" as appropriate without raising an exception.
3. THE Knowledge_Service SHALL track visual indexing status per document with states: "not_applicable" (no visual content detected or `ENABLE_VISUAL_INDEXING` is `false`), "pending" (visual content detected but not yet processed), "completed" (all visual pages processed successfully), or "partial" (one or more visual pages failed processing or were skipped due to timeout).
4. WHEN a document is re-indexed (new version uploaded), THE Knowledge_Service SHALL remove all previous Visual_Chunks for that document_uuid and version before creating new ones, preventing stale visual descriptions from persisting in the index.
5. THE Knowledge_Service SHALL expose a configuration flag `ENABLE_VISUAL_INDEXING` (environment variable, default `true`) that allows disabling visual content detection and processing entirely without affecting text-based indexing.
6. WHILE `ENABLE_VISUAL_INDEXING` is set to `false`, THE Knowledge_Service SHALL skip all visual content detection and Vision_Model calls during indexing, processing only text content as in the pre-multimodal behavior, and SHALL set the visual indexing status to "not_applicable" for any document indexed during this state.
7. WHEN document indexing completes, THE Knowledge_Service SHALL log indexing metrics at INFO level including: total pages processed, visual pages detected, visual pages successfully interpreted, visual chunks created, and total indexing duration in milliseconds.
8. WHEN document indexing completes successfully, THE Knowledge_Service SHALL include the visual indexing status and the count of visual chunks created in the indexing response returned to the caller, enabling downstream systems to determine whether visual content is available for retrieval.
