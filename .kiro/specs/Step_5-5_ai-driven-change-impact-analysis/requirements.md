# Requirements Document

## Introduction

This feature implements AI-Driven Change Impact Analysis (Phase 5.5) for the AlcoaBase Document & Knowledge Management System. When a document is updated (new version uploaded or content modified), the system automatically scans the repository to identify which other documents and training tasks are potentially affected by the change. It provides two core capabilities:

1. **Automated Dependency Mapping**: Identifies documents (URS, MVP, SOP, etc.) and Training Tasks that reference or depend on the updated document, flagging them as potentially out of date.

2. **Gap Analysis**: Performs a semantic comparison between an updated document and its dependent documents, highlighting specific sections that no longer align with the updated requirements or procedures.

The feature leverages the existing AI/RAG infrastructure (Phase 4.2-4.3), the Agent Registry (Phase 5.1) for a specialized "Change Impact Analyst" agent archetype, and the Cross-Reference service (Phase 5.4) for dependency graph construction. Impact analysis runs as an async Celery task, producing structured reports that integrate with the existing audit trail and document workflow.

## Glossary

- **Impact_Analysis_Engine**: The AI service that orchestrates change impact analysis by detecting document dependencies, performing semantic comparison between document versions, and producing structured impact reports identifying affected documents and training tasks.
- **Dependency_Graph**: A directed graph structure representing relationships between documents within a company scope. Nodes are documents (identified by document_uuid); edges represent dependency relationships (e.g., "MVP validates URS", "SOP references URS", "Training Task covers SOP"). Built from cross-references, explicit links, and semantic similarity.
- **Impact_Report**: A structured output produced by the Impact_Analysis_Engine containing: the triggering document change, a list of affected documents with severity ratings, affected training tasks, specific section-level gap findings, and recommended actions. Persisted as an immutable audit record.
- **Change_Delta**: The semantic difference between two versions of a document, represented as a list of changed sections with their old and new content summaries, classified by change type (addition, modification, deletion).
- **Gap_Finding**: A specific mismatch identified between an updated source document and a dependent document, containing: the source section that changed, the dependent document section that is now misaligned, a severity rating (critical, major, minor), and a description of the gap.
- **Dependency_Type**: The classification of a relationship between two documents. Types include: "validates" (MVP validates URS requirements), "references" (SOP references another SOP), "implements" (protocol implements URS requirement), "trains_on" (Training Task covers SOP content), and "derived_from" (document generated from template of another).
- **Impact_Severity**: The assessed severity of a change's impact on a dependent document: "critical" (dependent document contradicts updated content), "major" (dependent document is missing updated requirements or procedures), "minor" (dependent document uses outdated terminology or references but remains functionally correct).
- **Change_Impact_Analyst**: A specialized AI agent archetype (registered in the Agent Registry 5.1) configured for document comparison and impact assessment, with system prompts tuned for regulatory document analysis, cross-reference validation, and gap identification.
- **Affected_Item**: A document or training task identified as impacted by a change, including: the item identifier, relationship type to the changed document, impact severity, and specific sections affected.
- **InferenceClient**: The existing async HTTP client for vLLM communication (from 4.3).
- **KnowledgeService**: The existing RAG service for document retrieval, text extraction, and semantic search (from 4.2).
- **CrossReferenceService**: The existing service (from 5.4) that extracts and manages cross-references between documents.
- **JobTracker**: The existing async job tracking service for Celery task progress reporting.
- **TrainingTask**: The existing model (from 3.3) representing a training assignment linked to a specific SOP version.

## Requirements

### Requirement 1: Automated Dependency Graph Construction

**User Story:** As a quality manager, I want the system to automatically map dependencies between documents in my repository, so that when a document changes I can immediately see which other documents and training tasks are affected.

#### Acceptance Criteria

1. THE Impact_Analysis_Engine SHALL expose a POST /api/impact-analysis/dependency-graph/build endpoint that accepts {scope (optional, "full" or "incremental", default "incremental")} and returns HTTP 202 with a job_id for the async dependency graph construction task. This endpoint SHALL require the X-Change-Reason header.
2. WHEN an incremental dependency graph build is requested, THE Impact_Analysis_Engine SHALL scan only documents modified since the last successful graph build timestamp, updating existing graph edges and adding new ones without rebuilding the entire graph. IF no previous successful graph build exists for the company, THEN THE Impact_Analysis_Engine SHALL treat the incremental request as a full build.
3. WHEN a full dependency graph build is requested, THE Impact_Analysis_Engine SHALL scan all documents within the company scope, extracting cross-references using the CrossReferenceService and semantic similarity via the KnowledgeService to construct the complete Dependency_Graph.
4. THE Impact_Analysis_Engine SHALL detect the following Dependency_Types between documents: "validates" (identified by requirement ID cross-references between MVP/IQ/OQ/PQ and URS documents), "references" (identified by explicit document_uuid citations or title mentions), "implements" (identified by test case IDs referencing requirement IDs), "trains_on" (identified by TrainingTask records linking SOPs to training assignments), and "derived_from" (identified by GenerationProvenance records linking generated documents to their source templates or reference documents).
5. THE Impact_Analysis_Engine SHALL persist the Dependency_Graph as a set of edge records in the database, each containing: source_document_uuid, target_document_uuid, dependency_type, confidence_score (0.0 to 1.0), detected_references (array of specific identifiers linking the documents), and last_verified_at timestamp.
6. THE Impact_Analysis_Engine SHALL assign confidence_score values based on detection method: 1.0 for explicit cross-references (exact ID matches), 0.9 for database-linked relationships (TrainingTask, GenerationProvenance), and 0.5 to 0.8 for semantically inferred relationships (based on embedding similarity score from KnowledgeService). THE Impact_Analysis_Engine SHALL NOT create edges for semantically inferred relationships where the embedding similarity score is below 0.5, discarding candidate relationships that fall below this minimum threshold.
7. THE Impact_Analysis_Engine SHALL include Training Task dependencies in the graph by querying TrainingTask records and creating "trains_on" edges from each SOP document_uuid to a virtual node representing the training task group for that SOP version.
8. THE Impact_Analysis_Engine SHALL expose a GET /api/impact-analysis/dependency-graph endpoint that returns the Dependency_Graph for the current company as a list of edges, filterable by source_document_uuid, target_document_uuid, and dependency_type query parameters, with pagination via limit (default 50, maximum 200) and offset (default 0) query parameters.
9. THE Impact_Analysis_Engine SHALL expose a GET /api/impact-analysis/dependency-graph/{document_uuid} endpoint that returns all direct dependencies (both upstream and downstream) for a specific document, grouped by dependency_type, including the confidence_score and detected_references for each edge. IF the specified document_uuid has no edges in the Dependency_Graph, THEN THE Impact_Analysis_Engine SHALL return an empty result set grouped by dependency_type with zero entries rather than HTTP 404.
10. IF the dependency graph build encounters a document that cannot be retrieved from storage or fails text extraction, THEN THE Impact_Analysis_Engine SHALL skip that document, record a warning in the job metadata identifying the inaccessible document_uuid, and continue processing remaining documents.
11. THE Impact_Analysis_Engine SHALL scope all dependency graph operations to the company identified by the X-Company-Id header.
12. THE Impact_Analysis_Engine SHALL complete an incremental dependency graph build within 300 seconds. IF the build exceeds this timeout, THEN THE Impact_Analysis_Engine SHALL persist all edges discovered so far, mark the job as "partial_success" with a list of unprocessed document_uuids, and record the last processed document for resumption.
13. THE Impact_Analysis_Engine SHALL deduplicate dependency edges: if an edge between the same source and target with the same dependency_type already exists, THE Impact_Analysis_Engine SHALL update the existing edge's confidence_score, detected_references, and last_verified_at rather than creating a duplicate.
14. WHEN an incremental dependency graph build processes a modified document, THE Impact_Analysis_Engine SHALL remove any existing edges originating from that document whose detected_references are no longer present in the document's current content, ensuring stale dependencies are pruned when cross-references are deleted from a document.
15. IF the document_uuid provided to the GET /api/impact-analysis/dependency-graph/{document_uuid} endpoint does not correspond to any document within the company scope, THEN THE Impact_Analysis_Engine SHALL return HTTP 404 with an error message indicating the document was not found.

### Requirement 2: Automatic Change Impact Trigger

**User Story:** As a document controller, I want the system to automatically trigger an impact analysis whenever a document is updated, so that affected stakeholders are immediately notified without manual intervention.

#### Acceptance Criteria

1. WHEN a new DocumentVersion is created for an existing document (version upload via the existing document versioning endpoint), THE Impact_Analysis_Engine SHALL automatically enqueue a change impact analysis Celery task on the ai_operations queue within 5 seconds of the version creation event.
2. THE Impact_Analysis_Engine SHALL detect document version creation events by subscribing to the existing SQLAlchemy after_insert event on the DocumentVersion model, extracting the document_id, document_uuid, new version number, and company_id from the event context.
3. IF the document associated with a new DocumentVersion has current_status "Draft" or is flagged as is_csv_validation_record, THEN THE Impact_Analysis_Engine SHALL NOT enqueue an impact analysis task for that version creation event.
4. THE Impact_Analysis_Engine SHALL expose a POST /api/impact-analysis/trigger endpoint that accepts {document_id, document_version_id (optional, defaults to latest version)} and returns HTTP 202 with a job_id, allowing manual triggering of impact analysis for cases where automatic triggering was missed or a re-analysis is needed. This endpoint SHALL require the X-Change-Reason header.
5. IF a change impact analysis job with status "processing" already exists for the same document_uuid within the same company when a new trigger is received, THEN THE Impact_Analysis_Engine SHALL return HTTP 409 with the existing job_id. A processing job SHALL be considered stale and eligible for replacement if its last progress update is older than 600 seconds.
6. WHEN an impact analysis is triggered, THE Impact_Analysis_Engine SHALL compute the Change_Delta between the new version and the immediately preceding version by: (a) extracting text from both versions via KnowledgeService, (b) performing section-level diff to identify added, modified, and deleted sections, (c) classifying each change by significance level ("high" for changes to procedural steps, safety-critical content, or regulatory requirements; "medium" for changes to descriptive content or non-critical references; "low" for formatting, typographical, or cosmetic changes) using the Change_Impact_Analyst agent.
7. THE Impact_Analysis_Engine SHALL scope all trigger operations to the company identified by the X-Company-Id header.
8. IF the preceding document version cannot be retrieved (first version of a document, or storage failure), THEN THE Impact_Analysis_Engine SHALL treat the entire document content as "new" and perform impact analysis against the full content rather than a delta.
9. IF the Celery broker is unavailable or the task fails to enqueue when an automatic trigger fires, THEN THE Impact_Analysis_Engine SHALL log the failure with the document_uuid and version number, and the document SHALL remain eligible for analysis via the manual trigger endpoint (criterion 4) or upon the next version creation event.

### Requirement 3: Impact Assessment and Affected Item Identification

**User Story:** As a regulatory affairs specialist, I want the system to identify exactly which documents and training tasks are affected by a document change and assess the severity of impact, so that I can prioritize remediation efforts.

#### Acceptance Criteria

1. WHEN an impact analysis job executes, THE Impact_Analysis_Engine SHALL query the Dependency_Graph for all documents that have a direct dependency on the changed document (downstream edges where the changed document is the source), producing a list of candidate Affected_Items.
2. FOR EACH candidate Affected_Item, THE Impact_Analysis_Engine SHALL use the Change_Impact_Analyst agent to assess whether the Change_Delta actually impacts the dependent document by comparing the changed sections against the relevant sections of the dependent document retrieved via KnowledgeService. IF the agent determines the Change_Delta does not impact the candidate, THEN THE Impact_Analysis_Engine SHALL exclude that candidate from the final Affected_Items list.
3. THE Impact_Analysis_Engine SHALL assign an Impact_Severity to each confirmed Affected_Item: "critical" when the dependent document contains statements that now contradict the updated source, "major" when the dependent document is missing content that the updated source now requires, and "minor" when the dependent document uses outdated terminology or version references but remains functionally aligned.
4. THE Impact_Analysis_Engine SHALL identify affected Training Tasks by querying TrainingTask records where sop_document_uuid matches the changed document's document_uuid and is_completed is false, flagging them as requiring content review. For completed training (TrainingRecord with is_valid true), THE Impact_Analysis_Engine SHALL flag the training as potentially invalidated if the Change_Delta includes changes to procedural steps or safety-critical content (defined as: changes to sections containing hazard warnings, PPE requirements, critical process parameters, or regulatory compliance statements identified by the Change_Impact_Analyst agent).
5. THE Impact_Analysis_Engine SHALL produce a structured list of Affected_Items, each containing: affected_document_uuid (or training_task_id), affected_document_title, dependency_type, impact_severity, affected_sections (list of section headings in the dependent document that are impacted), change_summary (one-sentence description of why the item is affected, maximum 500 characters), and recommended_action ("update_required", "review_recommended", or "retraining_required").
6. THE Impact_Analysis_Engine SHALL limit the assessment to a maximum of 50 candidate Affected_Items per analysis job. IF the Dependency_Graph contains more than 50 downstream dependencies, THEN THE Impact_Analysis_Engine SHALL prioritize by confidence_score (highest first) and dependency_type (validates > implements > references > trains_on > derived_from).
7. THE Impact_Analysis_Engine SHALL scope all assessment operations to the company identified by the X-Company-Id header, ensuring impact analysis never crosses company boundaries.
8. IF the Change_Impact_Analyst agent (InferenceClient) is unavailable during assessment of a specific Affected_Item (connection timeout after 30 seconds, HTTP 503, or HTTP 429 after 3 retries with exponential backoff), THEN THE Impact_Analysis_Engine SHALL mark that item with impact_severity "unknown" and recommended_action "manual_review_required", recording the inference failure reason in the job metadata, and continue processing remaining items.
9. IF the KnowledgeService fails to retrieve the content of a candidate Affected_Item's document (storage unavailable or text extraction failure), THEN THE Impact_Analysis_Engine SHALL mark that item with impact_severity "unknown" and recommended_action "manual_review_required", recording the retrieval failure in the job metadata, and continue processing remaining items.

### Requirement 4: Gap Analysis Between Document Pairs

**User Story:** As a quality manager, I want the system to compare an updated document against its dependent documents and highlight specific sections that no longer meet the updated requirements, so that I can see exactly what needs to be fixed.

#### Acceptance Criteria

1. THE Impact_Analysis_Engine SHALL expose a POST /api/impact-analysis/gap-analysis endpoint that accepts {source_document_id, target_document_id, source_version_id (optional, defaults to latest), target_version_id (optional, defaults to latest)} and returns HTTP 202 with a job_id for the async gap analysis task. This endpoint SHALL require the X-Change-Reason header.
2. WHEN a gap analysis job executes, THE Impact_Analysis_Engine SHALL: (a) extract full text and section structure from both the source and target documents via KnowledgeService, (b) identify requirement statements, procedural steps, and key assertions in the source document, (c) for each identified item in the source, search the target document for corresponding coverage, (d) produce Gap_Findings for items classified as "missing", "contradicts", "incomplete", or "outdated" per the gap_type definitions in criterion 3.
3. THE Impact_Analysis_Engine SHALL produce Gap_Findings containing: source_section (heading and paragraph index in the source document), source_content_excerpt (first 300 characters of the relevant source text), target_section (heading and paragraph index in the target document where coverage was expected, or "not_found" if no corresponding section exists), target_content_excerpt (first 300 characters of the existing target text, or empty if not found), gap_type ("missing" if no coverage exists, "contradicts" if target states the opposite, "incomplete" if target partially covers the requirement, "outdated" if target references a superseded version), severity (Impact_Severity), and remediation_suggestion (AI-generated one-sentence recommendation for fixing the gap).
4. THE Impact_Analysis_Engine SHALL use the Change_Impact_Analyst agent to perform the semantic comparison, providing it with: the source document sections, the target document sections, the dependency_type between the documents, and instructions to identify misalignments specific to the document types (e.g., for URS→MVP pairs, check that every requirement has a corresponding validation approach).
5. THE Impact_Analysis_Engine SHALL expose a GET /api/impact-analysis/gap-analysis/{job_id}/results endpoint that returns the list of Gap_Findings for a completed gap analysis job, with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters, and filterable by severity and gap_type query parameters. IF the job status is "processing", THEN THE Impact_Analysis_Engine SHALL return HTTP 202 with the current job progress. IF the job status is "failed", THEN THE Impact_Analysis_Engine SHALL return HTTP 200 with an empty gap_findings array and the failure reason in the response metadata.
6. THE Impact_Analysis_Engine SHALL limit gap analysis to document pairs where a dependency relationship exists in the Dependency_Graph (confidence_score >= 0.5). IF no dependency relationship exists between the specified documents, THEN THE Impact_Analysis_Engine SHALL return HTTP 422 with an error message indicating no known dependency exists between the documents, suggesting the user build the dependency graph first.
7. THE Impact_Analysis_Engine SHALL complete a gap analysis job within 180 seconds. IF the analysis exceeds this timeout, THEN THE Impact_Analysis_Engine SHALL persist all Gap_Findings discovered so far, mark the job as "partial_success", and record the last processed source section for context.
8. THE Impact_Analysis_Engine SHALL scope all gap analysis operations to the company identified by the X-Company-Id header.
9. IF either the source or target document cannot be retrieved from storage or fails text extraction, THEN THE Impact_Analysis_Engine SHALL mark the gap analysis job as failed with a reason identifying which document (source or target) was inaccessible and the nature of the failure (not found in storage or text extraction error).
10. THE Impact_Analysis_Engine SHALL generate a maximum of 100 Gap_Findings per analysis job. IF more gaps are detected, THE Impact_Analysis_Engine SHALL retain the 100 highest-severity findings and record the total count of detected gaps in the job metadata.
11. IF the source_document_id equals the target_document_id, THEN THE Impact_Analysis_Engine SHALL return HTTP 422 with an error message indicating that gap analysis requires two distinct documents. IF either the source_document_id or target_document_id does not correspond to an existing document within the company scope, THEN THE Impact_Analysis_Engine SHALL return HTTP 404 with an error message identifying which document was not found.
12. IF the Change_Impact_Analyst agent (InferenceClient) is unavailable during gap analysis execution, THEN THE Impact_Analysis_Engine SHALL mark the gap analysis job as failed with a reason indicating inference service unavailability, and record the last successfully processed source section in the job metadata.

### Requirement 5: Impact Report Generation and Persistence

**User Story:** As a quality auditor, I want a complete, immutable record of every change impact analysis performed, including findings and AI reasoning, so that I can demonstrate regulatory compliance and traceability of change management decisions.

#### Acceptance Criteria

1. THE Impact_Analysis_Engine SHALL create an immutable Impact_Report record for each impact analysis job that reaches a terminal state (status "completed", "partial_success", or "failed") containing: report_id (UUID), triggering_document_uuid, triggering_version_id, change_delta_summary (structured summary of what changed), affected_items (list of Affected_Items with severity and recommendations), gap_findings (list of Gap_Findings if gap analysis was performed), status (the terminal status of the job), analysis_timestamp, analysis_duration_ms, agent_archetype_used, model_used, total_token_count, requesting_user_id (or "system" for auto-triggered analyses), and company_id. For "failed" jobs, affected_items and gap_findings SHALL be empty arrays and change_delta_summary SHALL contain the failure context.
2. THE Impact_Analysis_Engine SHALL persist Impact_Report records as immutable rows in the database (no UPDATE or DELETE operations permitted). Reports SHALL be retained indefinitely regardless of whether the triggering document is later deleted or superseded.
3. THE Impact_Analysis_Engine SHALL expose a GET /api/impact-analysis/reports endpoint that returns all Impact_Reports for the current company, sorted by analysis_timestamp descending (newest first), filterable by triggering_document_uuid, severity (returns reports containing at least one finding of the specified severity), date_range (ISO 8601 start_date and end_date query parameters), and status (completed, partial_success, failed), with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters. The response SHALL include a total_count field indicating the total number of matching reports before pagination.
4. THE Impact_Analysis_Engine SHALL expose a GET /api/impact-analysis/reports/{report_id} endpoint that returns the full Impact_Report including all affected items and gap findings. This endpoint SHALL return HTTP 404 if the report does not exist or does not belong to the company identified by the X-Company-Id header. IF the report_id parameter is not a valid UUID format, THEN THE Impact_Analysis_Engine SHALL return HTTP 422 with an error message indicating invalid report_id format.
5. THE Impact_Analysis_Engine SHALL include per-item AI reasoning in the Impact_Report: for each Affected_Item and Gap_Finding, the report SHALL record the inference_prompt_summary (first 500 characters of the prompt sent to the Change_Impact_Analyst), the model_response_summary (first 500 characters of the AI response), and the token_count for that individual assessment.
6. THE Impact_Analysis_Engine SHALL scope all report queries to the company identified by the X-Company-Id header.
7. IF the Impact_Report record cannot be persisted during an analysis job (database write failure), THEN THE Impact_Analysis_Engine SHALL mark the job status as "failed" via the JobTracker with an error_message indicating the persistence failure, ensuring no impact analysis results exist without a corresponding audit trail.
8. WHEN an impact analysis is auto-triggered by a document version event (Requirement 2), THE Impact_Analysis_Engine SHALL record requesting_user_id as the user who uploaded the new version (extracted from the DocumentVersion.uploaded_by field). IF the uploaded_by field is null or references a user that no longer exists, THEN THE Impact_Analysis_Engine SHALL record requesting_user_id as null and set a metadata flag "user_attribution_unavailable" to true in the change_delta_summary.

### Requirement 6: Impact Analysis Job Management and Status Tracking

**User Story:** As a user who triggered an impact analysis, I want to track the progress of the analysis and retrieve results when complete, so that I know when findings are ready for review.

#### Acceptance Criteria

1. THE Impact_Analysis_Engine SHALL track all impact analysis jobs via the existing JobTracker service, creating a job with operation "change_impact_analysis" and estimated_duration_seconds based on the number of downstream dependencies (15 seconds per dependency as baseline estimate, minimum 30 seconds).
2. THE Impact_Analysis_Engine SHALL update job progress monotonically as analysis proceeds: 10% after Change_Delta computation, 20% after Dependency_Graph query, 20-85% proportionally as each Affected_Item is assessed (evenly distributed across items), 85-95% during gap analysis (if performed as part of the same job), and 100% after Impact_Report persistence. Progress SHALL never decrease from a previously reported value.
3. THE Impact_Analysis_Engine SHALL expose a GET /api/impact-analysis/jobs/{job_id}/status endpoint that returns HTTP 200 with a JSON response containing: job_id, status (processing, completed, partial_success, failed), progress_percent (integer 0-100), current_phase ("computing_delta", "querying_dependencies", "assessing_impact", "analyzing_gaps", "persisting_report"), items_assessed (integer), items_total (integer), critical_findings_count (integer), major_findings_count (integer), minor_findings_count (integer), and error_message (null unless status is failed, maximum 1000 characters describing the failure reason).
4. WHEN an impact analysis job completes with status "completed" or "partial_success", THE Impact_Analysis_Engine SHALL include in the job result: report_id, total_affected_items, critical_count, major_count, minor_count, affected_training_tasks_count, analysis_duration_ms, and a summary_sentence (AI-generated summary of the overall impact, maximum 200 characters, truncated with ellipsis if the model produces a longer response).
5. THE Impact_Analysis_Engine SHALL enforce a maximum analysis timeout of 600 seconds (10 minutes) per job. IF the timeout is exceeded, THEN THE Impact_Analysis_Engine SHALL persist findings discovered so far as a "partial_success" report, record the list of unassessed Affected_Item document_uuids in the job metadata field "unassessed_items", and set error_message to indicate the timeout with the count of unassessed items.
6. THE Impact_Analysis_Engine SHALL scope all job status queries to the company identified by the X-Company-Id header.
7. IF the job_id provided to the status endpoint does not exist or does not belong to the requesting company, THEN THE Impact_Analysis_Engine SHALL return HTTP 404 with an error message indicating the job was not found.
8. IF the JobTracker service is unavailable when creating a job record, THEN THE Impact_Analysis_Engine SHALL fail the analysis request and return HTTP 503 with an error message indicating the job tracking service is temporarily unavailable.
9. IF an impact analysis job fails due to an unrecoverable error (not a timeout), THEN THE Impact_Analysis_Engine SHALL set the job status to "failed", populate error_message with the failure category and affected component (without exposing internal stack traces), and set progress_percent to the last successfully reported value.

### Requirement 7: Change Impact Analyst Agent Configuration

**User Story:** As a system administrator, I want a specialized AI agent archetype configured for change impact analysis, so that the system uses appropriate prompts and parameters for regulatory document comparison and gap identification.

#### Acceptance Criteria

1. THE Impact_Analysis_Engine SHALL register a "Change Impact Analyst" agent archetype in the Agent Registry (5.1) with agent_type "review", temperature 0.2, max_tokens 4096, and an evaluation rubric with scoring_method "weighted_average", criteria [accuracy of gap identification (weight 0.30), completeness of coverage assessment (weight 0.30), correctness of severity classification (weight 0.25), regulatory awareness (weight 0.15)], and severity_thresholds (critical: 0.9, major: 0.7, minor: 0.4, informational: 0.2).
2. THE Change_Impact_Analyst agent SHALL be configured with a system prompt that instructs the model to: identify misalignments between document pairs in a regulated environment, classify gaps by severity using the Impact_Severity definitions (critical: contradicts updated content, major: missing updated requirements, minor: outdated terminology but functionally correct), provide specific section references for all findings, avoid false positives by requiring clear evidence of misalignment before reporting a gap, and apply dependency_type-aware strictness (a "validates" relationship requires every source requirement to have corresponding target coverage, while a "references" relationship only requires no direct contradictions).
3. THE Change_Impact_Analyst agent SHALL be defined as a YAML file named "change-impact-analyst.yaml" in the agents/archetypes/ directory following the agent-definition-v2.json schema (including required fields: schema_version "2.0", dspy_modules with at least one ChainOfThought module, and knowledge_scopes with tags relevant to change impact analysis), enabling hot-reload via the agent file watcher without code changes.
4. THE Impact_Analysis_Engine SHALL use the Change_Impact_Analyst agent exclusively for impact assessment and gap analysis inference calls, passing document context through the InferenceClient with the agent's configured temperature (0.2) and max_tokens (4096) parameters.
5. IF the Change_Impact_Analyst agent archetype is not found in the Agent Registry at analysis time, THEN THE Impact_Analysis_Engine SHALL fall back to the existing "Regulatory Compliance Auditor" archetype with a system prompt suffix appended that instructs the model to focus on change impact assessment and gap identification between document pairs rather than general compliance auditing, and SHALL record the fallback event (including the missing archetype name and timestamp) in the job metadata under a "fallback_used" field.
6. IF the Change_Impact_Analyst YAML file fails schema validation against agent-definition-v2.json during loading, THEN THE Impact_Analysis_Engine SHALL reject the file, log a validation error identifying the failing field, and retain the previously loaded valid configuration until a corrected file is provided.

### Requirement 8: Notification and Integration with Document Workflow

**User Story:** As a document controller, I want to be notified when an impact analysis identifies critical or major findings affecting my documents, so that I can initiate corrective actions through the existing workflow system.

#### Acceptance Criteria

1. WHEN an impact analysis completes with at least one "critical" or "major" Affected_Item, THE Impact_Analysis_Engine SHALL create an impact_notification record for each affected document's owner (the user identified by Document.created_by), containing: notification_type ("change_impact"), report_id, affected_document_uuid, impact_severity, change_summary (maximum 500 characters), and created_at timestamp.
2. THE Impact_Analysis_Engine SHALL expose a GET /api/impact-analysis/notifications endpoint that returns all unacknowledged impact notifications for the current user within their company, sorted by severity (critical first) then by created_at (newest first), with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters.
3. THE Impact_Analysis_Engine SHALL expose a POST /api/impact-analysis/notifications/{notification_id}/acknowledge endpoint that marks a notification as acknowledged, recording the acknowledging user_id and timestamp. This endpoint SHALL require the X-Change-Reason header. IF the notification_id does not exist or does not belong to the requesting company, THEN THE Impact_Analysis_Engine SHALL return HTTP 404. IF the notification is already acknowledged, THEN THE Impact_Analysis_Engine SHALL return HTTP 200 with the existing acknowledgment details (idempotent operation).
4. WHEN an impact analysis identifies a Training Task as affected with recommended_action "retraining_required", THE Impact_Analysis_Engine SHALL update the affected TrainingTask's is_completed field to false (resetting completion status) and record the reason as "Invalidated by change impact analysis: {report_id}". This SHALL trigger the existing training-gated access control (3.5) to re-enforce training requirements. IF the TrainingTask is_completed is already false, THEN THE Impact_Analysis_Engine SHALL skip the update (idempotent).
5. THE Impact_Analysis_Engine SHALL expose a GET /api/impact-analysis/documents/{document_uuid}/status endpoint that returns the latest impact analysis status for a specific document: last_analysis_date, last_analysis_report_id, outstanding_critical_count, outstanding_major_count, and is_up_to_date (boolean, true if no unresolved critical or major findings exist for this document as a target). IF the document has never been analyzed, THEN THE Impact_Analysis_Engine SHALL return last_analysis_date as null, last_analysis_report_id as null, outstanding counts as 0, and is_up_to_date as true.
6. THE Impact_Analysis_Engine SHALL scope all notification and integration operations to the company identified by the X-Company-Id header.
7. IF the TrainingTask update fails (record not found or database error), THEN THE Impact_Analysis_Engine SHALL record the failure in the Impact_Report metadata as a "training_reset_failure" warning and continue processing remaining notifications, ensuring the analysis job does not fail due to a training integration issue.
8. THE Impact_Analysis_Engine SHALL NOT create duplicate notifications: if an unacknowledged notification already exists for the same affected_document_uuid and report_id combination, THE Impact_Analysis_Engine SHALL skip creating a new notification for that item.

### Requirement 9: Database Models for Change Impact Analysis

**User Story:** As a backend developer, I want well-defined database models for dependency graphs, impact reports, gap findings, and notifications, so that all change impact analysis data is properly structured, auditable, and queryable.

#### Acceptance Criteria

1. THE Impact_Analysis_Engine SHALL define a DependencyEdge model with columns: id (primary key), source_document_uuid (String(12), indexed), target_document_uuid (String(12), indexed), dependency_type (String(50)), confidence_score (Float, range 0.0 to 1.0), detected_references (JSONB, array of reference identifiers, maximum 500 entries), last_verified_at (DateTime with timezone), company_id (ForeignKey to companies.id), created_at (DateTime with timezone, server default now()), and updated_at (DateTime with timezone, nullable). A unique constraint SHALL exist on (source_document_uuid, target_document_uuid, dependency_type, company_id).
2. THE Impact_Analysis_Engine SHALL define an ImpactReport model with columns: id (primary key), report_id (UUID, unique, indexed), triggering_document_uuid (String(12), indexed), triggering_version_id (Integer, ForeignKey to document_versions.id), change_delta_summary (JSONB), affected_items (JSONB, array of Affected_Item structures), gap_findings (JSONB, array of Gap_Finding structures), status (String(20), constrained to: "completed", "partial_success", "failed"), analysis_timestamp (DateTime with timezone), analysis_duration_ms (Integer), agent_archetype_used (String(100)), model_used (String(100)), total_token_count (Integer), requesting_user_id (Integer, ForeignKey to users.id, nullable for system triggers), company_id (ForeignKey to companies.id), and created_at (DateTime with timezone, server default now()). The ImpactReport model SHALL use the immutability event listeners (before_update and before_delete) to prevent UPDATE and DELETE operations, raising ImmutableRecordError on any attempted mutation.
3. THE Impact_Analysis_Engine SHALL define an ImpactNotification model with columns: id (primary key), report_id (UUID, indexed), affected_document_uuid (String(12), indexed), notification_type (String(50), constrained to: "change_impact"), impact_severity (String(20), constrained to: "critical", "major", "minor", "unknown"), change_summary (Text, maximum 2000 characters), target_user_id (Integer, ForeignKey to users.id, indexed), is_acknowledged (Boolean, default false), acknowledged_at (DateTime with timezone, nullable), acknowledged_by (Integer, ForeignKey to users.id, nullable), company_id (ForeignKey to companies.id), and created_at (DateTime with timezone, server default now()). A unique constraint SHALL exist on (report_id, affected_document_uuid, target_user_id).
4. THE Impact_Analysis_Engine SHALL define a GapAnalysisResult model with columns: id (primary key), job_id (String(100), indexed), source_document_uuid (String(12)), target_document_uuid (String(12)), gap_findings (JSONB, array of Gap_Finding structures), total_gaps_detected (Integer), gaps_retained (Integer), status (String(20), constrained to: "completed", "partial_success", "failed"), analysis_duration_ms (Integer), company_id (ForeignKey to companies.id), and created_at (DateTime with timezone, server default now()). The GapAnalysisResult model SHALL use the immutability event listeners to prevent UPDATE and DELETE operations, as gap analysis results are append-only audit records.
5. THE Impact_Analysis_Engine SHALL apply the AuditMixin to DependencyEdge and ImpactNotification models, enabling SQLAlchemy-Continuum versioning for change tracking on mutable records.
6. THE Impact_Analysis_Engine SHALL create appropriate database indexes: composite index on (company_id, source_document_uuid) for DependencyEdge, composite index on (company_id, triggering_document_uuid) for ImpactReport, and composite index on (target_user_id, is_acknowledged) for ImpactNotification.
7. THE Impact_Analysis_Engine SHALL generate an Alembic migration for all new models, ensuring the migration is reversible: the upgrade function SHALL create all tables, indexes, and constraints; the downgrade function SHALL drop all tables created by this migration in reverse dependency order (ImpactNotification, GapAnalysisResult, ImpactReport, DependencyEdge) along with their associated indexes and constraints.

### Requirement 10: Frontend Impact Analysis Dashboard

**User Story:** As a document controller, I want a visual dashboard showing change impact analysis results, dependency graphs, and outstanding notifications, so that I can efficiently manage document change control across the repository.

#### Acceptance Criteria

1. THE Impact_Analysis_Engine SHALL provide a frontend page at route /impact-analysis that displays: a summary card showing total unresolved critical and major findings across all documents, a paginated list of Impact_Reports sorted by date (newest first) showing 20 reports per page, and a notification badge showing unacknowledged notification count. The page SHALL fetch summary data from GET /api/impact-analysis/reports and notification count from GET /api/impact-analysis/notifications.
2. THE Impact_Analysis_Engine SHALL provide a document-level impact view accessible from the existing document detail page, showing: the document's position in the Dependency_Graph (upstream and downstream dependencies) fetched from GET /api/impact-analysis/dependency-graph/{document_uuid}, the latest Impact_Report for that document, and any outstanding Gap_Findings where the document is the target.
3. THE Impact_Analysis_Engine SHALL provide a visual dependency graph component that renders documents as nodes and dependency relationships as directed edges, using color coding for Impact_Severity (red for critical, orange for major, yellow for minor, green for no outstanding findings). The graph SHALL support filtering by dependency_type and zooming/panning for graphs exceeding 20 nodes. The graph SHALL render a maximum of 200 nodes at once; if the dataset exceeds 200 nodes, the component SHALL display a message indicating the graph is truncated and prompt the user to apply filters.
4. THE Impact_Analysis_Engine SHALL provide a gap analysis detail view that displays Gap_Findings as a side-by-side comparison: source document section on the left, target document section on the right, with highlighted misalignments and the AI-generated remediation suggestion below each finding.
5. THE Impact_Analysis_Engine SHALL provide a notification panel accessible from the main navigation that lists unacknowledged impact notifications with: affected document title, impact severity badge, change summary, and an "Acknowledge" button that calls POST /api/impact-analysis/notifications/{notification_id}/acknowledge with the X-Change-Reason header.
6. THE Impact_Analysis_Engine SHALL provide a "Trigger Analysis" button on the document detail page that calls POST /api/impact-analysis/trigger with the X-Change-Reason header. WHEN the trigger returns HTTP 202, THE Impact_Analysis_Engine SHALL poll the job status endpoint (GET /api/impact-analysis/jobs/{job_id}/status) every 5 seconds, displaying a progress indicator showing current_phase and progress_percent, and automatically refreshing the impact results upon job completion or partial_success.
7. THE Impact_Analysis_Engine SHALL use Zustand for state management of impact analysis data (reports, notifications, dependency graph) and integrate with the existing apiClient for all API calls, including the required X-Change-Reason header on mutation endpoints (acknowledge, trigger).
8. THE Impact_Analysis_Engine SHALL display a loading skeleton while impact analysis data is being fetched and show empty states when no reports, findings, or notifications exist for the current scope. Empty states SHALL display a descriptive message indicating no data is available (e.g., "No impact reports found" for reports, "No outstanding notifications" for notifications, "No dependencies mapped" for the dependency graph) and, where applicable, a call-to-action directing the user to trigger an analysis or build the dependency graph.
9. IF an API call to any impact analysis endpoint fails (network error or HTTP 4xx/5xx response), THEN THE Impact_Analysis_Engine SHALL display an inline error message identifying the failed operation and provide a "Retry" button that re-attempts the failed request. The error message SHALL replace the loading skeleton for the affected section without disrupting other successfully loaded sections on the page.
10. IF the manual trigger endpoint returns HTTP 409 (concurrent analysis already running), THEN THE Impact_Analysis_Engine SHALL display a message indicating an analysis is already in progress for this document and begin polling the existing job_id returned in the 409 response.
