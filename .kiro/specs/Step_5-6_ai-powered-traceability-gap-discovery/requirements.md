# Requirements Document

## Introduction

This feature implements AI-Powered Traceability & Gap Discovery (Phase 5.6) for the AlcoaBase Document & Knowledge Management System. It provides automated generation of Traceability Matrices by using AI to crawl requirements documents (URS) and map them to test cases and validation results in other documents (IQ, OQ, PQ, MVP). It also detects orphan requirements (requirements without corresponding test cases) and orphan test cases (tests without justifying requirements).

The feature leverages the existing AI/RAG infrastructure (Phase 4.2-4.3), the Agent Registry (Phase 5.1) for a specialized "Traceability Analyst" agent archetype, the Cross-Reference service (Phase 5.4) for document relationship detection, and the Change Impact Analysis (Phase 5.5) for integration when requirements change. Traceability matrix generation runs as an async Celery task, producing structured matrices that serve as immutable audit records and feed into Phase 7.2's formal traceability export for FDA/EMA submissions.

## Glossary

- **Traceability_Engine**: The AI service that orchestrates traceability matrix generation by extracting requirements from source documents, identifying corresponding test cases and validation results in target documents, establishing requirement-to-test links, computing coverage metrics, and detecting orphan items.
- **Traceability_Matrix**: A structured mapping between requirements (from URS documents) and their corresponding test cases, validation results, and verification evidence (from IQ, OQ, PQ, MVP documents). Each matrix is an immutable audit record containing: source document references, target document references, individual traceability links, coverage metrics, and orphan item lists.
- **Traceability_Link**: A single mapping between one requirement and one or more test cases or validation results, containing: requirement_id (extracted identifier from the source document), requirement_text (first 500 characters), target_document_uuid, target_section, test_case_id (extracted identifier from the target document), test_case_text (first 500 characters), link_confidence (0.0 to 1.0), link_method ("exact_id_match", "semantic_match", "cross_reference"), and verification_status ("verified", "unverified", "failed").
- **Orphan_Requirement**: A requirement identified in a source document (URS) that has no corresponding test case or validation result in any target document within the company scope. Represents a gap in test coverage that may indicate regulatory non-compliance.
- **Orphan_Test_Case**: A test case identified in a target document (IQ, OQ, PQ) that does not trace back to any requirement in any source document within the company scope. Represents a test without justification that may indicate scope creep or documentation drift.
- **Coverage_Metric**: A quantitative measure of traceability completeness, including: total_requirements (count of requirements extracted from source documents), covered_requirements (count of requirements with at least one Traceability_Link), orphan_requirements (count of requirements with no links), coverage_percentage (covered_requirements / total_requirements * 100), total_test_cases (count of test cases in target documents), orphan_test_cases (count of test cases with no requirement link), and compliance_readiness_score (weighted score combining coverage percentage, orphan counts, and link confidence averages).
- **Coverage_Snapshot**: A point-in-time record of Coverage_Metrics for a specific set of documents, persisted as an immutable audit record for trend analysis and compliance reporting.
- **Traceability_Analyst**: A specialized AI agent archetype (registered in the Agent Registry 5.1) configured for requirement extraction, test case identification, and semantic matching between requirements and test cases, with system prompts tuned for regulatory document traceability in GxP environments.
- **Source_Document**: A document containing requirements to be traced (typically URS, Functional Specification, or Design Specification documents). Identified by document type classification or user designation.
- **Target_Document**: A document containing test cases, validation results, or verification evidence that should map back to requirements (typically IQ, OQ, PQ, MVP, or Validation Protocol documents). Identified by document type classification or user designation.
- **InferenceClient**: The existing async HTTP client for vLLM communication (from 4.3).
- **KnowledgeService**: The existing RAG service for document retrieval, text extraction, and semantic search (from 4.2).
- **CrossReferenceService**: The existing service (from 5.4) that extracts and manages cross-references between documents.
- **JobTracker**: The existing async job tracking service for Celery task progress reporting.
- **Impact_Analysis_Engine**: The existing change impact analysis service (from 5.5) that detects document dependencies and produces impact reports.

## Requirements

### Requirement 1: Automated Traceability Matrix Generation

**User Story:** As a quality manager, I want the system to automatically crawl requirements in URS documents and map them to test cases in IQ/OQ/PQ/MVP documents, so that I can generate a complete Traceability Matrix without manual effort.

#### Acceptance Criteria

1. THE Traceability_Engine SHALL expose a POST /api/traceability/matrices/generate endpoint that accepts {source_document_ids (array of document IDs containing requirements), target_document_ids (array of document IDs containing test cases), matrix_name (string, 1-200 characters), description (optional string, maximum 1000 characters)} and returns HTTP 202 with a job_id for the async matrix generation task. This endpoint SHALL require the X-Change-Reason header.
2. WHEN a matrix generation job executes, THE Traceability_Engine SHALL: (a) extract all identifiable requirements from each Source_Document using the Traceability_Analyst agent (identifying requirement IDs, requirement text, section headings, and acceptance criteria), (b) extract all identifiable test cases from each Target_Document (identifying test case IDs, test descriptions, expected results, and section headings), (c) establish Traceability_Links between requirements and test cases using a three-pass matching strategy: first by exact ID cross-reference (e.g., "REQ-001" referenced in a test case), second by explicit document cross-references detected via CrossReferenceService, and third by semantic similarity via KnowledgeService embedding comparison.
3. THE Traceability_Engine SHALL assign link_confidence values based on the matching method: 1.0 for exact ID matches (requirement ID explicitly cited in the test case text), 0.9 for cross-reference matches (CrossReferenceService detects a structural link between the documents), and for semantic matches the link_confidence SHALL equal the embedding similarity score returned by KnowledgeService (resulting in values between 0.5 and 1.0, since matches below 0.5 are discarded). THE Traceability_Engine SHALL NOT create Traceability_Links for semantic matches where the embedding similarity score is below 0.5.
4. THE Traceability_Engine SHALL validate the generation request: IF source_document_ids is empty or target_document_ids is empty, THEN THE Traceability_Engine SHALL return HTTP 422 with an error message indicating both source and target documents are required. IF any document ID in source_document_ids or target_document_ids does not correspond to an existing document within the company scope, THEN THE Traceability_Engine SHALL return HTTP 404 identifying the missing document IDs. IF any document ID appears in both source_document_ids and target_document_ids, THEN THE Traceability_Engine SHALL return HTTP 422 indicating a document cannot be both source and target.
5. THE Traceability_Engine SHALL limit matrix generation to a maximum of 10 source documents and 20 target documents per request. IF either limit is exceeded, THEN THE Traceability_Engine SHALL return HTTP 422 with an error message indicating the maximum document counts.
6. THE Traceability_Engine SHALL complete a matrix generation job within 600 seconds. IF the generation exceeds this timeout, THEN THE Traceability_Engine SHALL persist all Traceability_Links discovered so far, mark the job as "partial_success" with a list of unprocessed source requirements, and record the last processed requirement for context.
7. THE Traceability_Engine SHALL deduplicate Traceability_Links: if the same requirement maps to the same test case via multiple methods, THE Traceability_Engine SHALL retain only the link with the highest confidence score and record all detection methods in a link_methods array.
8. THE Traceability_Engine SHALL scope all matrix generation operations to the company identified by the X-Company-Id header.
9. IF a matrix generation job with status "processing" already exists for the same combination of source_document_ids and target_document_ids within the same company, THEN THE Traceability_Engine SHALL return HTTP 409 with the existing job_id.
10. IF the Traceability_Analyst agent (InferenceClient) is unavailable during requirement extraction or test case identification (connection timeout after 30 seconds, HTTP 503, or HTTP 429 after 3 retries with exponential backoff), THEN THE Traceability_Engine SHALL mark the job as "failed" with an error message indicating inference service unavailability and the phase at which failure occurred.
11. IF the KnowledgeService is unavailable during semantic matching (connection timeout after 30 seconds or HTTP 503 after 3 retries with exponential backoff), THEN THE Traceability_Engine SHALL complete the matrix using only exact ID and cross-reference matches (passes 1 and 2), mark the job as "partial_success", and record that semantic matching was skipped due to KnowledgeService unavailability. IF the CrossReferenceService is unavailable during cross-reference matching (connection timeout after 30 seconds or HTTP 503 after 3 retries with exponential backoff), THEN THE Traceability_Engine SHALL complete the matrix using only exact ID and semantic matches (passes 1 and 3), mark the job as "partial_success", and record that cross-reference matching was skipped due to CrossReferenceService unavailability.
12. WHEN a matrix generation job completes with status "completed", THE Traceability_Engine SHALL identify all requirements from source documents that have zero Traceability_Links and include them in an uncovered_requirements list within the matrix output, enabling the quality manager to identify gaps in test coverage.

### Requirement 2: Orphan Requirement Detection

**User Story:** As a regulatory affairs specialist, I want the system to flag any requirement in a URS that does not have a corresponding test case or validation result anywhere in the system, so that I can identify gaps in test coverage before an audit.

#### Acceptance Criteria

1. WHEN a matrix generation job completes, THE Traceability_Engine SHALL identify all Orphan_Requirements by comparing the extracted requirements list against the established Traceability_Links. A requirement SHALL be classified as orphan if it has zero Traceability_Links with link_confidence >= 0.5.
2. WHEN orphan requirements have been identified, THE Traceability_Engine SHALL produce a structured list of Orphan_Requirements, each containing: requirement_id (extracted identifier), requirement_text (first 500 characters), source_document_uuid, source_section (heading and paragraph index), severity ("critical", "major", or "minor"), and suggested_action ("create_test_case", "review_requirement", or "link_existing_test").
3. THE Traceability_Engine SHALL expose a GET /api/traceability/matrices/{matrix_id}/orphan-requirements endpoint that returns the list of Orphan_Requirements for a specific matrix, with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters, and filterable by severity and source_document_uuid query parameters. The response SHALL include a total_count field.
4. WHEN orphan requirements are identified, THE Traceability_Engine SHALL classify orphan requirement severity using the Traceability_Analyst agent by analyzing the requirement text against keyword categories in the following precedence order (highest to lowest): "critical" if the requirement contains safety-critical keywords (hazard, safety, sterility, biocompatibility, alarm, interlock) or regulatory-mandatory keywords (shall comply, regulatory requirement, FDA, EMA, ISO); "major" if the requirement contains functional keywords (shall perform, shall calculate, shall display); "minor" if the requirement contains only informational keywords (should, may, nice-to-have, optional). IF a requirement matches multiple categories, THEN the highest-precedence severity SHALL be assigned.
5. IF the Traceability_Analyst agent does not respond within 30 seconds or returns an error during orphan severity classification, THEN THE Traceability_Engine SHALL assign a default severity of "major" to all unclassified orphan requirements and record the classification failure in the matrix metadata.
6. THE Traceability_Engine SHALL scope all orphan requirement queries to the company identified by the X-Company-Id header.
7. IF the X-Company-Id header is missing or references a company the authenticated user does not belong to, THEN THE Traceability_Engine SHALL reject the orphan requirements request with an error response indicating insufficient authorization and SHALL NOT return any orphan requirement data.

### Requirement 3: Orphan Test Case Detection

**User Story:** As a validation engineer, I want the system to flag test cases that do not trace back to any requirement, so that I can identify tests without justification and ensure all testing effort is requirement-driven.

#### Acceptance Criteria

1. WHEN a matrix generation job completes, THE Traceability_Engine SHALL identify all Orphan_Test_Cases by comparing the extracted test cases list against the established Traceability_Links. A test case SHALL be classified as orphan if it has zero Traceability_Links with link_confidence >= 0.5 connecting it to any requirement.
2. WHEN orphan test cases have been identified, THE Traceability_Engine SHALL produce a structured list of Orphan_Test_Cases, each containing: test_case_id (extracted identifier), test_case_text (first 500 characters), target_document_uuid, target_section (heading and paragraph index), risk_level ("high" if the test case involves safety-critical validation, "medium" for functional tests, "low" for cosmetic or informational checks), and suggested_action determined by the Traceability_Analyst agent as one of: "link_to_requirement" (when a plausible requirement match exists with link_confidence between 0.3 and 0.49), "create_requirement" (when no plausible match exists and the test validates observable system behavior), or "remove_test_case" (when the test is redundant or duplicates another linked test case).
3. THE Traceability_Engine SHALL expose a GET /api/traceability/matrices/{matrix_id}/orphan-test-cases endpoint that returns the list of Orphan_Test_Cases for a specific matrix, with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters, and filterable by risk_level and target_document_uuid query parameters. The response SHALL include a total_count field and results SHALL be ordered by risk_level descending (high, medium, low) then by test_case_id ascending.
4. WHEN orphan test cases are identified, THE Traceability_Engine SHALL classify orphan test case risk_level using the Traceability_Analyst agent by analyzing the test case text for: safety-critical indicators (validates safety function, alarm verification, interlock test), functional indicators (verifies calculation, confirms workflow, validates data entry), and informational indicators (checks display format, verifies label text, cosmetic verification).
5. IF the Traceability_Analyst agent does not respond within 30 seconds or returns an error response during orphan test case classification, THEN THE Traceability_Engine SHALL assign a default risk_level of "medium" and a default suggested_action of "link_to_requirement" to all unclassified orphan test cases and record the classification failure in the matrix metadata.
6. THE Traceability_Engine SHALL scope all orphan test case queries to the company identified by the X-Company-Id header.
7. IF the matrix_id provided to the GET /api/traceability/matrices/{matrix_id}/orphan-test-cases endpoint does not correspond to an existing matrix within the requesting company's scope, THEN THE Traceability_Engine SHALL return HTTP 404 with an error message indicating the matrix was not found.

### Requirement 4: Traceability Matrix Persistence and Versioning

**User Story:** As a quality auditor, I want every generated Traceability Matrix stored as an immutable audit record with full versioning, so that I can demonstrate regulatory compliance and trace the evolution of requirement coverage over time.

#### Acceptance Criteria

1. THE Traceability_Engine SHALL persist each completed Traceability_Matrix as an immutable record in the database containing: matrix_id (UUID, unique), matrix_name, description, source_document_uuids (array), target_document_uuids (array), source_document_versions (array of {document_uuid, version_id} pairs capturing the exact versions analyzed), target_document_versions (array of {document_uuid, version_id} pairs), traceability_links (JSONB array of Traceability_Link structures), orphan_requirements (JSONB array of Orphan_Requirement structures), orphan_test_cases (JSONB array of Orphan_Test_Case structures), coverage_metrics (JSONB Coverage_Metric structure), status ("completed", "partial_success", "failed"), generation_timestamp, generation_duration_ms, agent_archetype_used, model_used, total_token_count, requesting_user_id, and company_id.
2. THE Traceability_Engine SHALL enforce immutability on Traceability_Matrix records: no UPDATE or DELETE operations SHALL be permitted. The model SHALL use before_update and before_delete event listeners to raise ImmutableRecordError on any attempted mutation. Matrices SHALL be retained indefinitely regardless of whether source or target documents are later deleted or superseded.
3. WHEN a new matrix is generated for a document set whose sorted source_document_uuids and sorted target_document_uuids both match those of an existing matrix within the same company, THE Traceability_Engine SHALL create a new matrix record (new matrix_id) rather than updating the existing one, enabling version comparison between successive generations. THE Traceability_Engine SHALL record a parent_matrix_id field referencing the most recent previous matrix for that matching document set (null if this is the first generation for that set).
4. THE Traceability_Engine SHALL capture the exact document versions analyzed at generation time by recording the current version_id for each source and target document. This ensures the matrix remains a faithful record even if documents are subsequently updated.
5. THE Traceability_Engine SHALL scope all matrix persistence operations to the company identified by the X-Company-Id header. IF the X-Company-Id header is missing or references a company for which the requesting user has no active membership, THEN THE Traceability_Engine SHALL reject the request without persisting any data.
6. IF the Traceability_Matrix record cannot be persisted during a generation job (database write failure after up to 3 retry attempts with exponential backoff), THEN THE Traceability_Engine SHALL mark the job status as "failed" via the JobTracker with an error_message indicating the persistence failure, and SHALL NOT leave partially written matrix data in the database.

### Requirement 5: Traceability Matrix API

**User Story:** As a frontend developer, I want well-defined API endpoints for retrieving traceability matrices, querying coverage status, and browsing individual traceability links, so that I can build a comprehensive traceability dashboard.

#### Acceptance Criteria

1. THE Traceability_Engine SHALL expose a GET /api/traceability/matrices endpoint that returns all Traceability_Matrices for the current company, sorted by generation_timestamp descending (newest first), filterable by source_document_uuid (returns matrices containing the specified document as a source), target_document_uuid, status, and date_range (ISO 8601 start_date and end_date query parameters), with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters. The response SHALL include a total_count field indicating the total number of matching matrices before pagination. IF the offset value exceeds total_count, THEN THE Traceability_Engine SHALL return an empty results array with the accurate total_count.
2. THE Traceability_Engine SHALL expose a GET /api/traceability/matrices/{matrix_id} endpoint that returns the full Traceability_Matrix including all traceability links, orphan requirements, orphan test cases, and coverage metrics. IF the matrix_id parameter is not a valid UUID format, THEN THE Traceability_Engine SHALL return HTTP 422 with an error message indicating invalid matrix_id format. IF the matrix_id does not exist or does not belong to the company identified by the X-Company-Id header, THEN THE Traceability_Engine SHALL return HTTP 404.
3. THE Traceability_Engine SHALL expose a GET /api/traceability/matrices/{matrix_id}/links endpoint that returns the Traceability_Links for a specific matrix, with pagination via limit (default 50, maximum 200) and offset (default 0) query parameters, and filterable by source_document_uuid, target_document_uuid, link_confidence_min (float between 0.0 and 1.0 inclusive, returns links with confidence >= specified value), and link_method query parameters. The response SHALL include a total_count field. IF the matrix_id parameter is not a valid UUID format, THEN THE Traceability_Engine SHALL return HTTP 422 with an error message indicating invalid matrix_id format. IF the matrix_id does not exist or does not belong to the company, THEN THE Traceability_Engine SHALL return HTTP 404. IF link_confidence_min is outside the range 0.0 to 1.0, THEN THE Traceability_Engine SHALL return HTTP 422 with an error message indicating the valid range.
4. THE Traceability_Engine SHALL expose a GET /api/traceability/documents/{document_uuid}/coverage endpoint that returns the latest coverage status for a specific document across all matrices where it appears as a source: latest_matrix_id, latest_matrix_date, coverage_percentage (float between 0.0 and 100.0 representing the percentage of requirements with at least one traceability link), orphan_requirement_count, total_requirements, and compliance_readiness_score (float between 0.0 and 100.0 representing the weighted combination of coverage_percentage and link confidence levels, or null if no matrix exists). IF the document has never been included in a matrix as a source, THEN THE Traceability_Engine SHALL return coverage_percentage as null, orphan_requirement_count as 0, total_requirements as 0, and compliance_readiness_score as null. IF the document_uuid parameter is not a valid UUID format, THEN THE Traceability_Engine SHALL return HTTP 422 with an error message indicating invalid document_uuid format.
5. THE Traceability_Engine SHALL expose a DELETE /api/traceability/matrices/{matrix_id} endpoint that performs a soft-delete by setting a deleted_at timestamp on the matrix record, removing it from list queries but preserving the immutable audit record. This endpoint SHALL require the X-Change-Reason header and return HTTP 204 on success. IF the matrix_id parameter is not a valid UUID format, THEN THE Traceability_Engine SHALL return HTTP 422 with an error message indicating invalid matrix_id format. IF the matrix_id does not exist, does not belong to the company, or has already been soft-deleted, THEN THE Traceability_Engine SHALL return HTTP 404.
6. THE Traceability_Engine SHALL scope all API queries to the company identified by the X-Company-Id header.

### Requirement 6: Traceability Analyst Agent Configuration

**User Story:** As a system administrator, I want a specialized AI agent archetype configured for requirement-to-test mapping and traceability analysis, so that the system uses appropriate prompts and parameters for extracting requirements, identifying test cases, and establishing semantic links between them.

#### Acceptance Criteria

1. THE Traceability_Engine SHALL register a "Traceability Analyst" agent archetype in the Agent Registry (5.1) with agent_type "review", temperature 0.15, max_tokens 4096, and an evaluation rubric with scoring_method "weighted_average", criteria [accuracy of requirement extraction (weight 0.25), accuracy of test case identification (weight 0.25), correctness of link establishment (weight 0.30), completeness of orphan detection (weight 0.20)], and severity_thresholds (critical: 0.9, major: 0.7, minor: 0.4, informational: 0.2).
2. THE Traceability_Analyst agent SHALL be configured with a system prompt that instructs the model to: extract individual requirements from regulatory documents by identifying requirement IDs (patterns like REQ-NNN, URS-NNN, R.N.N), requirement text, and acceptance criteria; extract individual test cases from validation documents by identifying test case IDs (patterns like TC-NNN, IQ-NNN, OQ-NNN, PQ-NNN), test descriptions, and expected results; establish links between requirements and test cases based on ID cross-references, semantic similarity with a minimum confidence score of 0.75 for link acceptance, and structural document relationships; classify orphan severity based on safety-critical and regulatory-mandatory keyword analysis; and reject candidate links that fall below the 0.75 confidence threshold to avoid false positives.
3. THE Traceability_Analyst agent SHALL be defined as a YAML file named "traceability-analyst.yaml" in the agents/archetypes/ directory following the agent-definition-v2.json schema (including required fields: schema_version "2.0", agent_type "review", dspy_modules with at least one ChainOfThought module for requirement extraction and one for link establishment, knowledge_scopes with tags relevant to traceability analysis, target_document_tag, required_chapters, compliance_checklist, and severity_rules as mandated by the schema for review-type agents), enabling hot-reload via the agent file watcher without code changes.
4. THE Traceability_Engine SHALL use the Traceability_Analyst agent exclusively for requirement extraction, test case identification, and semantic link confidence scoring, passing document context through the InferenceClient with the agent's configured temperature (0.15) and max_tokens (4096) parameters.
5. IF the Traceability_Analyst agent archetype is not found in the Agent Registry at analysis time, THEN THE Traceability_Engine SHALL fall back to the existing "Change Impact Analyst" archetype with a system prompt suffix appended that instructs the model to focus on requirement-to-test traceability mapping rather than change impact assessment, and SHALL record the fallback event in the job metadata under a "fallback_used" field.
6. IF the Traceability_Analyst YAML file fails schema validation against agent-definition-v2.json during loading, THEN THE Traceability_Engine SHALL reject the file, log a validation error identifying the failing field, and retain the previously loaded valid configuration until a corrected file is provided.
7. IF the InferenceClient call using the Traceability_Analyst agent does not return a response within 120 seconds, THEN THE Traceability_Engine SHALL abort the pending inference request, record a timeout event in the job metadata, and return an error indication to the caller identifying which analysis step (requirement extraction, test case identification, or link scoring) timed out.

### Requirement 7: Coverage Metrics and Compliance Readiness Scoring

**User Story:** As a compliance officer, I want the system to calculate and expose coverage percentages, gap counts, and compliance readiness scores, so that I can quickly assess whether a document set is ready for regulatory submission.

#### Acceptance Criteria

1. WHEN a matrix generation job completes, THE Traceability_Engine SHALL compute Coverage_Metrics containing: total_requirements (count of all requirements extracted from source documents), covered_requirements (count of requirements with at least one Traceability_Link with link_confidence >= 0.5), orphan_requirements_count (total_requirements - covered_requirements), coverage_percentage (covered_requirements / total_requirements * 100, rounded to two decimal places), total_test_cases (count of all test cases extracted from target documents), linked_test_cases (count of test cases with at least one Traceability_Link), orphan_test_cases_count (total_test_cases - linked_test_cases), average_link_confidence (mean of all link_confidence values across established links, rounded to two decimal places; 0.00 if no links exist), and compliance_readiness_score (computed per criterion 2).
2. THE Traceability_Engine SHALL compute the compliance_readiness_score as a weighted composite: (coverage_percentage * 0.40) + (link_quality_score * 0.25) + (orphan_penalty * 0.20) + (completeness_score * 0.15), where link_quality_score is (average_link_confidence * 100), orphan_penalty is max(0, 100 - (orphan_requirements_count * 5) - (orphan_test_cases_count * 3)), and completeness_score is 100 if all source documents had at least one requirement extracted and all target documents had at least one test case extracted, otherwise (documents_with_extractions / total_documents * 100). The final score SHALL be clamped to the range 0.0 to 100.0. IF total_requirements is zero, THEN coverage_percentage SHALL be 0.00 and compliance_readiness_score SHALL be 0.0.
3. THE Traceability_Engine SHALL expose a GET /api/traceability/coverage/summary endpoint that returns an aggregated coverage summary across all non-deleted matrices for the current company: total_matrices_generated, latest_matrix_date, average_coverage_percentage (across all completed matrices, rounded to two decimal places), total_orphan_requirements (across latest matrix per source document), total_orphan_test_cases, average_compliance_readiness_score (rounded to two decimal places), and a breakdown by source document (limited to the 200 most recently updated documents, sorted by document name ascending) showing per-document coverage_percentage and orphan_count. IF no matrices exist for the company, THEN THE Traceability_Engine SHALL return a response with total_matrices_generated set to 0, all numeric aggregates set to 0.00, and an empty breakdown list.
4. THE Traceability_Engine SHALL expose a GET /api/traceability/coverage/history endpoint that returns Coverage_Snapshots over time for the current company, sorted by snapshot_date descending, with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters, filterable by source_document_uuid and date_range (ISO 8601 start_date and end_date). Each snapshot SHALL contain: snapshot_date, matrix_id, coverage_percentage, orphan_requirements_count, orphan_test_cases_count, and compliance_readiness_score. IF source_document_uuid does not exist or belongs to a different company, THEN THE Traceability_Engine SHALL return an empty results list with total_count of 0.
5. WHEN a matrix generation job completes with status "completed" or "partial_success", THE Traceability_Engine SHALL persist a Coverage_Snapshot record containing the computed Coverage_Metrics and a timestamp, enabling historical trend analysis without requiring re-computation from matrix data.
6. IF the X-Company-Id header is missing or references a company the requesting user does not belong to, THEN THE Traceability_Engine SHALL reject the coverage metric request with an error response indicating the company context is invalid or unauthorized.
7. THE Traceability_Engine SHALL scope all coverage metric queries to the company identified by the X-Company-Id header.

### Requirement 8: Frontend Traceability Dashboard

**User Story:** As a document controller, I want a visual dashboard showing traceability matrices, coverage heatmaps, orphan alerts, and drill-down to specific requirement-test links, so that I can efficiently manage traceability compliance across the document repository.

#### Acceptance Criteria

1. THE Traceability_Engine SHALL provide a frontend page at route /traceability that displays: a summary card showing overall coverage percentage (0-100%, rounded to one decimal place) and compliance readiness score (0-100 scale), a count of total orphan requirements and orphan test cases across the latest matrices, a paginated list of Traceability_Matrices sorted by date (newest first) showing 20 matrices per page, and a "Generate Matrix" button. The page SHALL fetch data from GET /api/traceability/matrices and GET /api/traceability/coverage/summary.
2. THE Traceability_Engine SHALL provide a matrix detail view at route /traceability/matrices/{matrix_id} that displays: a tabular view of all Traceability_Links with columns for requirement_id, requirement_text (truncated to 100 characters with tooltip for full text), target_document, test_case_id, test_case_text (truncated to 100 characters with tooltip for full text), link_confidence (displayed as a percentage badge with color coding: green >= 0.8, yellow >= 0.5, red < 0.5), and link_method. The table SHALL support sorting by any column and filtering by link_confidence_min.
3. THE Traceability_Engine SHALL provide a coverage heatmap component that visualizes requirement coverage as a grid: rows represent source documents, columns represent target documents, and cells display the coverage percentage for that document pair with color intensity (dark green for 100%, graduating through yellow at 50% to red for 0%). Hovering over a cell SHALL display a tooltip with the exact coverage percentage and orphan count for that pair.
4. THE Traceability_Engine SHALL provide an orphan alerts panel within the matrix detail view that displays two tabs: "Orphan Requirements" showing the list from GET /api/traceability/matrices/{matrix_id}/orphan-requirements with severity badges (red for critical, orange for major, yellow for minor), and "Orphan Test Cases" showing the list from GET /api/traceability/matrices/{matrix_id}/orphan-test-cases with risk_level badges. Each orphan item SHALL display its suggested_action as an actionable chip.
5. THE Traceability_Engine SHALL provide a "Generate Matrix" dialog triggered by the button on the traceability page, containing: a multi-select document picker for source documents (filtered to show URS/specification-type documents, maximum 50 selections), a multi-select document picker for target documents (filtered to show IQ/OQ/PQ/MVP-type documents, maximum 50 selections), a matrix_name text input (required, 1-150 characters), and an optional description textarea (maximum 500 characters). Submitting the dialog SHALL call POST /api/traceability/matrices/generate with the X-Change-Reason header. The submit button SHALL be disabled until at least one source document, one target document, and a valid matrix_name are provided.
6. WHEN the generate endpoint returns HTTP 202, THE Traceability_Engine SHALL poll the job status endpoint (GET /api/traceability/jobs/{job_id}/status) every 5 seconds for a maximum of 10 minutes, displaying a progress indicator showing current_phase and progress_percent, and automatically navigating to the matrix detail view upon job completion or partial_success.
7. IF the job status returns a failed state or polling exceeds 10 minutes without completion, THEN THE Traceability_Engine SHALL stop polling, display an error message indicating the generation failed or timed out, and provide a "Retry" button that re-opens the Generate Matrix dialog with the previously entered values preserved.
8. THE Traceability_Engine SHALL provide a coverage trend chart component on the traceability page that displays coverage_percentage over time as a line chart, fetched from GET /api/traceability/coverage/history. The chart SHALL support filtering by source_document_uuid and display the compliance_readiness_score as a secondary axis.
9. THE Traceability_Engine SHALL use Zustand for state management of traceability data (matrices, coverage metrics, orphan lists) and integrate with the existing apiClient for all API calls, including the required X-Change-Reason header on mutation endpoints.
10. THE Traceability_Engine SHALL display a loading skeleton while traceability data is being fetched and show empty states when no matrices, findings, or coverage data exist. Empty states SHALL display a descriptive message indicating no data is available for the specific section and a call-to-action button directing the user to generate their first matrix.
11. IF an API call to any traceability endpoint fails (network error or HTTP 4xx/5xx response), THEN THE Traceability_Engine SHALL display an inline error message identifying the failed operation and provide a "Retry" button that re-attempts the failed request. The error message SHALL replace the loading skeleton for the affected section without disrupting other successfully loaded sections.
12. IF the generate endpoint returns HTTP 409 (concurrent generation already running), THEN THE Traceability_Engine SHALL display a message indicating a generation is already in progress for this document set and begin polling the existing job_id returned in the 409 response.

### Requirement 9: Integration with Change Impact Analysis (5.5)

**User Story:** As a quality manager, I want the system to automatically flag affected traceability links when a requirement changes, so that I can immediately see which test cases may need updating and which traceability links are now stale.

#### Acceptance Criteria

1. WHEN the Impact_Analysis_Engine (5.5) completes an impact analysis for a document that is a source in any existing non-deleted Traceability_Matrix, THE Traceability_Engine SHALL automatically create a traceability_impact_alert record within 30 seconds of the ImpactReport after_insert event, containing: triggering_report_id (from the impact analysis), affected_matrix_ids (list of matrix IDs where the changed document is a source), affected_link_count (number of Traceability_Links originating from the changed document across affected matrices), alert_severity ("critical" if the impact report's highest finding severity is "critical", "major" if the highest finding severity is "major", "minor" otherwise), and created_at timestamp.
2. THE Traceability_Engine SHALL expose a GET /api/traceability/alerts endpoint that returns all unresolved traceability_impact_alerts for the current company, sorted by alert_severity (critical first, then major, then minor) then by created_at (newest first), with pagination via limit (default 20, maximum 100) and offset (default 0) query parameters. The response SHALL include a total_count field indicating the total number of unresolved alerts before pagination.
3. THE Traceability_Engine SHALL expose a POST /api/traceability/alerts/{alert_id}/resolve endpoint that marks an alert as resolved, recording the resolving user_id, resolution_action ("matrix_regenerated", "links_verified", "no_action_needed"), and resolution_note (optional, maximum 500 characters). This endpoint SHALL require the X-Change-Reason header. IF the alert_id does not exist or does not belong to the requesting company, THEN THE Traceability_Engine SHALL return HTTP 404. IF the alert is already resolved, THEN THE Traceability_Engine SHALL return HTTP 409 with an error message indicating the alert has already been resolved.
4. WHEN a traceability_impact_alert is created with alert_severity "critical", THE Traceability_Engine SHALL mark all Traceability_Links originating from the changed document in the affected matrices with a stale_since timestamp (set to the alert creation time) and a stale_reason referencing the triggering_report_id. This stale marking SHALL be reflected in API responses for matrix links (criterion 3 of Requirement 5) as an additional "is_stale" boolean field and "stale_since" timestamp field.
5. THE Traceability_Engine SHALL detect impact analysis completion by subscribing to the ImpactReport model's after_insert event, checking whether the triggering_document_uuid matches any source_document_uuid in existing non-deleted Traceability_Matrices for the same company.
6. THE Traceability_Engine SHALL scope all alert operations to the company identified by the X-Company-Id header.
7. IF the alert creation fails (database write error), THE Traceability_Engine SHALL log the failure with the triggering_report_id and affected_matrix_ids but SHALL NOT cause the impact analysis job to fail, as the alert is a downstream integration and not part of the impact analysis critical path.
8. WHEN a traceability_impact_alert with alert_severity "critical" is resolved with resolution_action "links_verified" or "matrix_regenerated", THE Traceability_Engine SHALL clear the stale markings on the affected Traceability_Links by setting is_cleared to true and cleared_at to the resolution timestamp on the corresponding StaleLinkMarker records.

### Requirement 10: Database Models for Traceability

**User Story:** As a backend developer, I want well-defined database models for traceability matrices, links, coverage snapshots, and alerts, so that all traceability data is properly structured, auditable, and queryable.

#### Acceptance Criteria

1. THE Traceability_Engine SHALL define a TraceabilityMatrix model with columns: id (primary key), matrix_id (UUID, unique, indexed), matrix_name (String(200)), description (Text, nullable, maximum 1000 characters), source_document_uuids (JSONB, array of String(12)), target_document_uuids (JSONB, array of String(12)), source_document_versions (JSONB, array of {document_uuid, version_id} objects), target_document_versions (JSONB, array of {document_uuid, version_id} objects), traceability_links (JSONB, array of Traceability_Link structures), orphan_requirements (JSONB, array of Orphan_Requirement structures), orphan_test_cases (JSONB, array of Orphan_Test_Case structures), coverage_metrics (JSONB, Coverage_Metric structure), status (String(20), constrained to: "completed", "partial_success", "failed"), parent_matrix_id (UUID, nullable, ForeignKey to self), generation_timestamp (DateTime with timezone), generation_duration_ms (Integer, minimum 0), agent_archetype_used (String(100)), model_used (String(100)), total_token_count (Integer, minimum 0), requesting_user_id (Integer, ForeignKey to users.id), company_id (ForeignKey to companies.id), deleted_at (DateTime with timezone, nullable), and created_at (DateTime with timezone, server default now()). The TraceabilityMatrix model SHALL use a before_update event listener that permits UPDATE operations only on the deleted_at column (for soft-delete) and raises ImmutableRecordError on any attempted mutation of other columns. The before_delete event listener SHALL raise ImmutableRecordError on any attempted DELETE operation.
2. THE Traceability_Engine SHALL define a CoverageSnapshot model with columns: id (primary key), matrix_id (UUID, ForeignKey to TraceabilityMatrix.matrix_id, indexed), source_document_uuid (String(12), indexed), coverage_percentage (Float, valid range 0.0 to 100.0), orphan_requirements_count (Integer, minimum 0), orphan_test_cases_count (Integer, minimum 0), compliance_readiness_score (Float, valid range 0.0 to 100.0), total_requirements (Integer, minimum 0), covered_requirements (Integer, minimum 0), total_test_cases (Integer, minimum 0), linked_test_cases (Integer, minimum 0), snapshot_date (DateTime with timezone), company_id (ForeignKey to companies.id), and created_at (DateTime with timezone, server default now()). The CoverageSnapshot model SHALL use immutability event listeners (before_update and before_delete) to prevent UPDATE and DELETE operations, raising ImmutableRecordError on any attempted mutation.
3. THE Traceability_Engine SHALL define a TraceabilityAlert model with columns: id (primary key), alert_id (UUID, unique, indexed), triggering_report_id (UUID, indexed), affected_matrix_ids (JSONB, array of UUIDs), affected_link_count (Integer, minimum 0), alert_severity (String(20), constrained to: "critical", "major", "minor"), is_resolved (Boolean, default false), resolved_at (DateTime with timezone, nullable), resolved_by (Integer, ForeignKey to users.id, nullable), resolution_action (String(50), nullable, constrained to: "matrix_regenerated", "links_verified", "no_action_needed"), resolution_note (Text, nullable, maximum 500 characters), company_id (ForeignKey to companies.id), and created_at (DateTime with timezone, server default now()). A unique constraint SHALL exist on (triggering_report_id, company_id) to prevent duplicate alerts for the same impact report.
4. THE Traceability_Engine SHALL define a StaleLinkMarker model with columns: id (primary key), matrix_id (UUID, indexed), requirement_id (String(100)), stale_since (DateTime with timezone), stale_reason (Text, maximum 500 characters), triggering_report_id (UUID), is_cleared (Boolean, default false), cleared_at (DateTime with timezone, nullable), company_id (ForeignKey to companies.id), and created_at (DateTime with timezone, server default now()). A unique constraint SHALL exist on (matrix_id, requirement_id, triggering_report_id).
5. THE Traceability_Engine SHALL apply the AuditMixin to TraceabilityAlert and StaleLinkMarker models, enabling SQLAlchemy-Continuum versioning for change tracking on mutable records.
6. THE Traceability_Engine SHALL create appropriate database indexes: composite index on (company_id, generation_timestamp) for TraceabilityMatrix, composite index on (company_id, source_document_uuid, snapshot_date) for CoverageSnapshot, composite index on (company_id, is_resolved) for TraceabilityAlert, and composite index on (matrix_id, is_cleared) for StaleLinkMarker.
7. THE Traceability_Engine SHALL generate an Alembic migration for all new models, ensuring the migration is reversible: the upgrade function SHALL create all tables, indexes, and constraints; the downgrade function SHALL drop all tables created by this migration in reverse dependency order (StaleLinkMarker, TraceabilityAlert, CoverageSnapshot, TraceabilityMatrix) along with their associated indexes and constraints.
8. IF a CoverageSnapshot is created with coverage_percentage outside the range 0.0 to 100.0 or compliance_readiness_score outside the range 0.0 to 100.0, THEN THE Traceability_Engine SHALL reject the record with a validation error before persisting to the database.

### Requirement 11: Job Management for Matrix Generation

**User Story:** As a user who triggered a matrix generation, I want to track the progress of the generation and retrieve results when complete, so that I know when the traceability matrix is ready for review.

#### Acceptance Criteria

1. THE Traceability_Engine SHALL track all matrix generation jobs via the existing JobTracker service, creating a job with operation "traceability_matrix_generation" and estimated_duration_seconds based on the total number of source and target documents (30 seconds per document as baseline estimate, minimum 60 seconds).
2. THE Traceability_Engine SHALL update job progress monotonically as generation proceeds: 5% after request validation, 5-30% proportionally as requirements are extracted from source documents (evenly distributed across source documents), 30-60% proportionally as test cases are extracted from target documents (evenly distributed across target documents), 60-85% proportionally as Traceability_Links are established (evenly distributed across requirement-to-test matching passes), 85-90% during orphan detection and classification, 90-95% during Coverage_Metric computation, and 95-100% after Traceability_Matrix persistence. Progress SHALL never decrease from a previously reported value.
3. THE Traceability_Engine SHALL expose a GET /api/traceability/jobs/{job_id}/status endpoint that returns HTTP 200 with a JSON response containing: job_id, status (processing, completed, partial_success, failed), progress_percent (integer 0-100), current_phase ("validating", "extracting_requirements", "extracting_test_cases", "establishing_links", "detecting_orphans", "computing_metrics", "persisting_matrix"), requirements_extracted (integer), test_cases_extracted (integer), links_established (integer), orphans_detected (integer), error_message (null unless status is failed or partial_success, maximum 1000 characters describing the failure reason, truncated with ellipsis if the underlying message exceeds 1000 characters).
4. WHEN a matrix generation job completes with status "completed" or "partial_success", THE Traceability_Engine SHALL include in the job result: matrix_id, total_requirements, total_test_cases, total_links, coverage_percentage, orphan_requirements_count, orphan_test_cases_count, compliance_readiness_score, generation_duration_ms, and a summary_sentence (AI-generated summary of the traceability analysis, maximum 200 characters, truncated with ellipsis if the model produces a longer response; set to null if the AI model fails to produce a summary).
5. THE Traceability_Engine SHALL enforce a maximum generation timeout of 600 seconds per job. IF the timeout is exceeded, THEN THE Traceability_Engine SHALL set the job status to "partial_success", persist all Traceability_Links discovered so far as a partial matrix, record the list of unprocessed source requirement identifiers in the job metadata field "unprocessed_requirements", and set error_message to indicate the timeout with the count of unprocessed items.
6. THE Traceability_Engine SHALL scope all job status queries to the company identified by the X-Company-Id header. IF the X-Company-Id header is missing from a job status request, THEN THE Traceability_Engine SHALL return HTTP 400 with an error message indicating the header is required.
7. IF the job_id provided to the status endpoint does not exist or does not belong to the requesting company, THEN THE Traceability_Engine SHALL return HTTP 404 with an error message indicating the job was not found.
8. IF the JobTracker service is unavailable (database connection failure or query timeout exceeding 5 seconds) when creating a job record, THEN THE Traceability_Engine SHALL fail the generation request and return HTTP 503 with an error message indicating the job tracking service is temporarily unavailable.
9. IF a matrix generation job fails due to an unrecoverable error (not a timeout), THEN THE Traceability_Engine SHALL set the job status to "failed", populate error_message with the failure category and affected component (without exposing internal stack traces), and set progress_percent to the last successfully reported value.
10. IF a matrix generation request is submitted while a job with operation "traceability_matrix_generation" is already in "processing" status for the same set of source and target documents within the same company, THEN THE Traceability_Engine SHALL reject the request with HTTP 409 and return an error message indicating a generation is already in progress, including the existing job_id.
